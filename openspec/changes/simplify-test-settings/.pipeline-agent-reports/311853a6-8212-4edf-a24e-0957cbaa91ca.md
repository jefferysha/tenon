## 1. 测试档位 / 按改动选测试

| --- | --- | --- | --- |

## 2. 测试种类分类法

- Martin Fowler《Practical Test Pyramid》，<https://martinfowler.com/articles/practical-test-pyramid.html>，列出分层：Unit、Integration、Contract、UI、End-to-End、Exploratory。原文提醒："Don't become too attached to the names of the individual layers in Cohn's test pyramid." 以及 "The software development community simply hasn't managed to settle on well-defined terms around testing."
- Google 三级：80% 窄范围单测、15% 中等范围集成、5% 端到端（引文 "around 80% of our tests being narrow-scoped unit tests"、"15% medium-scoped integration tests"、"5% end-to-end tests that validate the entire system"，来源同 SWE Book 第 11 章），图注称 "Google’s version of Mike Cohn’s test pyramid."
- Playwright，<https://playwright.dev/docs/test-components>：组件测试是 "a regular Playwright end-to-end test that runs against a small story gallery page"，用同一个 runner。
- Cypress，<https://docs.cypress.io/app/core-concepts/testing-types>：两类，E2E 为 "tests your app from the web browser through to the back end of your application."，组件测试为 "Component tests differ from end-to-end tests in that instead of visiting a URL to pull up an entire app"。
- 「静态检查是否算测试」：本次未找到把 lint / typecheck 明确归入或排除出「测试」的一手文字。上面的主流分类（金字塔、Google sizes、Cypress 两类）都只讨论运行时测试，没有静态检查这一层。

事实小结：主流分层是 3 档（Google：小 / 中 / 大）到 5-6 档（Fowler）。Cypress 只有 E2E 与组件两类。工具文档本身承认命名不统一。「unit / integration / e2e」三层几乎是共同交集；静态检查与基准没有现成一手分类依据，属项目自定。

## 3. 保留注释地编辑 YAML

- `yaml`（eemeli），<https://eemeli.org/yaml/>：
  - CST 保留所有字符："it retains every character of the input, including whitespace."
  - 改 CST token 时："Best efforts are made to retain any comments previously associated with the `token`."
  - Document API 的输出格式由库决定，不沿用源文本："the simplest option for the value in question will always be chosen."
  - 已知局限："the library's comment handling is not completely stable, in particular for trailing comments." 与 "When creating, writing, and then reading a YAML file, comments may sometimes be associated with a different node."
  - `CST.setScalarValue`："Set the value of token to the given string value, overwriting any previous contents and type that it may have."（可只改被改节点的 token 文本）
  - CST 拼接 "applies no validation whatsoever, and simply concatenates the sources in their logical order."
  - `keepSourceTokens` 选项会在每个解析节点上附上对应 CST token。
  - 注意：`yaml` 是外部依赖，题设要求「不引入新依赖」，这里只作机制参考，仓库现有 `yaml-subset.ts` 是否同样可用由主线判断。
- ruamel.yaml，<https://yaml.dev/doc/ruamel.yaml/overview/>："block style and key ordering are kept"；保留注释的前提是 "normally not broken unless you severely alter the structure of a component"（举例为删除字典键、移除列表项）；"individual indentation of lines is not preserved"。
- Renovate：以 helmv3 的 `update.ts` 为例，<https://raw.githubusercontent.com/renovatebot/renovate/main/lib/modules/manager/helmv3/update.ts>，用正则做文本替换而非重新序列化，代码为 `content.replace(regEx(`^(?<version>version:\\s*).*$`, 'm'), `$<version>${newChartVersion}`)`，该文件未引入 YAML 解析器。这只证明这一个 manager 的做法，不是 Renovate 全部 manager 的统一机制；Renovate 通用的 `fileReplacePosition` 机制本次未找到一手来源。
- Dart `yaml_edit`，<https://pub.dev/packages/yaml_edit>："A library for YAML manipulation with comment and whitespace preservation."；局限："Users are not allowed to define tags in the modifications." 与 "Map keys will always be added in the flow style."。（搜索结果称 update 保留同级注释、remove 后 insert 不保留，该句只来自搜索摘要，未取到一手原文，仅作线索。）
- 搜索中出现 Rust 的 `yamlpatch`（Replace / Add / Remove / RewriteFragment，说明「best-effort」保留格式）与 `noyalib`，均只有搜索摘要，未取到一手页面，只作线索。
- Dependabot：未找到一手来源。
- kustomize / kyaml：搜索未得到关于 RNode 写入时保留注释的一手文字，README 链接 404，未找到。

事实小结：存在两类机制。一类是「按文本区间替换」（Renovate 正则、`yaml` 的 CST token 修改、搜索线索里的 yamlpatch），被改节点之外的字节不动。另一类是「解析成带注释的树再重新输出」（ruamel、`yaml` Document API），注释靠挂在节点上，结构变化大时会漂移或丢失。官方文档明确的局限是：尾随注释不稳定、删除条目会破坏注释、输出缩进可能被重排。被改节点内部的注释，在「区间替换」方案里会随该区间被替换而丢失（这是机制的推论，上述来源没有逐字说明）。

## 4. 运行仓库命令前的信任模型

| 工具 | 信任键 | 存放位置 | 多 worktree |
| --- | --- | --- | --- |
| direnv `allow` | 绝对路径 + 文件内容的 SHA-256 | 用户级 `$XDG_DATA_HOME/direnv/allow`（文件名为哈希） | 路径不同则哈希不同，不共享 |
| mise `trust` | 配置所在目录（解析后的真实路径） | 用户级 state directory | 链接 worktree 在主检出同路径被信任时继承；paranoid 模式不共享 |
| VS Code Workspace Trust | 文件夹 | Trusted Folders 列表（存放位置文档未写） | git worktree 文档未提 |
| git `safe.directory` | 目录路径（可 `*` 通配） | 仅认「受保护配置」（system / global / command），仓库本地配置忽略 | 按路径列出 |
| Nix `accept-flake-config` | 布尔开关 | nix.conf | 不适用 |

逐字引用：

- direnv man，<https://direnv.net/man/direnv.1.html>："`$XDG_DATA_HOME/direnv/allow` : Records which `.envrc` files have been `direnv allow`ed."；"Otherwise any git repo that you pull, or tar archive that you unpack, would be able to wipe your hard drive."
- direnv 源码 `internal/cmd/rc.go`，<https://raw.githubusercontent.com/direnv/direnv/master/internal/cmd/rc.go>：哈希为 `hasher.Write([]byte(path + "\n"))` 后拷入文件内容；allow 文件按该哈希命名放在 allow 目录；deny 文件只按路径哈希。检查顺序：deny 文件存在则 Denied；allow 哈希文件存在则 Allowed；否则查配置白名单（`WhitelistExact` 与 `WhitelistPrefix`，只按路径匹配）；否则 NotAllowed。
- mise 安全页，<https://mise.jdx.dev/security.html>："Trust records are kept in the state directory."、"Trust records use resolved paths."、"A config in a linked git worktree is trusted when the same path in the main checkout is trusted."、"Paranoid mode does not share trust between worktrees."、`trusted_config_paths` 为 "trusts configs under these paths without a prompt, including projects you create there later."（全局设置）。paranoid 模式下信任 "tied to the file's contents"（来自 trust 命令页的转述，页面原句较短，见 <https://mise.jdx.dev/cli/trust.html>）。
- mise 绕过漏洞：GHSA-436v-8fw5-4mj8（CVE-2026-35533），<https://osv.dev/vulnerability/GHSA-436v-8fw5-4mj8>，摘要 "Local settings bypass config trust checks"，细节 "`mise` loads trust-control settings from a local project `.mise.toml` before the trust check runs." 与 "An attacker who can place a malicious `.mise.toml` in a repository can make that same file appear trusted"。受影响起 2026.2.18。修复版本有分歧：OSV 页写 fixed 2026.6.4，二手镜像（cvefeed 等）写 2026.4.6 或更高，主线若引用请直接查 GitHub advisory。另有 GHSA-77g9-363w-rccq（CVE-2026-55441，task-include 路径在信任检查前执行模板），只见于搜索摘要与二手镜像，未取到一手页面，补丁状态不明。教训（事实层面）：信任判定所用的设置若可由被检仓库自己提供，就能自我授权。
- VS Code，<https://code.visualstudio.com/docs/editing/workspaces/workspace-trust>："When you trust a folder, it is added to the **Trusted Folders & Workspaces** list"；"You can also trust a parent folder, which applies trust to the parent folder and all its subfolders."；"VS Code tasks can run scripts and tool binaries."（Restricted Mode 限制任务）。
- git config，<https://git-scm.com/docs/git-config>：`safe.directory` 为 "specify Git-tracked directories that are considered safe even if they are owned by someone other than the current user"；"This config setting is only respected in protected configuration (see SCOPES). This prevents untrusted repositories from tampering with this value."；"To completely opt-out of this security check, set `safe.directory` to the string `*`."；"Giving a directory with `/*` appended to it will allow access to all repositories under the named directory."
- Nix，<https://nix.dev/manual/nix/stable/command-ref/conf-file.html>：`accept-flake-config` 为 "Whether to accept Nix configuration settings from a flake without prompting."，默认 `false`，该项属实验特性；`trusted-users`："Adding a user to `trusted-users` is essentially equivalent to giving that user root access to the system."
- asdf、devbox：未找到信任模型。搜索只证实 devbox 的 `init_hook` 在每次 shell 启动时执行，未发现信任门（原话来自搜索摘要的转述，未取到一手页面）。
- direnv 的 allow 绕过 CVE：搜索未找到。

`git rev-parse --git-common-dir` 与 worktree：

- <https://git-scm.com/docs/git-rev-parse>："`--git-common-dir`: Show `$GIT_COMMON_DIR` if defined, else `$GIT_DIR`."（该页对 worktree 无专门段落）。
- <https://git-scm.com/docs/git-worktree>："Within a linked worktree, `$GIT_DIR` is set to point to this private directory (e.g. `/path/main/.git/worktrees/test-next`) and `$GIT_COMMON_DIR` is set to point back to the main worktree's `$GIT_DIR` (e.g. `/path/main/.git`)."；"refs are shared across all worktrees, except `refs/bisect`, `refs/worktree` and `refs/rewritten`."；"By default, the repository `config` file is shared across all worktrees."
- 因此官方文字支持：同一仓库的所有链接 worktree 的 common dir 指向同一个主 `.git` 目录。另需注意两点。其一，主 worktree 的 `--git-common-dir` 可能返回相对路径（该页说 `--git-dir` 在相对时相对当前目录，对 common-dir 同类行为页面未明说，此点未验证），所以需要取真实路径。其二，仓库内的 `config` 是仓库内文件，攻击者控制的仓库可以自带；这里的信任键只是路径，不是内容摘要，仓库被替换为另一个同路径仓库时键不变（推论，需主线评估；direnv 把内容摘要纳入键正是为避免此类情形）。
- 「把信任按命令字符串共享到别的仓库」的已知攻击：未找到专门讨论；最接近的一手事实是 mise 漏洞（信任设置由被检仓库提供）与 git 的 "protected configuration"（信任设置不得由仓库本身提供）。

## 5. 构建 / 测试指纹排除测试输出

- Turborepo，<https://turborepo.dev/docs/reference/configuration>：`inputs` 为 "A list of file glob patterns relative to the package's `package.json` to consider when determining if a package has changed."，默认 `[]` 即 "all files in the package that are checked into source control."（所以默认按 git 跟踪与 gitignore 过滤）；"Using the `inputs` key opts you out of `turbo`'s default behavior of considering `.gitignore`."；可用 `$TURBO_DEFAULT$` 恢复并追加排除，如 `["$TURBO_DEFAULT$", "!README.md"]`；`package.json`、`turbo.json`、锁文件 "are **always** considered inputs, even if you try to explicitly ignore them."；`outputs` 为任务成功后缓存的文件，输出路径需在仓库根内。
- Nx，<https://nx.dev/docs/reference/inputs>："Nx leaves files listed in `.gitignore` out of a task's inputs, so a change to one of them doesn't invalidate the cache."；"Prefixing a source file input with `!` will exclude the files matching the pattern"；`includeIgnored: true` 可让被忽略文件参与。`outputs` 的定义该页无，未找到一手定义。
- Gradle，<https://docs.gradle.org/current/userguide/build_cache.html>："Gradle can compute a build cache key that uniquely defines the task’s outputs based on its inputs."；"Missing task outputs can cause build failures if Gradle does not completely capture all outputs for a given task."；`@Internal` 属性不计入键的具体文字本次未取到。
- Bazel：测试输出放在专用目录，不进输入。<https://bazel.build/reference/test-encyclopedia>：`TEST_UNDECLARED_OUTPUTS_DIR` 为 "absolute path to a private writable directory (used to write undeclared test outputs)."，其内文件 "will be zipped up" 并 "added to an outputs.zip file under bazel-testlogs."；`XML_OUTPUT_FILE` 为 "Location to which test actions should write a test result XML output file."。Bazel hermeticity 页（<https://bazel.build/basics/hermeticity>）本次未取到关于声明输入的原文。
- 「按被 git 忽略」排除：Turborepo（默认）与 Nx（默认）都是。「按扩展名排除」：这几个工具的文档中均未找到。
- 「借输出目录藏源码」的安全讨论：未找到一手来源。最接近的是 Nx 博客 <https://nx.dev/blog/can-you-trust-your-build-cache>："Editing `shared/vite-shared-plugin.js` changes the output but not the cache key."、"The tool trusts the author to have enumerated everything and verified configuration correctness."、"Audit the usual undeclared inputs."，讲的是未声明输入导致缓存键不反映文件，而不是输出目录藏源码；Nx Cloud Task Sandboxing 可以记录声明之外的读写。可视为同类风险的旁证，不是直接证据。

## 6. 测试报告里的绝对路径

- Jest，<https://jestjs.io/docs/configuration>：`rootDir` 默认为 "The root of the directory containing your Jest config file or the package.json or the pwd if no package.json is found"；"Using '<rootDir>' as a string token in any other path-based configuration settings will refer back to this value."；`coveragePathIgnorePatterns` 建议用 `<rootDir>` 以免 "in different environments that may have different root directories"。`testResultsProcessor` 的负载里 `"testFilePath"` 是 "absolute path to test file"。即 `<rootDir>` 是配置输入的占位符，不是对输出做改写；Jest 对 reporter 输出里绝对路径的处理，页面未写，未找到。
- Vitest，<https://vitest.dev/guide/reporters.html>：JUnit 的 `classnameTemplate` 默认 "Relative file path"；`{filename}` "resolves to the **relative path** from the project root."，`{filepath}` 是绝对路径；`addFileAttribute` 默认 `false`；JSON reporter 示例里的 `name` 是绝对路径（"/root-directory/__tests__/test-file-1.test.ts"），页面未说明可改写。
- pytest，<https://docs.pytest.org/en/stable/reference/customize.html>：rootdir 用于 "Construct *nodeids* during collection"，nodeid 以 rootdir 为根，因此 JUnit 里的 `classname` / `file` 属性是相对 rootdir 的；这里引用的是文档对 nodeid 的描述，JUnit 里各属性是否一定相对，页面例子里 `file="test_function.py"` 是相对形式（<https://docs.pytest.org/en/stable/how-to/output.html>）。`junit_family` 默认 `xunit2`，`junit_logging` 默认 `no`，即默认不把捕获输出写进 JUnit（<https://docs.pytest.org/en/stable/reference/reference.html>）；失败回溯文本里是否含绝对路径，文档未写，未找到。
- Playwright，<https://playwright.dev/docs/test-reporters>：JUnit `outputFile` 为 "Full path to the output file."；`stripANSIControlSequences` 为 "Whether to remove ANSI control sequences from the text before writing it in the report."；页面未说明报告里文件路径是否相对。
- JUnit XML 通用规范对路径的约定、「把仓库根改写为相对路径或占位符」的通用做法：未找到一手来源。
