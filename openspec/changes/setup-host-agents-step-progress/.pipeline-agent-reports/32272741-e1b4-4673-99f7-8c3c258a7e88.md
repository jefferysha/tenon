### 与计划不一致、需要主线知道的两处（都是为了不改用例行为、不出现粘贴重复）

1. **`useWorktreeInitFixture()` 的返回值比 plan 的 Interfaces 多一个 `temps: string[]`。** 原用例里 `不是 git 仓库` 与 `已在 linked worktree 里` 两条直接 `temps.push(...)`（自己建的临时目录登记给 afterEach 清理），不暴露 `temps` 就无法保持这两条的清理行为。用例体里写成 `fx.temps.push(...)`。
2. **`TWO_STEP_WF` 移到 support 文件导出，`init.test.ts` 前半段改为 `import { TWO_STEP_WF } from './init-worktree-test-support.js'`。** 它被 `init.test.ts` 前半段（2 处）与 worktree 组的「自定义工作流」用例（1 处）共用；若原样各留一份，就是 21 行跨文件粘贴重复（代码规模口径）。常量内容与注释逐字不变，只是定义位置变了。这使 `init.test.ts` 的改动不是纯删除：除删除整块外，还有「删掉 21 行常量定义 + 改 import」。若主线更想严格按 plan（`init.test.ts` 前半段零改动），回退办法是把该常量原样放回 `init.test.ts` 并在 `init-worktree.test.ts` 里另留一份（代价是 21 行重复）。

8. .worktrees/demo 已有同名普通目录：报冲突退出，目录内容不变，没有分支和任务状态
9. 分支 tenon/demo 已存在：失败退出，.worktrees/demo 与任务状态都没有创建

17. 不带 --json：stdout 保持为空（init 的 stdout 契约不变）

`[SETUP]`（11 条，`init-worktree-setup.test.ts`）：
1. 主检出的信任条目带进新 worktree：trusted 含同一摘要，approvals 与 writes 为空，主检出的封存不变
2. 目录受信任且声明了 setup：在新 worktree 里执行（主检出不受影响），输出在 stderr，最后两行仍是 worktree 路径与切换做法
3. setup 经注入的执行器在 worktree 里执行：收到命令原文与 worktree 路径
4. --json：setup 往 stdout 和 stderr 各写一行，stdout 仍只有那一行 JSON（setup 的输出转到 stderr）
5. 目录未受信任：不执行 setup，提示「未受信任」与 tenon test trust，init 仍成功
6. 目录没有 setup：跳过，不报错，不执行
7. 项目没有测试目录：不提 setup，不执行
8. setup 退出码 1：init 仍返回 0、任务已建好，输出 WARN 与在 worktree 里重跑的命令；--json 的 stdout 仍是一行
9. 在 worktree 里改了套件命令：该 worktree 里判为未信任，主检出的封存不变
10. 主检出的目录有未提交改动并已在主检出信任：新 worktree 里是 HEAD 版本，判为未信任，setup 不执行并提示
11. 原地建立（TENON_INIT_IN_PLACE=1）：没有新 worktree，不继承信任也不执行 setup
