## Q1 Claude Code 子代理加载时机

### 结论 1.1：文件监听存在，但模型能派发的子代理类型在「回合开始」才刷新；同一回合内新写的文件不能派发（已由会话记录证实，官方文档未写这一点）

官方 sub-agents 文档（https://code.claude.com/docs/en/sub-agents）逐字：

> Claude Code watches `~/.claude/agents/` and `.claude/agents/`. When you add or edit a subagent file on disk, or ask Claude to write one for you, Claude Code detects the change within a few seconds and the next delegation uses the updated definition, with no restart needed.

文档同时列出仍需重启的三种情况：

> The watcher covers only directories that existed when the session started, so after creating a scope's first agent file in a new `agents` directory, restart to load it.
> Claude Code doesn't watch `.claude/agents/` inside directories added with `--add-dir` or `/add-dir`, so after adding or editing a subagent there, restart to load the change.
> （第三种：以 `--disable-slash-commands` 启动的会话完全不监听。）

另一处（同文档创建子代理一节）：

> If Claude can't find the new subagent, restart Claude Code and try again. This happens only when `~/.claude/agents/` didn't exist before the session started, because a running session doesn't detect a newly created `agents` directory.

本仓的实测证据：

- 会话 `4f9542da`（`~/.claude/projects/-Users-a1234-Documents-code-manager-projects-tenon-local/4f9542da-59e8-40c2-9bf5-5324115f6498.jsonl`），版本字段全部是 `2.1.292`，与本机当前版本相同。报错原文：`Agent type 'tenon-researcher' not found. Available agents: claude, claude-code-guide, codex:codex-rescue, Explore, general-purpose, impeccable-*, Plan, sonnet-reviewer, sonnet-worker, statusline-setup, trellis-check, trellis-implement, trellis…`。
- 项目的 `.claude/agents/` 目录在该会话之前就存在：`sonnet-worker.md` 是 9 月 29 日的，`trellis-*.md` 是 9 月 8 日的（`ls -la .claude/agents`）。所以不属于文档里「目录会话启动时不存在」的例外。
- `design.md` 的初始假设是「只在会话启动时读取」；下面的补充观测表明实际是「下一个用户回合开头刷新」。

**主线补充的观测与我的核对（会话记录 jsonl，可回溯）**

观测 A（来源：主线观测，我已在记录里核对）：本会话 `be80e77d` 里，`tenon agent prompt` 在 09:49:04-09:49:10 UTC（本地 17:49）写出 `tenon-{architecture,backend-quality,security}.md`；用户消息 09:59:37 之后 5 秒，09:59:42 出现一条 `type: attachment`、`attachment.type: "agent_listing_delta"` 的记录，渲染成系统提醒：`New agent types are now available for the Agent tool:\n- tenon-architecture: …`，`addedTypes` 只含这三个。写文件到列表更新之间隔了 10 分钟，更新发生在一个新用户回合的开头，不在回合中途。

观测 B（来源：主线观测，我已在记录里核对）：会话 `4f9542da` 的时间线（UTC）：09:22:22 用户消息；09:24:52 唯一一条 `agent_listing_delta`，`addedTypes` 是启动时的全部类型（claude、Explore、general-purpose、sonnet-worker、trellis-* 等 16 个，不含 tenon-*）；09:28:41 用户消息；09:29:00-09:29:05 `tenon init`（写文件）；09:31:15 `tenon agent prompt`；09:33:22 派发返回 `Agent type 'tenon-researcher' not found. Available agents: …`（列表不含 tenon-*）。从 09:28:41 到 09:33:22 之间没有新的用户消息，也没有第二条 `agent_listing_delta`。整个会话只有这一条 delta。

这两条合起来说明：Claude Code 维护一份「Agent 工具可用类型」清单，磁盘上的新文件由文件监听检测到后，**通过 `agent_listing_delta` 在下一个用户回合开头注入模型上下文并更新清单**；同一回合内派发一个尚未进清单的类型会被拒（报错列出的 Available agents 就是这份清单）。这与官方文档「detects the change within a few seconds and the next delegation uses the updated definition」不矛盾的读法是：文档里的 next delegation 指下一回合的派发，而不是同一回合。我上一版把二者写成冲突，该判断作废。`design.md` 的初始假设「只在会话启动时读取」也不准确：正确说法是「会话中途新增的文件，下一个用户回合开始时才可派发」。

对 CHANGELOG 与文档的核对：

- CHANGELOG（`github.com/anthropics/claude-code/blob/main/CHANGELOG.md`）里搜索 `agent_listing`、`New agent types`、`agent types`、`listing`、`file watcher` 的 agents 相关条目，**未找到**描述这一刷新机制的发行说明。相关的间接条目只有：`Fixed the Agent tool description referencing an agent list that is never delivered when running with --bare or with attachments disabled`（说明 Agent 工具描述里的 agent 清单是通过 attachment 投递的，`--bare` 或关闭 attachments 时不投递）和 `Fixed the Agent tool in claude mcp serve always reporting no available agents and rejecting every subagent_type`。这两条是旁证，不是对「回合开头刷新」的明文说明。
- 官方文档 sub-agents 页：没有 `agent_listing_delta` 或 `New agent types` 字样（grep 无结果），也没有写「同一回合内新增文件不能派发」。「回合开头刷新、回合内不刷新」因此只有本仓会话记录这一份一手证据，**文档未写**。
- 我没有找到官方对「每次 query 开始时刷新」这个说法的明文，这个说法与记录吻合（delta 在用户消息后 5 秒出现），但吻合不等于文档确认。

对方案的影响（下一段保留原有判断，并据此修正）：

- 「会话中途写文件、同一回合派发」不可行，这就是 `not found` 的原因；与 init 写文件的位置（项目级还是用户级）无关，只和「写入与派发是否在同一个用户回合」有关。
- 由此「必须开新会话」这个前提需要放宽：安装命令写完后，**下一个用户回合**就可用，不必重开会话；`tenon agent prompt` 提示的措辞应是「下一条用户消息起生效」。这一点同样适用于 `tenon init` 在会话里建的第一个任务：若 init 仍在会话中写项目级文件，用户只需再发一条消息，但本回合内的第一次派发仍必须退回通用子代理。
- 「目录监听只覆盖会话启动时已存在的目录」这条例外依然成立：用户级 `~/.claude/agents/` 在本机已存在（里面有 impeccable-*.md），项目级 `.claude/agents/` 也已存在，所以这两个目录对监听都有效；全新机器上首次建目录才需要重启。
- 因此「用户级 vs 项目级」的取舍里，「开新会话才生效」这条理由弱化了：两者都是下一回合生效。剩下的理由是 Q5 列的所有权、跨项目覆盖和卸载路径。
- 仍然需要保留「派发前如实判定」：同一回合内（init 与派发之间没有新用户消息）文件虽在磁盘上，模型清单里没有，必须直接返回通用子代理；仅凭磁盘文件存在就返回 `tenon-<name>` 会重现 `not found`。这是 `design.md` 一致性判定的一个漏洞：它只比较文件内容，没有考虑「文件在当前回合内才写入」。判断「该文件在本回合开始前就已存在」需要一个信号（例如比较文件 mtime 与会话当前回合开始时间，或读取会话 transcript），这不是一手文档提供的能力，我没有找到现成的 hook 字段给出「本回合开始时间」；`UserPromptSubmit` hook 可以在回合开头记一个时间戳，属于可行方向，未验证。

### 结论 1.2：优先级

同文档表格（逐字，从高到低）：

| Priority | Location | Scope |
| 1 | Managed settings | Organization-wide |
| 2 | `--agents` CLI flag | Current session |
| 3 | `.claude/agents/` | Current project |
| 4 | `~/.claude/agents/` | All your projects |
| 5 | Plugin's `agents/` directory | Where plugin is enabled |

所以项目级 `.claude/agents/tenon-*.md` 会遮住用户级 `~/.claude/agents/tenon-*.md`。旧逻辑残留的项目级文件会盖住新装的用户级文件，`design.md` 的这条风险属实，迁移清理方案要覆盖它。

### 结论 1.3：`/agents` 命令

文档逐字：

> Running `/agents` prints a reminder to ask Claude or edit `.claude/agents/` and `~/.claude/agents/` directly.

> On Claude Code v2.1.197 and earlier, `/agents` opens an interactive wizard…

CHANGELOG 2.1.198：`Removed the /agents wizard; ask Claude to create or manage subagents, or edit .claude/agents/ directly`。所以没有「刷新」命令。

### 结论 1.4：插件自带 agents

文档逐字：

> Plugin `agents/` directories are also scanned recursively. Unlike project and user scopes, a subfolder inside a plugin's `agents/` directory becomes part of the scoped identifier: a file at `agents/review/security.md` in plugin `my-plugin` registers as `my-plugin:review:security`.

> `name` … Names can't contain `:`, which is reserved for plugin-scoped identifiers such as `my-plugin:reviewer`

插件子代理的限制（逐字）：

> For security reasons, plugin subagents don't support the `hooks`, `mcpServers`, or `permissionMode` frontmatter fields.

即插件 agent 命名是 `<插件名>:<agent名>`（本机插件名 `tenon`，会是 `tenon:researcher`），加载时机文档未单独说明。它是静态随插件分发的，而 Tenon 的 agent 库有用户级和项目级自定义层，且任务冻结的是某一版定义，插件分发只能覆盖官方 10 个。这只是备选路径，未调研其与冻结一致性的兼容性。

## Q2 hook 的 `systemMessage`

来源：https://code.claude.com/docs/en/hooks（抓取为 `hooks.md` 后 grep，行号为该文件内行号）。

### 结论 2.1：PostToolUse 的 `systemMessage` 是给用户看的警告，文档没有逐事件说明它在终端的确切样式

通用字段表（逐字）：

> `systemMessage` | none | Warning message shown to the user. In Agent SDK and `--output-format stream-json` output, it can arrive as an `SDKInformationalMessage`

> Universal fields like `continue` are listed in the table below. Every event accepts them, but some events discard them or deliver `systemMessage` somewhere other than the transcript. Each event's section says so.

PostToolUse 一节（`### PostToolUse`，hooks.md 第 2016-2121 行）没有写「丢弃 `systemMessage`」，也没有写它出现在哪里。明确丢弃它的事件有：Setup、InstructionsLoaded、MessageDisplay、Notification、ConfigChange、PreCompact、PostCompact、WorktreeRemove、SessionEnd 等，PostToolUse 不在其中。据此：PostToolUse 的 `systemMessage` 按默认规则「Most events: Shows in the transcript」显示给用户。但「终端里具体怎么渲染（一行警告、折叠与否）」文档未写，**这一点要真机看**。

### 结论 2.2：是否进入模型上下文，文档未说明；进入上下文的是 `additionalContext`

`additionalContext`（逐字）：

> The `additionalContext` field passes a string from your hook into Claude's context window. Claude Code wraps the string in a system reminder and inserts it into the conversation at the point where the hook fired.

> Return `additionalContext` inside `hookSpecificOutput` alongside the event name

`systemMessage` 被描述为「shown to the user」，没有说进入模型上下文。只有后台异步 hook 的 `systemMessage` 被明说「delivers … to Claude on the next conversation turn … Unlike a synchronous hook's `systemMessage`, neither field is shown to you」（hooks.md 第 3740 行），反过来印证同步的 `systemMessage` 是给用户看的。PostToolUse 同步 hook 的 `systemMessage` 是否会被模型看到：**未找到明文**。

### 结论 2.3：`suppressOutput` 无效

> `suppressOutput` | `false` | Has no effect: Claude Code accepts the field but doesn't act on it. A successful hook's stdout is never shown in the transcript and is recorded in the debug log

所以普通 stdout 不会在终端出现，想让用户看到只能走 `systemMessage`（或 `terminalSequence` 这类终端序列，不适合打印清单）。

### 结论 2.4：matcher、`if` 过滤、输入字段

- PostToolUse 按工具名匹配：「Matches on tool name, same values as PreToolUse.」`matcher: "Bash"` 可以只匹配 Bash。
- 只在成功后触发：「Runs immediately after a tool completes successfully.」Bash 非零退出走 PostToolUseFailure（其输入的 `error` 以 `Exit code N` 开头）。所以 PostToolUse 触发就意味着该命令 exit 0。
- 输入含 `tool_input` 与 `tool_response`：「The input includes both `tool_input`, the arguments sent to the tool, and `tool_response`, the result it returned.」Bash 的 `tool_input.command` 可取（本仓 `hooks/json-input.sh` 的 `pipeline_json_get_command` 已在用）。**Bash 的 `tool_response` 形状是 `{stdout, stderr, interrupted, isImage}`，没有 `exit_code` 字段**（hooks.md 第 2089 行：「`Bash` returns an object with `stdout`, `stderr`, `interrupted`, and `isImage` fields」）。我抓取摘要时曾得到含 `exit_code` 的示例，原文没有，已按原文纠正。
- hook 条目有 `if` 字段，可在拉起进程之前过滤（逐字）：

> `if` | no | Permission rule syntax to filter when this hook runs, such as `"Bash(git *)"` or `"Edit(*.ts)"`. The hook command only runs if the tool call matches the pattern.

  例如 `matcher: "Bash"` + `if: "Bash(tenon *)"` 只在命令含 `tenon …` 子命令时才起进程，文档写明这样可以「avoiding the process spawn overhead」。但 `if` 一个条目只能放一条规则，且「best-effort」，无法判断时仍会运行；`if` 只能到 `tenon *` 这一级，区分 `init|transition|…` 仍要脚本里做。

### 附带发现（与本变更无直接关系，低优先级）

`hooks/test-nudge.sh:122` 与 `hooks/interactive-skill-gate.sh:182` 输出的是顶层 `{"additionalContext":"..."}`，而 Claude 文档要求 PostToolUse 的 `additionalContext` 放在 `hookSpecificOutput`（含 `hookEventName`）里。顶层写法在 Claude Code 是否生效，文档没有说，我没有实测。若不生效，这两个提醒在 Claude Code 上是静默失效的。作为 finding 记在末尾。

## Q3 Codex

### 结论 3.1：子代理文件位置明确；「会话启动还是每次派发时读」文档没有直接说，源码显示在配置装载时读取

官方文档（`developers.openai.com/codex/subagents` 308 重定向到 https://learn.chatgpt.com/docs/agent-configuration/subagents）逐字：

> To define your own custom agents, add standalone TOML files under ~/.codex/agents/ for personal agents or .codex/agents/ for project-scoped agents. Each file defines one custom agent. Codex loads these files as configuration layers for spawned sessions, so custom agents can override the same settings as a normal Codex session config.

文档没有写「会话启动时读取」或「每次派发读取」。源码（https://github.com/openai/codex ，`codex-rs/agent-roles/src/loader.rs` 的 `load_agent_roles`，`codex-rs/core/src/config/mod.rs:3832` 在构造 `Config` 时调用 `load_agent_roles(fs, &cfg, &config_layer_stack, &mut startup_warnings)`）显示角色在配置装载阶段、遍历各配置层的 `agents` 目录（`config_folder.join("agents")`）时一次性发现。因此倾向于「随配置装载读，会话内新增不一定被识别」，但我没有核实会话中途是否会重新构造 `Config`，**这条证据强度为中，不是确证**。

### 结论 3.2：Codex 有 PostToolUse，且支持 `systemMessage`

hooks 文档（https://learn.chatgpt.com/docs/hooks，原 `developers.openai.com/codex/hooks`）逐字：

> PostToolUse supports systemMessage , continue: false , and stopReason . suppressOutput is parsed but not currently supported for that event.

> systemMessage Surfaced as a warning in the UI or event stream

> Plain text on stdout is ignored. JSON on stdout can use systemMessage and this hook-specific shape: …

> PostToolUse observes Bash, file edits performed through apply_patch, MCP tool calls, and other local function tools（Shell commands 与 Unified exec 都「Match as Bash」）

输入含 `tool_name`、`tool_use_id`、`tool_input`（「Bash and apply_patch use tool_input.command」）、`tool_response`。matcher 对 PostToolUse 生效（示例 `"matcher": "^Bash$"`）。特性开关写作 `[features].hooks`（旧别名 `codex_hooks` 仍可用）。

所以 `design.md` 里「Codex 宿主上的进度展示只在确认 hook 支持 `systemMessage` 时才做」这个条件已满足。Codex 的 `systemMessage` 具体显示位置只写了「UI or event stream」，样式未知。

### 结论 3.3：仓库对 Codex hook 的现有处理（旁证）

- Codex 插件清单 `.codex-plugin/plugin.json` 的 `"hooks": "./hooks/hooks.json"`：与 Claude 插件共用同一份 `hooks/hooks.json`。因此新增 PostToolUse 条目会同时在两个宿主生效，脚本要同时认 `Bash`（Claude）与 Codex 的 `Bash`/`exec`/`command_execution`（`hooks/json-input.sh:306` `pipeline_json_is_command_tool` 已处理）。
- `packages/cli/src/commands/setupEnvironment.ts:341` `migrateLegacyCodexHooks` 读写 `~/.codex/hooks.json`，只用来清理旧 adapter 的 hook，说明 `tenon setup --codex` 已有写用户级 Codex 目录的先例。
- `adapters/codex/hooks.json` 是旧 adapter（PostToolUse 走 `track.sh`），不是插件路径。

## Q4 Claude Code 的 Todo 工具可用条件

**结论：缺失是模型决定的，不是环境故障。一手源给出了完整条件。**

CHANGELOG（https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md）：

- 2.1.233：`Todo/task-tracking tools (TaskCreate/Get/Update/List, TodoWrite) are no longer available on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and newer models; set CLAUDE_CODE_ENABLE_TODO_TOOLS=1 to bring them back`
- 2.1.268：`Changed the task-tracking tools (TaskCreate/Get/Update/List, TodoWrite) to be offered only on Claude 3.x, Opus 4.0–4.7, Sonnet 4.0–4.6, Haiku 4.5; set CLAUDE_CODE_ENABLE_TODO_TOOLS=1 elsewhere`
- 2.1.286：`Fixed foreground subagents sometimes missing the task-tracking tools (TaskCreate/Get/Update/List, TodoWrite) in sessions that have them enabled`

工具参考（https://code.claude.com/docs/en/tools-reference ，`Task tool availability` 一节）逐字：

> The task-tracking tools, `TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`, and `TodoWrite`, are available by default only on Claude 3.x models, Opus 4 through 4.7, Sonnet 4 through 4.6, and Haiku 4.5.

> On every other model, Claude Code leaves the tools out unless you opt in. The same applies to a model ID Claude Code doesn't recognize, such as a custom model name served through an LLM gateway.

开启方式：`CLAUDE_CODE_ENABLE_TODO_TOOLS=1`（环境变量，要求 v2.1.233+）、`--allowedTools TaskCreate`、`--tools` 列出这些工具。`CLAUDE_CODE_ENABLE_TASKS=0` 用来在有工具的会话里改用旧的 `TodoWrite`（env-vars 文档）。

对本变更的含义：用户在 Sonnet 5 / Opus 4.8 及更新模型的会话里默认就没有 Todo 工具，这是官方行为，不会因为 Tenon 的 skill 要求而出现；而且官方给出的理由是新模型「keeps track of multi-step work without a written checklist」。skill 第 5 步要求建 Todo，在这些模型上必然静默失效，这印证了「用 hook 由代码保证进度显示」的方向。`design.md` 的非目标「不排查 Claude Code 缺少 Todo 工具的原因」可以改为「原因已查明：模型相关，见本报告 Q4」。

## Q5 仓库内：setup / update / sync / uninstall 与宿主 agent 文件

### 5a 每条命令的作用域与写入位置

| 命令 | 作用域 | 写什么（证据） |

### 5b 所有权清单

- `.pipeline-owned.json` 是**项目根**文件（`packages/kernel/src/state/ownership-manifest.ts` 的 `OWNED_MANIFEST`，`host-agent-files.ts:23` `HOST_AGENT_OWNED_MANIFEST = OWNED_MANIFEST`），格式 `path -> 内容 hash`（`ownership.ts` 顶注 A①⓪）。宿主 agent 文件与 `tenon uninstall` 共用这一份。
- uninstall 的用法（`ownership.ts` 顶注 D 与 `uninstall.ts`）：只删清单内文件；不透明文件「unmodified→删、modified→保留」；清单缺失 exit 0，清单空 exit 1。
- **没有用户级的所有权记录**可复用：全仓没有针对 `~/.claude` 或用户级文件的 hash 清单；`managed-release-journal` / `runtime-rollback-journal` 是 runtime 发布与回滚的事务日志，不是文件所有权。写用户级 agent 文件需要新建一份用户级清单（建议放产品 `stateRoot` 或 `configRoot`），并让 uninstall / 新的卸载路径能读它。`uninstall` 现在的 homedir 守卫（cwd 为 `$HOME` 就拒绝）也说明它不是为用户级文件设计的。
- **现有交互风险（新发现）**：`sync --migrate` 会调用 `pruneOwnedManifest`（`ownership-manifest.ts:206-233`），其规则是「key 不在 known 集（`knownKeys` ∪ 迁移路径，且 `.pipeline/` 恒留、AGENTS.md 特判）就剪掉」。`runSync` 的 `known` 只在有 Codex 目录时才含 `CODEX_UPGRADE_MARKERS`，否则为空。也就是说，项目里记着的 `.claude/agents/tenon-*.md` 条目在 `tenon sync --migrate` 时会被当成孤儿从清单里剪掉（文件本身不删），之后这些文件既不受 uninstall 管，也不受 `pruneHostAgentFiles` 回收。这条我是读代码得出的，没有跑过；是否确实发生要实测。对迁移方案有影响：旧项目的清单条目可能已经丢了所有权。
- 本仓当前的 `.pipeline-owned.json`（未跟踪）里只有 7 个 `.claude/agents/tenon-*.md` 条目，没有别的，说明这份清单在本项目里目前只为宿主文件服务。

### 5c agent 库的位置与是否触发宿主文件

- 三层（`packages/cli/src/commands/agent-library.ts` 顶注：「三层来源：官方（随发行包，只读）/ 自定义（用户级 config）/ 项目（`<项目>/.tenon/agents`，随仓库共享）。同名时项目级优先于自定义；官方名字任何一层都不能用」）。
- 存储（`packages/kernel/src/infrastructure/agent-store.ts` 顶注与 `loadAgentLibrary`）：官方 `<configRoot>/agents/builtin`、用户级 `<configRoot>/agents/custom`、项目 `<项目>/.tenon/agents`。本机 `configRoot` = `~/Library/Application Support/tenon/config`，`agents/builtin` 里有 10 个官方 agent（architecture、backend-quality、builder、code-review、code-size、e2e、frontend-quality、researcher、security、spec-consistency），`custom` 目录存在。`loadAgentLibrary` 每次加载还会把发行包里的 builtin 同步进 `configRoot`（`ensureBuiltinAgents`）。

## Q6 hook 分发、热路径、先例、步骤状态数据源

### 6.1 分发链路

- `hooks/hooks.json` 里每个条目都是 `bash "${HOME}/.local/bin/tenon-hook" <hook-id>`。
- `~/.local/bin/tenon-hook`（本机实测）是 `#!/bin/sh` 启动器，由 managed runtime 发布（`packages/cli/src/runtime/launchers.ts` / `runtime/tenon-bootstrap.mjs` 里的 `stableLauncherText`，`setup` 与 `session-start` 时修复），最后一行是 `exec <node> <bootstrap>/active.mjs hook "$@"`。
- `runtime/tenon-bootstrap.mjs:1319-1348` `runHook`：校验 `hookId` 匹配 `^[a-z0-9-]+$`，读 stdin，找到 active release 的 payload，然后 `spawnSync('/bin/bash', [join(active.payload, 'hooks', `${hookId}.sh`)], { input, … })`。映射规则就是 hook-id → `hooks/<hook-id>.sh`。所以新增 hook 的步骤是：加 `hooks/step-progress.sh` + 在 `hooks.json` 注册 `tenon-hook step-progress`；`release-payload.ts:234,298` 会校验 payload 里 `hooks.json` 与 `hooks/*.sh`，新文件要在打包校验里能通过。
- **重要事实**：每次 hook 调用都会先经过 `tenon-hook` → **Node 启动**（`active.mjs`）→ 再起 bash 脚本。所以「PostToolUse 热路径不起解释器」只约束脚本本身（bash 内），而每次工具调用的 node 启动成本已经存在。已有的 PostToolUse `*` 条目有 4 个（`skill-tracker`、`interactive-skill-gate`、`terminal-activity`、`test-nudge`），再加一个就是第 5 个 node + bash 链。可以用 hooks.json 的 `if: "Bash(tenon *)"`（见 Q2）在 Claude 侧省掉大多数调用的整条链。Codex 侧的 `if` 支持我没有查。

### 6.2 约束写在哪里

脚本头注释反复引用「CONTRACT §5.4」「CONTRACT §5 硬规则 4：PostToolUse shim 零解释器 spawn」（`hooks/skill-tracker.sh`、`test-nudge.sh`、`statusline.sh`）。我没有在仓库里找到名为 CONTRACT 的 Markdown 文件含 §5.4（grep 无结果）。约束的一手出处只剩各脚本的头注释；`adapters/contract.md` 存在但我没有逐节核对是否就是它。

注意并非严格零解释器：`skill-tracker.sh` 在 Skill 工具命中时会 `node "$BUNDLE" internal-native-skill-receipt …`。所以先例是「绝大多数路径零解释器，命中真正要做事的路径才调 CLI」，与 `design.md` 的设计一致。

### 6.3 已有 PostToolUse `*` hook 如何判断工具类型、读取输入

共同模式（`skill-tracker.sh`、`test-nudge.sh`、`terminal-activity.sh`）：`INPUT="$(cat)"` → `source hooks/json-input.sh` → `pipeline_json_get_string "$INPUT" tool_name` → `pipeline_json_is_command_tool`（`Bash|command_execution|exec` 通过）→ `pipeline_json_get_command` 取命令（兼容 `command`/`cmd`/`command_line`/`commandLine`/argv 数组）→ `pipeline_json_get_cwd` → `project-root.sh` 的 `pipeline_project_root "$CWD" existing changes` 取项目根 → `active-change.sh` 取当前 change。`test-nudge.sh` 另有「只看 1 MiB 以内的冻结计划，bash 正则扫描」的先例。`json_get` 是纯 bash 字符串提取。

### 6.4 `systemMessage` 先例

仓库（`hooks/`、`adapters/`、`packages/`）内 grep `systemMessage`：**没有任何先例**，没有任何 hook 输出这个字段。现有输出路径：`session-start.sh:90` 用 `hookSpecificOutput.additionalContext`；`test-nudge.sh:122`、`interactive-skill-gate.sh:182` 用顶层 `additionalContext`（见 Q2 附带发现）。因此 step-progress 将是第一个用户可见输出的 hook，终端样式要真机确认。

### 6.5 `statusline.sh` 能否复用

可以复用其读法，不能直接拿来渲染步骤清单。它是纯 bash：`json-input.sh` 取 cwd → `project-root.sh` → `canonical-state.sh`（校验 digest 与 twin 后取 `hookState`，legacy YAML 仅兜底）→ 输出 `<change> · <phase> [· 等:<门>…]`。它只拿到当前 `phase`，没有步骤列表。步骤列表在冻结计划 `<change>/.pipeline-workflow-plan.json`（本变更这个文件 38 KB）里；`test-nudge.sh` 已有用 bash 正则扫它的先例，但取 `projection.steps` 的 `id`/`label` 序列需要新写扫描。

### 6.6 步骤完成状态的数据源

我对本变更实际运行了两条命令：

- `tenon workflow plan setup-host-agents-step-progress --json`：顶层 `{change, source: "frozen-snapshot", current_step: "explore", plan}`；`plan.projection` 为 `{steps: [{id:"open",label:"立项"},{id:"explore",label:"调研"},{id:"spec",label:"规格"},{id:"build",label:"实现"},{id:"verify",label:"验证"},{id:"ship",label:"交付"},{id:"archive",label:"完结"}], stepLabelSource: "localized-builtin"}`。**每步只有 `id` 与 `label`，没有完成状态。**
- `tenon status <change> --json`：键为 `active_changes` 和 `step`；`step` 含 `id`、`label`、`gate`、`archived`、`next` 等，描述的是当前步，不含各步完成度。

所以「已过 ✓ / 当前 ● / 未到 ○」要自己推：按 `projection.steps` 顺序，当前步之前的算已过，当前步算当前，之后的算未到，当前步取 `current_step`（或 `status` 的 `step.id`）。局限（我没有验证，需在设计里明确）：(1) 在 verify 失败退回 build 时，verify 之前被「已过」标记的步骤其实被重新打开，按顺序推会把 verify 显示成未到，这是合理的；但 build 之后再回退后，`ship` 之前的状态仍按顺序推即可；(2) 非线性 workflow（自定义工作流 `workflow-defined` 标签来源）的 `projection.steps` 是否保序且代表主线，我只验证了 default 工作流；(3) 轨道（track）可能跳过某些步骤，`projection` 是否按轨道裁剪，我没有核实（本变更 track 是 `backend`，其投影仍是完整 7 步）；(4) 归档后 `archived` 为真，全部应算已过。

## 开放问题（需要主线或用户裁决）

1. **同一回合内如何判定「文件已在模型清单里」**：磁盘上文件存在不等于可派发（见 Q1.1 观测 B）。`tenon agent prompt` 要如实返回通用子代理，需要知道文件是否在本回合开始前就存在。候选：`UserPromptSubmit` hook 记录回合开始时间并与文件 mtime 比较（未验证）；或保守地规定「由安装命令写、`tenon init`/`prompt` 绝不写」，则凡是回合开始前已存在的文件才可能被清单收录，但安装命令若也在会话里执行，同样要等下一回合。是否需要这层判定，由主线裁决。
2. **用户级还是项目级写入**，取舍要点：
   - 用户级（`~/.claude/agents/`，由 `setup`/`update` 写）：优点是写入发生在终端执行的命令里（下一回合即可用，见 Q1.1）、无需项目级本机排除与归档回收、跨项目只写一次。缺点是 (a) 项目层 `.tenon/agents` 的 agent 无法覆盖，且同名不同定义的跨项目冲突（一份文件只能有一个版本）；(b) 本仓没有用户级文件所有权清单与卸载路径，要新建；(c) Tenon 目前没有写 `~/.claude/agents/` 的先例，是新的全局副作用；(d) `update` 的约定是「不改任何项目工作区」，用户级是否也适用该约定要确认；(e) 任务冻结旧版本定义时，已装文件只对应库当前版本，需要退回通用子代理。(f) 项目级旧文件优先级更高会遮住新的用户级文件。
   - 项目级（`tenon sync` 或新子命令，在终端执行）：优点是天然按项目的 agent 库三层解析、沿用现有的 `.pipeline-owned.json` 与 uninstall、可 `git` 忽略。缺点是仍要保留本机排除与指纹排除，要用户在每个项目都执行一次，且 `sync --migrate` 的 prune 要避开这些清单条目（见 Q5b 新发现）。
   - 折中：官方 + 用户自定义的 agent 写用户级，项目层的 agent 仍写项目级。这会引入两处写入与两份所有权记录，复杂度最高。
