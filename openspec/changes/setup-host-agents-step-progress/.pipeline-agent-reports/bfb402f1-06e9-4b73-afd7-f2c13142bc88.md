## setup-host-agents-step-progress 安全评审报告（验证最后一轮，8 项逐项覆盖）

### 新增入口与出口

**入口**
- 环境变量 `CLAUDE_CONFIG_DIR` / `CODEX_HOME`。
- 用户可写的 `<configRoot>/agents/host-owned.json`。
- git common dir 输出。
- hook 的 stdin（工具命令文本和 cwd）。
- 仓库里提交的测试目录 `setup`。
- 本机信任封存。

**出口**
- 用户级 agent 文件的写入和删除。
- 旧项目级 agent 文件的删除。
- `git worktree add`。
- `spawn(shell:true)` 执行 `setup`。
- hook 调用 `tenon workflow progress "$NAME"`。

### 逐项结论

1. **用户级子代理安装/卸载：无问题。**
   - 配置目录只采用绝对路径的环境变量值（`host-agent-install.ts:55-63`）。
   - 清单键不被信任。回收时只认 `parseHostAgentPath` 能反解的条目，路径由当前 `agentsDir` 加名字重新拼出（同文件:189-192），所以清单里的 `../`、绝对路径或其它目录分组都不会被删。
   - 安装前先校验名字能被原样反解（同文件:152），拼路径用 `posix.basename`（同文件:67）。
   - 目标是符号链接时拒绝写入或删除。`inspectFile` 用 `lstat`，不跟随链接（`host-agent-fs.ts:31-41`）。
   - 原子写用 `wx` 创建唯一临时文件，再 `rename`（`host-agent-fs.ts:18-28`）。
   - 清单解析用 `Object.fromEntries`，没有原型污染（`host-agent-install.ts:79-95`）。
   - 清单损坏时已有文件一律不删。
   - 清单在 `withLock` 里读改写。
   - 残余：`lstat` 到 `unlink` 之间有 TOCTOU 窗口，攻击者要有同一配置目录的写权限，这时已经不需要它了。

2. **旧项目级文件清理：无可利用问题，有一条 low。**
   - `legacyRootOf` 只在 `.git` 是文件（linked worktree）时才调用 `mainCheckoutOf`（`host-agent-files.ts:57-61`）。
   - `mainCheckoutOf` 读了：用 `execFile` 数组参数，没有 shell；cwd 为 `projectRoot`；超时 1.5 秒；`maxBuffer` 4KB；common dir 的 basename 必须是 `.git`，并且 realpath 与项目根不同才返回（`main-checkout.ts:16-27`）。
   - 删除前逐项检查：`hasLinkedParent` 发现任一级父目录是符号链接就保留（`host-agent-files.ts:88-98,153`）；目标本身是链接也保留（同文件:162）；只有哈希与清单记录一致、没被改过的文件才删（同文件:166 之后）。
   - 候选范围限定为 `parseHostAgentPath` 能反解的 `tenon-*` 文件。
   - low：恶意仓库可以让 worktree 的 `.git` 文件指向攻击者构造的 gitdir，使 `mainCheckoutOf` 返回别的目录。但删除仍受三道限制：必须是 `tenon-*` 文件名、必须落在该目录的 agents 目录下、哈希必须和该目录自己的清单一致。影响仅限删除受控目录里的 Tenon 自有文件，所以只记 low。

3. **hook `step-progress.sh`：无问题。**
   - 任务名只取正则捕获组 `[a-z0-9][a-z0-9-]*`（`step-progress.sh:32-34`）。它不会以 `-` 开头，不能被当成选项注入；后面接空白、分隔符或结尾，所以 `$(…)` 之类不会被截断后执行。
   - 调用方式是加引号的 `tenon workflow progress "$NAME"`，不经 `eval`（:43）。命令文本只作匹配，不执行（:3-7 注释，:43）。
   - 输出经 `pipeline_json_escape` 转义（:48）。
   - 输入读取有 65536 字节上限（:25）。`CWD` 来自宿主的 hook 输入，且要求是目录（:41）。
   - 失败路径全部 `exit 0`。

4. **`tenon init` 建 worktree 与 `setup`：无问题。**
   - 任务名先过 `CHANGE_NAME` 白名单（`task-worktree.ts:60`），路径是 `join(repoRoot, WORKTREES_DIR, change)`，不会穿越。分支名是 `tenon/<change>`。
   - git 调用全是数组参数，没有 shell。
   - 执行 `setup` 前要通过 `isTrusted(seal, catalogExecDigest(catalog))`（`init-setup.ts:111-118`）。`catalogExecDigest` 已把 `setup` 纳入摘要（`catalog.ts:137-138`）。所以仓库里提交的 `setup` 在用户本机首次信任前不会执行，改一个字符就需要重新信任。
   - `inheritTrust` 只复制 `trusted`，不复制 `approvals`、`writes`、`heads`（`init-setup.ts:28-42`）。摘要不一致就不执行，并提示用户自己运行 `tenon test trust`，agent 不能代为确认。
   - 失败不抛错，输出转 stderr，不污染 `--json` 的 stdout。
   - 残余：被信任过的摘要会随信任继承。这是设计内行为，前提是用户已在主检出信任过同样的命令。

5. **`start_sha` 伴随文件与三个字段不可改写：无问题。**
   - CLI 的 `set` 路径拒绝 `start_sha`、`base_branch`、`created_at`，提示由 `tenon init` 管理（`fields.ts:78-81`；`field-values.ts:25-31`）。
   - 伴随文件要求键集合精确、`sha` 必须是 40 或 64 位十六进制提交 id、`revisionId` 过 `^[A-Za-z0-9_-]+$`、`stateDigest` 为 64 位十六进制（`start-sha-store.ts:12,56-70`）。
   - 它还必须与 revision 的编号、id、摘要三者一致（:84-90），读取时拒绝符号链接或非普通文件（:131-136），发布走原子 link（:117-124）。伴随文件被篡改会抛 `RunStateCorruptError`，而不是被静默采用。

6. **工作区指纹跳过未跟踪的 `.claude/worktrees/`：无问题（有说明）。**
   - 跳过条件是「路径在 `.claude/worktrees` 之下，且没有被 git 跟踪，也不是含已跟踪文件的目录」，大小写折叠与普通指纹一致（`host-local.ts:225-244`，约 237 行）。
   - 被跟踪的 `.claude/worktrees/x.js` 仍计入指纹，有夹具覆盖（`verify-ci-fixture.ts:226`）。
   - 理论上，攻击者往该目录放未跟踪文件不会改变指纹，但这是按设计跳过宿主本地内容。该目录本来就是不属于任务产物的宿主 worktree，攻击者要有本地写权限，不构成越权。

7. **测试专用夹具是否进入发布产物：无问题（有说明）。**
   - `packages/cli/tsconfig.json` 的 exclude 已列出 `test-support.ts`、`runtime/test-support.ts`、`integration-harness*.ts`、`commands/init-worktree-test-support.ts`、`verify-ci-fixture.ts`、`schema-validation-fixture.ts`。
   - 发布的 `packages/cli/dist/tenon.mjs` 里 grep `harnessArtifactSubmission|verify-ci-fixture|schemaValidationFixture` 命中 0 次。
   - 说明：`integration-phase-skill-test-support.ts` 和 `integration-submission-test-support.ts` 不在 exclude 里，本地 `dist/` 下有对应 `.js`。但这两个文件和 `dist/*`（除入库的 `tenon.mjs`）都被 `.gitignore:13` 忽略，除测试 harness 外没有非测试代码引用它们，也不是本任务新增的。建议顺手加进 exclude，作纵深防御，见下方 low。

8. **`tools/check-repository-hygiene.mjs` 的窄豁免：无法被利用。**
   - 放行条件是三者同时满足：身份属于 `FORBIDDEN_REFERENCE_IDENTITIES.slice(0,1)`（只有第一个）；路径匹配 `SETUP_HOST_AGENTS_CHANGE_PATH`；捕获组 `(.+)` 的值在只含一个固定报告文件名的 `Set` 里（:82-90,:234-241）。
   - 路径正则两端锚定（`^…$`），目录部分只允许固定任务名，或 `archive/YYYY-MM-DD-` 加这个任务名。
   - 文件名是 `Set` 精确匹配，不是模式匹配，因此改后缀、加子目录或同目录其它报告都不会放行。
   - 路径来自 `git ls-files`，并在比较前统一成 POSIX 分隔符，没有 `..` 绕过空间。
   - 另外两个身份在这条豁免里不放行。
   - 残余：这个文件内的内容整份不再检查第一个身份，范围仅此一份报告。

### 残余风险
- `integration-phase-skill-test-support.ts` 和 `integration-submission-test-support.ts` 未列入 CLI tsconfig exclude。它们只存在于被忽略的本地 `dist/`，不进入入库的 `tenon.mjs` 和发布产物，所以是 low。
- 恶意仓库借 `.git` 文件重定向来影响 `mainCheckoutOf`，最多删除受控目录里清单一致的 `tenon-*` 文件，是 low。
- 用户级清单和 `lstat`/`unlink` 之间有 TOCTOU 窗口，需要攻击者已有配置目录写权限。
- 本轮没有跑测试，也没有动任何文件或 Tenon 状态。
