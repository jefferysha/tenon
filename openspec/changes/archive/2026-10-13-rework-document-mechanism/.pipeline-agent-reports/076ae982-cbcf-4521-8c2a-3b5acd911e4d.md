## 覆盖摘要

读了 `documents/step-outputs.ts`（341 行）和 `workflow/transition-step-outputs.ts`，核对了 `step-checkpoint.ts`、`step-output-ledger.ts`、`step-outputs-model.ts` 的 import 边，并 grep 了 `documents.mode` 的分流点。没有重读其它四份评审报告，下面不重复它们的内容。

整体结构符合设计：

- 依赖方向：`workflow/transition-step-outputs` → `documents/step-outputs` → `{state/ledger, workspace/checkpoint, documents/model}`。
- 没有发现环。
- `step-outputs-model.ts` 只做 `import type`，是纯规则，可以单独测。
- git 子进程只在 `workspace/step-checkpoint.ts` 里。
- 观察问题降级为 `unavailable` 或 `truncated`，Tenon 自己的账本损坏则照实抛出，两类错误的归属清楚。

## 发现

1. **medium**，`packages/kernel/src/state/step-output-ledger.ts:9`：`state` 层反向依赖 `workspace` 层——账本从 `workspace/step-checkpoint.ts` 引入 `CHECKPOINT_PATH_LIMIT`、`isCommitId`、`OBSERVED_PATH_MAX_LENGTH` 和 `StepCheckpoint`。账本是持久化格式的校验方，却要依赖 git 基础设施模块。修法：把 `StepCheckpoint` 类型、路径上限常量和 `isCommitId` 挪到没有 I/O 的小模块（如 `step-checkpoint-model.ts`），`workspace` 和 `state` 都从那里引用。
2. **medium**，`packages/kernel/src/documents/step-outputs.ts:296-330`：`matchingFileExists` 是手写的有界目录遍历（计数上限、深度、跳过隐藏目录和 `node_modules`），属于文件系统扫描而非应用层逻辑，和 `workspace` 层的检查点各自带了一套「哪些路径被观察」的规则。没有做重复实现的搜索，无法确认仓库里是否已有等价的遍历工具。修法：先搜可复用的遍历；没有就移到 `workspace/`，让 `step-outputs.ts` 只留编排。
3. **low**，`packages/kernel/src/documents/step-outputs.ts:215-253`：`readStepOutputs` 的 40 行混了账本读取、实时比较、按步骤聚合和文件存在性检查；聚合部分（`latest` 与 `produced`）没有 I/O，可以抽到 model 里做纯函数。
4. **low**，`packages/kernel/src/workflow/transition-step-outputs.ts:8-9`：转换层直接依赖 `documents/step-input-gate` 与 `documents/step-outputs`，符合设计「直接调用、不加注入点」的决定，不算问题；只提醒 `stepOutputsContextFor` 靠「往上三级目录」推出项目根，这个布局假设只在这一处，别处需要时应共用。
5. **low**，`documents.mode` 分流点：数据来源唯一（`plan.capabilities.documents.mode`），但判断散在约 15 处（CLI 的 status、handoff、artifact、review、check、document，kernel 的 `transition-application`、`step-exit-report`，server 的 `stepIo` 与 automation），且 `workflow-run-repository.ts:133` 用 `!== 'contract'`、其它处用 `=== 'observed'`，将来出现第三种模式时会不一致。修法：统一用一个谓词（如 `isObservedDocuments(plan)`）。

## 残余风险

- 没有跑测试，也没有逐行核对 `step-checkpoint.ts` 的 git 调用安全（见 security 报告）。
- 没有确认 `recordStepExit` 的「提交失败后重试」幂等性在账本并发写情形下的表现；它依赖调用方持有任务锁，这点只写在注释里，没有类型层面的强制。
