## 3. Claude Code / Codex hook 时机

### 3.1 Claude Code
- 事件表（https://code.claude.com/docs/en/hooks）：`PreToolUse`「Before a tool call executes. Can block it」；`PostToolUse`「After a tool call succeeds」；`PostToolBatch`「After a full batch of parallel tool calls resolves, before the next model call」；`Stop`「When Claude finishes responding」；`SubagentStop`「When a subagent finishes」。
- `Skill` 是工具、可被 matcher 匹配：同一页 UserPromptExpansion 一节「This event covers the path `PreToolUse` doesn't: a `PreToolUse` hook matching the `Skill` tool fires only when Claude calls the tool, but typing `/skillname` directly bypasses `PreToolUse`. `UserPromptExpansion` fires on that direct path.」该页的 `tool_input` 子节列表没有 Skill（未找到 Skill 的 `tool_input` 模式文档）。本仓库 `hooks/hooks.json:31-34` 已用 `"matcher": "Skill"` 的 PreToolUse 调 `skill-start`，`hooks/skill-start.sh:32-34` 从输入取 `tool_name`=Skill 与 `skill` 字段。
- PostToolUse 输入：「`PostToolUse` hooks fire after a tool has already executed successfully. The input includes both `tool_input`, the arguments sent to the tool, and `tool_response`, the result it returned.」另有 `duration_ms`。
- **技能内容在调用时一次性载入**，此后不再有「技能进行中/结束」状态：https://code.claude.com/docs/en/skills「When you or Claude invoke a skill, the rendered `SKILL.md` content enters the conversation as a single message and stays there across later turns.」所以 Skill 工具的 Pre/PostToolUse 都只对应「加载」，不对应技能要求的工作做完；PostToolUse（Skill）在工具返回（内容已载入）时触发，此时技能的实际工作尚未开始。该推论是据上面两条文档推出，官方页没有直接写「PostToolUse for Skill fires when load completes」这句话——**直接证据：未找到**。
- **没有任何 hook 事件表示「一个技能的工作结束」**：hooks 页与 skills 页均未找到；skills 页明说无单一结束点（「The page gives no single end condition」是抓取摘要的结论，原文只有 per-turn 清理规则，如「`allowed-tools` grant clears when you send your next message」）。最接近的是 `Stop`（整轮结束）、`SubagentStop`（`context: fork` 的技能在子代理里跑时，子代理结束；skills 页：「The subagent summarizes its results and returns them to your main conversation when it finishes.」）。
- 技能自带 hooks：frontmatter `hooks`「Hooks that Claude Code registers when the skill is invoked and keeps running for the rest of the session」，同样没有「技能结束」生命周期。

## 4. 基于 git 的检查点先例与原语

### 4.1 其他工具

**Claude Code checkpointing**（https://code.claude.com/docs/en/checkpointing）
- 机制：「checkpointing automatically captures the state of your code before each prompt you send that starts a turn」；只跟踪文件编辑工具：「Claude Code tracks all changes made by its file editing tools」。保留最近 100 个检查点。
- 局限：「Checkpointing does not track files modified by Bash commands.」；子代理编辑通常不被捕获（「Any other subagent: rewinding doesn't restore the edits. Use git to revert them.」）；「Manual changes you make to files outside of Claude Code and edits from other concurrent sessions are normally not captured」；符号链接/硬链接不恢复；「Checkpoints are designed for quick, session-level recovery.」「Not a replacement for version control」。
- 要点：它不是 git 机制，对 Bash 引起的文件变化不可见，所以不适合当「本步产出」的来源。

**Cline shadow git**（https://docs.cline.bot/features/checkpoints）
- 「Cline maintains a shadow Git repository separate from your project's actual Git history.」「After each tool use (file edits, commands, etc.), Cline commits the current state of your files to this shadow repo.」「Checkpoints capture everything, including files not tracked by Git.」「Your main Git repository stays untouched.」「For very large repositories, checkpoints may use significant storage and slow down Cline.」页面未说影子仓库位置、未列排除规则。
- 源码层面（cline/cline `main`，提交 `8eba11b2703f5b12d3f415544be37ffc0ca03be1`）：旧的 `src/integrations/checkpoints` 代码已不在树里（仓库已重构为 `apps/ sdk/`），无法引用实现。可引用的是 `CHANGELOG.md` 的已知问题记录（逐字）：
  - `CHANGELOG.md:97`「Checkpoints no longer re-hash every untracked file on each message. In workspaces holding large untracked directories this delayed every message by seconds to minutes; a persistent per-task index now lets git skip files it has already seen.」
  - `CHANGELOG.md:140`「Restoring a checkpoint now refuses to run when commits were made after it, instead of silently knocking them off the branch where only the reflog could recover them.」
  - `CHANGELOG.md:928`「Retry nested git restore and prevent silent `.git_disabled` leftovers in checkpoints」（嵌套 git 仓库的处理：重命名 `.git` 会留下残留）
  - `CHANGELOG.md:1380`「Initial checkpoint commit now non-blocking for improved responsiveness in large repositories」
  - `CHANGELOG.md:1891`「Add robust checkpoint timeout handling with early warning at 7 seconds and timeout at 15 seconds to prevent hanging on large repositories」
  - `CHANGELOG.md:332`「Include files that were untracked when a snapshot was taken in checkpoint diffs, and pick up checkpoints when git is initialized part-way through a session.」

**Aider**（https://aider.chat/docs/git.html）
- 「Whenever aider edits a file, it commits those changes with a descriptive commit message.」可用 `--no-auto-commits` 关闭；对已有未提交改动的脏文件：先把用户改动单独提交一次再改（「It first saves your existing changes in their own commit」，此为抓取摘要的转述，非逐字）；作者/提交者名追加「(aider)」；`/undo`「will undo and discard the last change」。页面未提 `.gitignore` 交互。
- 要点：Aider 直接写用户的 git 历史（会与用户的 git 状态交织），与「影子」方案相反。

### 4.2 原语（官方文档 + 本机 scratch 实测）

实测环境：macOS，`git version 2.39.5 (Apple Git-154)`，scratch 仓库（非 linked worktree）`.../scratchpad/exp/main`，内含已跟踪 `a.txt`、`.gitignore`（忽略 `ign`）、被忽略文件 `ign`、未跟踪 `n.txt`。初始对象文件数 4。

| 原语 | 写对象库？ | 尊重 .gitignore？ | linked worktree | 备注与依据 |
|---|---|---|---|---|
| `git status --porcelain=v2 -z --untracked-files=all` | 实测不新增对象（4→4）。但会刷新并**写回索引**：文档「By default, `git` `status` will automatically refresh the index, updating the cached stat information from the working tree and writing out the result.」建议后台脚本用「`git` `--no-optional-locks` `status`」。 | 是：默认不列忽略文件，`--ignored` 才列（porcelain v2 为 `! <path>`）。实测 `ign` 不在输出里，`n.txt` 显示为 `? n.txt`，`a.txt` 为 `1 .M N... ...`。 | 文档：HEAD、index 为每个 worktree 私有（见下），所以状态按各自工作树计算，只读语义应安全；**未实测**。 | 格式引用：「Untracked items have the following format: `? <path>`」；「`-z` Terminate entries with NUL」。`--no-optional-locks` 文档：「Do not perform optional operations that require locks. ## 5. mtime 作为来源标注依据的可靠性

- **APFS**：Apple 文档「Volume Format Comparison」表（https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/VolumeFormatComparison/VolumeFormatComparison.html）逐字「Time stamp granularity | 1 second | 1 nanosecond」，列序 HFS+ 在前、APFS 在后。该页已标注为存档文档。Apple File System Reference PDF 本身我没能解析（二进制 PDF，pdftotext 不在本机，自写提取失败），所以 `mod_time` 字段定义无官方逐字引用；libfsapfs 社区文档称为纳秒（二手源，仅作线索）。
- **ext4**：https://docs.kernel.org/filesystems/ext4/inodes.html「`i_mtime` … Last data modification time, in seconds since the epoch.」「`i_mtime_extra` … Extra modification time bits. This provides sub-second precision.」「the upper 30 bits are used to provide nanosecond timestamp accuracy」（128 字节旧 inode 没有 extra 字段，因此只有秒精度；ext4 默认 256 字节 inode）。
- **但 Linux 内核实际写入的时间戳是粗粒度的**：https://docs.kernel.org/filesystems/multigrain-ts.html「Historically, the kernel has always used coarse time values to stamp inodes.」「This value is updated every jiffy, so any change that happens within that jiffy will end up with the same timestamp.」多粒度时间戳（Phoronix 报道合入 Linux 6.6，ext4/XFS/btrfs/tmpfs 已转换）只在「when a file has had its timestamps queried recently」才用细粒度。结论：Linux 上 mtime 的有效分辨率受 jiffy（典型几毫秒到 10ms 量级，取决于 CONFIG_HZ，**具体值未找到一手来源**）限制，同一 jiffy 内的两次写入时间戳相同。
- **git 对 mtime 的行为**：https://public-inbox.org/git/51DB8966.2060308@lsrfire.ath.cx/ 抓取失败（HTTP 502）。搜索结果的转述（二手，仅线索）：checkout 写出的新文件 mtime 为 checkout 时间而不是提交时间；git 开发者认为 mtime 对版本存储不重要；强制恢复 mtime 的补丁被 Junio Hamano 拒绝；`git-restore-mtime` 等第三方工具靠 post-checkout hook 补。**官方文档里关于「checkout/rebase 会改 mtime」的逐字一手引用：未找到**。从机制上，`git checkout`/`rebase`/`stash pop` 凡重写文件内容就会产生新的 mtime（常识推断，未实测），因此在转换时刻前后若用户或 agent 切分支，mtime 与「某技能写了它」的因果会被破坏。
- **编辑器**：未查。常见编辑器保存/原子替换（写临时文件再 rename）会产生新 inode 与新 mtime，部分工具还会 touch；**未找到一手来源**。
- **Claude Code 的 mtime 外部影响**：checkpointing 页指出 Bash 对文件的修改不被跟踪、子代理改动通常不在检查点内，同样意味着 mtime 是唯一来源线索时，需要区分技能加载时间窗内的写入者（主线程 vs 子代理 vs Bash），hook 数据本身是否带这些信息：未核查。
