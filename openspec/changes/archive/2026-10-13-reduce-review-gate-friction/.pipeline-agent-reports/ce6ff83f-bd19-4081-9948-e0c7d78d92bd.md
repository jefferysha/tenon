## 先说三个会改变设计前提的发现

1. **没有任何代码在转换时检查「验证报告已写出」。** design.md 写「回退边原有的就绪要求（如 `verify-fail` 需要已写出的验证报告）保留，并在转换时强制」，但现状这条检查只存在于 `review request` 一侧，而且只对旧执行模型（phase-manifest）的在途任务生效（见 Q3-b）。免回执后要么新增转换侧检查，要么接受「新任务的 verify-fail 本来就没有报告检查」。
2. **`tenon transition` 不清理 `.pipeline-pending-review` marker。** 转换只清 canonical 回执字段；marker 只在 acknowledge / Dashboard 决策 / 删任务时删除。design.md 写「pending 的回退边请求……转换时清掉 marker」，这需要新增代码（见 Q4）。不加的话，升级前已 request 的任务转换后 marker 仍拦写最多 30 分钟，且用户回「确认继续」也解不开。
3. **design-system 工作流的 `review` 步被新规则覆盖。** `review-changes → generate` 是回退边，该步 `gate: review`，没写 `max_rounds`，按内置默认 2 受约束（见 Q3-a）。免回执意味着 agent 可以不经用户直接把预览打回生成。这与「轮次内回退几乎是唯一合理走法」的前提不一定一致（用户看预览才是这一步的意义）。
