## 一、上一轮 3 条 low 的修复核对

### F1'（状态目录规则的脚本与内联盲区）：已修复，剩余盲区已如实写进头部注释
- **内联代码**：`pipeline_command_inline_takes_trust` 对整条命令判定，条件是"解释器 + 内联开关 + 状态目录字样"。
  - 判定在 `pipeline_shell_writes_record` 里，位于 shell 包装展开之后、按段扫描之前，因此内联代码里的 `;` 不会把代码切散而躲过去。
  - 字样为 TEST_TRUST、RUNTIME_HOME、RUNTIME_ROOTS、XDG_STATE_HOME，或"独立词 tenon + trust/HOME"。
  - `tenon-local`、`.tenon` 这类更长的名字不算独立词。
  - 我对照 `pipeline_names_tenon_word` 的四条模式逐一检查了边界，包括 `tenon` 在开头或结尾、紧跟 `.mjs`、前面是 `/`。结论正确，`tenon.mjs` 和 `/x/tenon` 会命中，`mytenon` 不命中。
- **脚本文件**：形态 8 新增了 TEST_TRUST 和 `test trust` 扫描，原因为 trust。这与"脚本文件已被 git 跟踪且未改动则放行"的既有判断一致。
- **粗筛与判定的字样表**：粗筛（`pipeline_command_may_inline_trust`）比判定宽，没有出现粗筛漏过而判定本应命中的情况。粗筛按子串认 tenon，判定按独立词认，这是安全方向。
- **PIPELINE_PY**：它在 `protected-writes.sh:84` 和 `gate.sh:85` 都有定义，非空。`"$PIPELINE_PY"[0-9]*` 不会把所有数字开头的记号当成解释器。
- **bash 3.2**：
  - `read -r -d '' -a toks <<< ...` 和 `case` 里的通配都是 3.2 支持的写法。
  - 空字段用 `[ -n "$token" ] || continue` 跳过。
  - `-[a-zA-Z]*[ce]` 不会误匹配 `--require` 这类双横线开关。
  - 它会匹配 `-exec`、`-inspect-c` 这类以 c 或 e 结尾的单横线开关，属于宁多拒，且只在解释器之后、第一个非开关记号之前生效。
- **性能**：整条命令一次 `read` 切分，再对记号线性遍历，没有逐字符替换。入口先用 case 子串筛掉绝大多数命令，因此是线性的。

### F2（`protected-writes.sh` 缺失时 gate 放行）：已修复，缺库路径确实失败关闭
- `gate.sh` 在库缺失时，只要输入含 trust、TRUST、RUNTIME_HOME、RUNTIME_ROOTS、`HOME=`、XDG_STATE_HOME 就 `exit 2`，其余放行。
- 外层 case 入口新增了 `*test-trust*`、`*RUNTIME_HOME*`、`*RUNTIME_ROOTS*`、`*HOME=*`、`*XDG_STATE_HOME*`，所以这些字样一定进入该分支。

- L445 在每个命令段开头把 `PIPELINE_REFUSE_KIND` 重置为 record。L448 对 state 做了保留，不会被改写成 trust。
- 内联路径先设置 state 再返回 0，之后没有代码把它覆盖，所以 `PIPELINE_REFUSE_KIND` 在新路径上不会被覆盖成错误文案。

## 二、本轮新增改动的新发现

### N1（low）：内联解释器名单是固定列表，未覆盖的解释器可绕过
- **位置**：`hooks/lib/trust-command.sh:182`。
- **前置条件**：agent 能在 shell 里调用名单外的、支持内联代码的运行时。
- **步骤**：`tsx -e` 或 `npx tsx -e`、`ts-node -e`、`tclsh`、`pwsh -c`、`julia -e`、`groovy -e`、`awk` 的 system()，在内联代码里设置 `process.env.TENON_RUNTIME_HOME` 并 spawn tenon。
- **后果**：绕过"agent 不改写状态目录"这条纵深防御。
- **性质**：头部注释已声明"尽力而为"。信任记录仍有 HMAC 封印，且转换时检出链头不符，所以影响面有限。
- **修法**：把名单扩成 tsx / ts-node / pwsh / julia / groovy / tclsh。
- **是否可利用**：不确定，取决于运行环境里装了哪些运行时。

### N2（low）：摘要里的 `entry.kind`、数值和类名依赖目录解析的校验
- **位置**：`packages/kernel/src/test-system/protected-summary.ts` 的 `describeNotApplicable`，以及 `levels-diff.ts` 的行拼接。
- **核对结论**：不可信文本不会进入用户确认屏。
  - 文案里只有枚举类型（`TestKind`、`LevelName`、`TestClass`、`COVERAGE_METRICS`）和数值，理由原文刻意不进摘要。
  - `review-waivers.ts:161` 对每一行再过一遍 `foldDisplayText`，折行并去掉控制字符。
- **残余风险**：它依赖 `parseTestCatalog` 严格校验 kind 和类名为枚举，我没有逐行核对 decode 层。建议在 `describeLevelChanges` 里对插值也用 `displaySafeText`，作为纵深防御。
- **性质**：加固建议，不是已确认的缺陷。

### N3（low，沿用上一轮思路的补充）：内联开关之前带"开关 + 单独值"的写法仍躲得过
- **位置**：`trust-command.sh:174-180`。
- **示例**：`node --require ./x.js -e …`，`./x.js` 被当成第一个非开关记号，之后的 `-e` 不再判定。
- **性质**：头部注释已声明是已知盲区，这里作为残余风险登记。
- **修法**：对已知带值的开关（`--require`、`-r`、`-W`、`-I`）跳过其值记号，或在内联判定里放宽成"该解释器之后任意位置出现内联开关"。后者会在 `node script.js -e` 上误拦，属于取舍。
