## 补读项结论

### 1. `catalog-patch-lines.ts` 与 `catalog-patch.test.ts`
- **CRLF**：`splitSegments` 按行记下各自的行尾。没动的行连同行尾原样保留，新增行沿用文件第一个出现的行尾。混合换行符也各自保留。
- **行尾空格**：没动的行整行原样，不做 trim。
- **无结尾换行**：`applyLineEdits` 的 `unterminated` 分支让最后一行始终不带换行。删掉最后一行时，前一行也不留换行。
- **`---` 开头**：文档起始标记属于没动的行，字节不变。
- **注释**：`lastContentLine` 把节点末尾的空行和整行注释划给下一个节点。删除只带走节点自己的行，节点内部的注释随它所在的键一起改动或删除。
- **其余字节不变的最终保证**：区间重叠时 `applyLineEdits` 直接抛错。`patchCatalogText` 在改动前校验原文与 `before` 一致，改动后整份重解析并与 `after` 做 canonical 对比，不一致就抛错。所以任何边角情形要么字节不变，要么抛错，不会静默写错。
- **测试覆盖**：`catalog-patch.test.ts` 逐项覆盖了 CRLF、行尾空格、无结尾换行（含最后一行被改）、`---` 开头、混合换行符、条目内部注释、分节注释、flow 写法、顺序变化回退、同列缩进、第一个键被删。另有 3 个抛错用例：改出不合法的目录、before 与原文对不上、原文本身不合法。覆盖充分。
- **没发现测试覆盖的边角**（见下面的 low 发现 8）：块标量末尾以 `#` 开头的行，以及 YAML `...` 文档结束标记。

### 2. `catalog-file.ts` 的 `updateCatalog` 路径
- 持锁，锁内顺序是 `observe`、读文件、`mutate`（同步）、patch、原子替换。
- 原文存在时走 `patchCatalogText`，原文不存在才整份 `serializeTestCatalog` 并回读校验。
- patch 抛错时返回 `{ok:false}`，不写盘。`result.catalog === base` 或 `text === original` 时不重写。
- 目录 `invalid` 时拒绝，不覆盖人写坏的文件。除 ENOENT 外的读错误原样抛出，没有吞掉。没发现问题。

### 3. server 端
- **DTO 向后兼容**：`PolicyDto.level` 是可选字段，只有档位派生的策略才有。旧 `test_policy` 仍走原有字段，`policyDto` 的旧字段形状不变。`files.unregistered` 在 kernel 报告里恒空，但 DTO 把字段换成了 `claimed`。这是一次 DTO 字段改名：旧 Dashboard 读 `unregistered` 会得到 `undefined`，需要确认 Dashboard 已同步，dist 是同一次生成。
- **旧策略仍可显示**：`projectTestEvidence` 里 `resolveStepTestPolicy` 对旧策略原样返回，`stepHasTestPolicy` 覆盖两种声明。
- **工作流写接口拒绝 `test` 与 `test_policy` 并存**：`serverPostGovernanceRoutes.ts` 里 `decodeWorkflowDef` 走 `compileStepTestLevel`，两者并存时报"test 与 test_policy 只能写一个"，被 try/catch 接成 400，响应体是 `{ok:false, errors:[...]}`。`server.test.ts:3535` 有对应用例，断言点名了该步且不覆盖已发布的定义。
- **`levels` 只读接口**：`catalogView` 里的 `levels` 是 `LEVEL_NAMES.map(resolveLevel)` 的纯读取，没有写路径。
- **输入收窄**：本次新增和修改的行里，对 `: any`、`as any`、非空断言 `!`、`as unknown as`、`@ts-ignore`、`eslint-disable` 的搜索没有任何命中。

### 4. 抽查项补看结论
- **`evaluate-v2.ts`、`evaluate-files.ts`、`evaluate-kinds.ts`**：运行集与 `tenon test run --stage` 同源（`stageRunSet`）。`changedFilesError` 会变成 `files-diff-unavailable` 阻断，失败关闭。已知的取舍见下面的 low 发现 5。

- **`review-waivers.ts`**：`stepTestMetrics` 每次现读，不进冻结清单。

## 发现清单

### 新发现

**1. medium：`packages/cli/src/commands/test-trust.ts:215-219`（`untrustedEntries`）**
- `trustScope` 在三种情况下返回 `undefined`：不是 git 仓库、`.git` 是伪造指针、`git` 失败（超时 10 秒、所有权不符、临时错误）。
- 代码只在 `scope !== undefined` 时调用 `legacySealIsMachineLocal`。所以 `git` 在真实克隆上超时或失败，会让"被 git 跟踪的旧封存是仓库自带的、不认"这道检查被整个跳过，仓库自带的封存加密钥就能给自己授信。
- 文件头注释说这是"非 git 目录退回旧封存"的规格。但"git 暂时失败"和"确实不是 git 仓库"被混成了一个状态。前者不应放行，后者才是规格允许的。
- 修法：让 `repoTrustIdentity` 或 `trustScope` 区分"确定不是 git 仓库"（ENOENT、`rev-parse` 报 not a repository）和"git 出错"。后者按未信任处理，或至少对旧封存也要求 `legacySealIsMachineLocal` 通过。

### 保留的 3 条 low（上一份报告）

**2. low：`hooks/lib/protected-writes.sh:27`**
- 路径里含 `/test-trust/` 段就按受保护处理，项目里同名普通目录的合法写入会被误拦。
- 修法：收窄到 `<slug>.json` 或 `<slug>.key` 的文件名形状，或在文档里注明保留名。

**3. low：`packages/cli/src/test-system/repo-identity.ts:28`**
- `gitEnvironment()` 在这里和 `legacy-seal-origin.ts`、kernel `workspace/host-local.ts` 各有一份，清理规则以后容易只改一处。
- 修法：抽成共享的 helper。

**4. low：`packages/kernel/src/test-system/trust-store.ts:175`**
- `ensureKey` 用 `wx` 创建密钥文件，到写完内容之间有短暂的空文件窗口，并发读者会读到空并判为不可信。
- 修法：写临时文件再 `rename`，或保持现状（读者按失败关闭处理，影响很小）。

### 新增的 low

**5. low：`packages/kernel/src/test-system/evaluate-files.ts:115-118` 与 `stage-run-set.ts:73-75`**
- `changedFiles === undefined` 且不是 `changedFilesError` 的情形，也就是宿主不提供改动列表的能力，只出一条 `files-unchecked` 提示。
- 此时 `changed` 档的派生运行集为空，只靠"必需类在目录里有套件"来拦。已书面记录的取舍只覆盖了 `--stage` 一侧，没有说明门禁一侧也是这个行为。
- 修法：在文档里写明"宿主无改动列表能力时，`changed` 档在门禁上只检查类是否存在"。

**6. low：`packages/kernel/src/test-system/catalog.ts` 的 `suiteExecEntry`**
- 服务排序的比较器 `canonicalJson(left) < canonicalJson(right) ? -1 : 1` 对相等元素也返回 1，不满足比较器一致性。
- 实际无影响（相等元素内容完全相同，摘要不变）。
- 修法：补一个 `0` 分支。

**7. low：`packages/kernel/src/test-system/evaluate-suite.ts` 的 `NODE_TEST_FILE_HINT`**
- 一行 `export const NODE_TEST_FILE_HINT ='（…` 等号后少一个空格，属风格问题。

**8. low：`packages/kernel/src/test-system/catalog-patch-lines.ts:85-90`（`lastContentLine`）**
- 它把节点末尾以 `#` 开头的行当作"下一个节点的注释"。块标量（`|`）命令末尾恰好是 `#` 开头的行时，这些行会留在被替换区间之外。
- 之后重解析与 `after` 对比不一致，会抛错，不会静默写错，所以只会让这种改动失败，不会损坏文件。
- 修法：先不改，在文档中注明，或在遇到块标量时按缩进判断区间。
