## 第 1 轮问题的复核结论

1. **trustScope 混淆两种状态：已修复，完整，没有引入新问题。**
   - `RepoTrustIdentity` 与 `TrustScope` 现在都是三态。
   - `repoTrustIdentity` 对应三种结果：
     - `not-repo` 只看文件系统，不调用 git，除 ENOENT 外的任何失败都按「有 `.git`」处理。
     - `repo` 表示读出了仓库身份。
     - `unresolved` 覆盖 git 出错、超时和伪造指针。
   - 所有消费方分支正确：
     - `untrustedEntries`：`unresolved` 全部未信任，不查存储也不看旧封存。
     - `ensureTrusted`、`cmdTestTrust`：在 `unresolved` 下拒绝写入。
     - `statusStepTrust.pendingTrust`：沿用同一 `trustScope`。
   - 仍保持失败关闭：`user` 作用域下旧封存还要过 `legacySealIsMachineLocal`。
2. **`gitEnvironment` 重复：已修复。** `git-exec.ts` 清除全部 `GIT_*` 变量（大小写不敏感），固定 `LC_ALL=C`，带超时和缓冲上限。`repo-identity` 与 `legacy-seal-origin` 都经它调用。
3. **比较器 0 分支、写封存失败的 try/catch、`local` 被跟踪时拒绝写入：** 均确认已修。`legacySealWouldBeRecognized` 在 lstat 非 ENOENT 时落到 `legacySealIsMachineLocal`，仍然失败关闭。

## 发现清单

全部为 low，没有 medium 及以上。

- **low** `packages/cli/src/test-system/report-md.ts:183-191`
  - 问题：`benchmarkRows` 里的 `metric.unit` 是目录里最长 32 字节的自由文本，直接输出，没走 `escapedInline`。`suite.suite` 和 `metric.name` 有正则约束，没有风险。文件头注释声称所有不可信文本都已转义，与实现不符。
  - 修法：对 `metric.unit` 套 `escapedInline`，或在目录解码处限制 `unit` 的字符集。
- **low** `packages/cli/src/test-system/plan-context.ts:54-59`（`stepPolicyFor`）
  - 问题：`readCatalogFile` 对 ENOENT 之外的读错误会抛出。`test-integrity.ts` 与 `agent.ts` 的 `testSummaryFor` 没有 try/catch，目录不可读时命令会带堆栈崩溃。
  - 修法：`stepPolicyFor` 内捕获异常并按目录缺失处理，或由调用方转成一行 `ERROR`。
- **low** `packages/kernel/src/test-system/trust-store.ts:101-109`（`trustDirIsSafe`）
  - 问题：只检查是否为普通目录以及组和其他用户的写位，没有核对属主是否为当前 uid。此外 HMAC 不绑定 `slug`，同机其他用户若能控制 `stateRoot` 可以搬运存储。威胁面和注释里承认的「同 UID 不防」属于同一类。
  - 修法：加一条 `entry.uid === process.getuid?.()` 的检查，并把 `slug` 并入 `macOf` 的输入。
- **low** `packages/kernel/src/test-system/catalog-patch.ts:25-26`（其余残余风险同类，按设计保留）
  - 问题：按节点写回依赖 `lastContentLine` 与「写回后整份重解析且与 after 深等」两道兜底。兜底失败是抛错、不写盘，所以不会静默写错。
  - 建议：这类失败路径保留对应的回归用例，不必改动。
- **low** `templates/workflows/default.yaml`（产品行为变化）
  - 问题：默认工作流不再有覆盖率 80% 和 `lines_added ≤ 2000` 的硬门槛，spec 步骤的场景映射也不再强制，改由 `test: none|plan|changed|full` 与目录 `levels` 缺省承接，缺省档位不设覆盖率和 flaky 门槛。这与「重构是删功能而非搬功能」的方向一致，但属于门禁强度下降。
  - 修法：在 release-notes 里已写明的前提下无需代码改动。需要项目级门槛的用户通过 `levels.full.coverage` 自行声明。

## 逐项通用维度结论

- **correctness：**
  - 认领（`claim.ts`）经 `changed-files.ts` 的 `--diff-filter=ACMR` 排除已删除文件，不会出现「已删除文件必须执行」。
  - `stageRunSet` 在求值与 `tenon test run --stage` 之间只有一份实现。
  - 读不到改动列表时失败关闭（`files-diff-unavailable`），运行侧给 WARN。
  - `evaluate-v2` 把「认领文件未执行」汇总成对应套件的 `failed`。
- **安全：**
  - 路径穿越：`legacySealIsMachineLocal` 逐级 lstat 防符号链接，`backlinksTo` 只读普通小文件。
  - 命令注入：`runGit` 用 `execFile` 且不经 shell。
  - 密钥与凭据：信任存储与密钥为 0600，目录组写位被拒。
  - 展示注入：`cell()` 对竖线与反斜杠的处理自洽，`visibleLine` 把控制字符和双向字符转成可见转义。
  - 环境变量劫持：`GIT_*` 全部清除。
  - 证据文件豁免：`test-evidence-files.ts` 只放行已知惰性扩展名且未被 git 跟踪的普通文件，git 无法回答时不放行。
- **错误处理：** 信任存储区分「损坏则读空」与「I/O 错误则抛出」，写入前不会因暂时读错覆盖已有信任。`catalog-patch` 的失败只返回消息、不写盘。
- **数据访问：** 没有数据库与迁移。文件写入走锁加原子替换。`run-paths` 的正则只有字符类与定长前瞻，无回溯风险。

## 残余风险

- 信任模型的上限是「同 UID 且能读密钥即可伪造」，已由 hook 拒写 `test-trust` 路径加失败关闭兜底，属于已声明的威胁边界。
- 目录 `levels` 由仓库提供，恶意仓库可以把 `required` 写空来弱化门禁。该文件属于受保护测试配置，变更必须经评审确认，风险被评审门承接，不是实现缺陷。
- macOS 上 `legacy-seal-origin` 的 `:(icase,literal)` 只折叠 ASCII 大小写，不处理 Unicode 归一化差异。涉及的路径段（`.tenon`、`users`、slug、`local`）都是 ASCII，当前无影响。
