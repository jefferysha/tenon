## 10 个信任边界的结论

1. **信任存储 `trust-store.ts`：通过。**
   - 读取永不抛错，读不出一律当空，失败关闭。
   - 目录必须是真实目录，且组和其他用户不能写；密钥必须是 0600 的普通非空小文件。
   - 存储文件限 8MB，必须是普通文件，封印不符则作废。
   - HMAC 比较前先比长度，再用 `timingSafeEqual`。
   - 写入在目录锁内读—改—写，用 `wx` 创建密钥。读存储遇到非 ENOENT 的 I/O 错误会抛出，不会把已有信任整份换掉。
   - 用户 slug 有正则校验，拼不出路径穿越。

## 发现

1. **medium：被检仓库的压缩包自带 `.git` 和封存时，旧封存能被认下。**
   - 位置：`legacy-seal-origin.ts` 与 `test-trust.ts:109`。
   - 路径：攻击者分发一个压缩包，里面有合法的 `.git` 目录，并附带未被索引跟踪的 `.tenon/users/<受害者 slug>/local/test-seal.json` 和 `env.key`，封印由攻击者算好。受害者解压后，`legacySealIsMachineLocal` 因为"未被跟踪"返回 true，`isTrusted` 通过，目录里的命令不经确认就执行。
   - 前提：受害者解压并在其中运行 `tenon test run`，攻击者知道受害者的 slug（由邮箱派生，可猜）。
   - 说明：这是"没有 `.git` 的目录认检出旧封存"这条已知取舍在有 `.git` 时的同类情形，属 spec 允许的兼容策略。
   - 修法：旧封存里加上机器绑定（例如把本机标识并入封印），或者在 git 仓库里完全停止认检出里的旧封存。

2. **medium：评审请求原样打印豁免理由，控制字符能混进去。**
   - 位置：`review-waivers.ts` 的 `reviewItemLines`（约第 135 行：`${waiver.key} — ${waiver.reason}`）。
   - 事实核对：派发说明里写"计划解码时会拒收含控制字符或双向字符的理由"，我没有找到这个行为。
     - `plan.ts:138` 与 `catalog-na.ts:42` 的豁免理由只用 `str()` 校验，它只拒 `\r`、`\n`、`\0`，并限制 1000 字节。
     - `hasUnsafeDisplayChars` 只在 `review-residual.ts` 里用，没有用在计划或目录的理由解码上。
   - 路径：计划里的 `test:` 豁免理由由 agent 写入。目录里 `not_applicable` 的 reason 由仓库提供，所以克隆来的仓库也能提供。理由里可以带 ESC 转义序列或双向覆盖字符，在用户确认豁免的那一屏上改写或隐藏真实内容。
   - 说明：这是基线行为，本次改动只是在它下面加了"最新运行"一行，所以不是新引入。
   - 修法：`reviewItemLines` 打印前先 `foldDisplayText`，不要截短，因为用户要看全文。或者在 `plan.ts` 和 `catalog-na.ts` 的理由解码里加 `hasUnsafeDisplayChars` 拒收。

3. **low：同一路径换仓库继承信任。**
   - 位置：`repo-identity.ts` 与 `trust-store.ts`。
   - 说明：身份是 common dir 的真实路径。这是按设计保留的取舍，我没有新的利用路径。

4. **low：信任存储的防篡改依赖 hook 和文件权限。**
   - 位置：`trust-store.ts` 与 `hooks/lib/protected-writes.sh`。
   - 说明：密钥与存储同目录、同 UID，不是对恶意同用户进程的密码学防御。文件头已写明这一点。

5. **low：报告里的裸网址自动成链接。**
   - 位置：`report-md.ts` 的 `escapedInline`。
   - 说明：不转义 `:` 和 `.`，所以 GFM 会把 `https://…` 和 `www.` 渲染成链接。目标就是可见文字，没有隐藏目的地。
