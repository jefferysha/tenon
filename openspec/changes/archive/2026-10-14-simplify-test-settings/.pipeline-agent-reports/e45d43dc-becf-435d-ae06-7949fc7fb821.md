# architecture 评审报告（验证第 5 轮）

**覆盖说明**

我做了这些检查:
- 运行了 `node tools/check-architecture.mjs`。结果通过:扫描 1578 个生产文件,kernel 运行时 import 图的循环(SCC)为 0,4 个仅体积例外。
- grep 了 kernel 的 `test-system/`、`workflow/test-level.ts` 和 `workspace/test-evidence-files.ts`,查 `process.env` 和指向 cli / server / dashboard 的 import。没有 kernel 反向依赖,也没有 kernel 读环境变量。唯一的 grep 命中是 `trust-store.ts` 和 `machine-profile.ts` 的注释,注释里写的是不读 `process.env`。
- 抽读了 `trust-store.ts` 和 `machine-profile.ts` 的 import 与头部。kernel 依赖 `node:fs/promises`、`node:crypto`、`node:os`、`node:path`,这是 kernel 里已有的 IO 用法。状态根由调用方传入,与 M5 的设计一致。
- 读了其它四份评审报告的摘要,它们都没有 medium 及以上的发现。

我没有读全文的部分:
- CLI `test-system/`(`repo-identity.ts`、`git-exec.ts`、`run-paths.ts`、`claim-orphans.ts`)、`commands/test-trust.ts`、`hooks/lib/trust-command.sh`、server 的 `testPolicyDto.ts` 和 Dashboard 文件,我都没读。它们只由架构检查脚本的依赖图覆盖,我没有逐文件核对。
- 也没有逐个文件检查 M1 到 M7 的接口深度。

**发现**

没有 medium 及以上的结构问题。

**残余风险**
- `type-only SCC=1`:类型层面存在一个循环。它不是运行时循环,门禁也放行了。我没确认这个循环是不是本次引入的。
- M1 到 M7 的深度和接缝只依据设计文档与架构检查,没有逐模块验证。
