## 发现清单

**F1（medium）`packages/kernel/src/test-system/protected-summary.ts:24`**
- 问题：档位定义（`levels`）现在在 agent 可编辑的 `catalog.yaml` 里，但 `describeCatalog` 只比较套件和服务。
- 后果：只改 `levels` 的改动（清空 `required`、去掉覆盖率或不稳定用例门槛）在评审里只显示「套件与服务没有变化（其它字段有改动）」。用户批准受保护配置改动时，看不到门槛被放宽了。
- 对比：旧 `test_policy` 在冻结的工作流里，agent 改不了；`not_applicable` 的放宽有 `approved_by` 单独批准。
- 修法：让 `describeCatalog` 对 `levels` 逐档逐键前后对比，输出放宽或收紧的文案，顺带列出 `not_applicable` 的变化。

**F2（low）`packages/kernel/src/workspace/test-evidence-files.ts:52`**
- 问题：在任意深度名为 `coverage/`、`test-results/`、`playwright-report/` 的目录下，未被 git 跟踪的 `.txt`、`.csv`、`.xml`、`.md` 和图片等文件不进候选指纹。
- 后果：这些文件新增或被改写，已有运行记录不会过期，而测试代码可能读取它们。例如源码树里恰好叫 `coverage/` 的目录下的新夹具。
- 修法：把范围缩到仓库根层，或者只认运行记录里登记过的输出路径。至少在设计文档里写明这条信任边界。

## 残余风险

- hook 识别是尽力而为，已记录的几类不再重复。另一类：`HOME=/tmp/x npm run <script>` 会放行。如果 package 脚本里间接调用 `tenon test trust --yes`，hook 看不到。真正的拦截依赖「信任需要交互终端或 `--yes`」，以及 `*/test-trust/*` 的路径拒写。
- 用户级信任库的防护是「误写需要刻意」，不是对同 UID 恶意者的密码学防御，模块头已写明。
- `trustScope` 每次调用起两个 git 进程。`tenon status` 路径上每次都会触发，目前量级可接受，没有缓存。
- 结论建立在 Tenon 记录的全部测试通过之上。我没有重跑任何测试，也没有独立验证 F1 的实际输出。
