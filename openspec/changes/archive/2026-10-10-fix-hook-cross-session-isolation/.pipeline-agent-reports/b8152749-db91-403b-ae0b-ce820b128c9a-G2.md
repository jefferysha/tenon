## 1. 对外接口（第 3 组写文档与技能用）

### 1.1 `next` 里的新动作形状

用完（`rounds.current >= rounds.max`）且 `requiredEvidenceFailed` 时，`next` 不再给回退边的 `request-review` / `choose-exit` / `transition`，按不通过的是什么分两种。

**只剩必需评审者不通过，或失败的必需测试都已登记豁免** -> 前进边的 `request-review`，新增三个字段，与已有的 `waivers` 并存：

```json
{
  "action": "request-review",
  "event": "verify-pass",
  "waivers": ["test:code-size"],
  "residual": ["reviewer:security"],
  "rounds": { "current": 2, "max": 2, "source": "workflow" },
  "alternatives": [
    "调高上限后回退修复：这是用户的决定，没有用户明确指示不要执行；由用户定 N（须大于 2），执行 tenon set <c> max_rounds <N>。设置会改变任务状态，已发起或已批准的评审请求随之失效，调高之后重读 next 并重新 tenon review request",
    "经 requirements-changed 回到规格重新规划：tenon transition <c> requirements-changed（在声明了该事件的步骤上执行，例如实现步；回到规格后验证轮次重新计数）",
    "终止任务：用户决定不再继续时就停在这里，不要自行放弃，也不要绕过上限"
  ]
}
```

- `waivers` 只在有待批准豁免时出现；`residual`、`rounds`、`alternatives` 三个只在用完且评审者不通过时出现，未用完时动作与修改前逐字相同。
- `residual` = 必需评审者里 `status === 'fail'` 的 `reviewer:<agent>`，按评审者声明序。
- 通过结论字段（`verify_result` / `branch_status` 等 outcome）在这种情况下照常先填（前进边需要它们才就绪）。
- 已有评审请求绑在前进边上：pending -> `await-review`，approved -> `transition`（沿用旧逻辑）。绑在回退边上（用完之前发的）：当作没有请求，重新发前进边的 `request-review`。
- 评审已 approved 但前进边仍被评审者的 `reviewer-failed` 挡着（接受没覆盖现在的运行或代码）：`fix`，blocker 的 `source: 'reviewer'`、`code: 'residual-unaccepted'`，文案点名 `tenon review revoke <c> --reason <原因>` 后重新 `review request`。

**还有没登记豁免的失败必需测试** -> `stop`：

```json
{ "action": "stop", "code": "rounds-exhausted", "message": "验证轮次已用完（2/2，上限来源：工作流声明），不再自动回退修复；必需测试 code-size 仍然失败且没有登记豁免。停下，把下列出路交给用户，等用户决定：① 先登记步骤测试豁免：tenon test waive <c> --test <测试 id> --reason <理由>（目录套件的失败用 --kind <种类> 或 --covers <条目>），豁免经评审确认批准后再重读 next；评审者仍不通过的部分会作为剩余阻断，随前进边的评审请求一并交给用户接受；② 调高上限…；③ 经 requirements-changed 回到规格…；④ 终止任务…" }
```

- 上限来源标签：`workflow` -> 「工作流声明」，`default` -> 「内置默认」，`task` -> 「任务字段 max_rounds」。
- `stop` 排在 `run-test` 之前（同一份代码上重跑改变不了失败）；目录套件的失败（`testFlow.failed` 里要改代码的项）同样 stop，失败对象取 `subject ?? code`。
- 评审者在必需测试没通过（也没豁免）时本来就跑不了（`agent prompt` 报「还需等待：test:<id>」），所以这条路径上评审者通常还没有结论。

### 1.2 `status --json` 里与上限、剩余阻断相关的字段（没有新的顶层字段）

- `step.rounds`：G1 已有；`exits` 与 `rounds` 现在是同一个事实的两个面：用完后受约束步骤的**回退边**在 `step.exits[]` 里 `ready: false`，多一条 `blockers: [{ source: 'guard', code: 'rounds-exhausted', message }]`（message 写出 `n/m`、来源与 `tenon set <c> max_rounds <N>`）；前进边与放弃边（`scope-expanded`）原样。未用完 / 不受约束时 `exits` 与修改前逐字相同。

- `step.reviewers[].status` 仍是 `fail`（视图层不套用接受记录，`next` 的 `residual` 就取自它）。

### 1.4 剩余阻断：冻结、接受、存放位置

**存放位置：评审冻结清单边车 `openspec/changes/<c>/.pipeline-review-waivers.json`（扩展，不新建文件）。** 理由：`hooks/lib/protected-writes.sh` / `gate.sh` 只按路径保护 `.pipeline-test-plan.json`、`test-plan.yaml`、`.pipeline-review-waivers.json` 等已列名的文件，任何新文件名都不在保护内，而第 2 组不许动 hooks；这个边车已经是「请求时冻结、`tenon review` 在锁内写」的既有位置，agent 的编辑类工具与 shell 写入都被 gate 拒绝。

形状（读取是严格解码，坏形状整份读不出 = 什么都不接受 / 不冻结）：

```json
{
  "version": 1, "phase": "verify", "event": "verify-pass", "requestedAt": "...", "waivers": [],
  "residual": [
    { "key": "reviewer:security", "runId": "<评审运行 id>", "candidate": "workspace:sha256:<64hex>",
      "findings": 2, "summary": ["high src/a.ts:3 SQL 拼接", "medium src/b.ts:9 未校验输入"] }
  ],
  "accepted": [
    { "key": "reviewer:security", "runId": "<评审运行 id>", "candidate": "workspace:sha256:<64hex>",
      "findings": 2, "acceptedBy": "tester@tenon.test", "acceptedAt": "2026-10-09T11:00:00.000Z" }
  ]
}
```

- `residual`：待接受项，请求时冻结，绑定那一次请求（phase / event / requestedAt 与回执逐项相同才算）；`summary` 每条 = `<级别> <位置> <说明>`，折成单行、截 200 字、反引号与尖括号换全角，最多 5 条；`findings` 是阻断级发现总数。
- `accepted`：接受记录，**跨请求保留**（`clearReviewWaiverSelection` 只清待批准项：有 `accepted` 时重写成 `waivers: []` + `accepted`，没有时仍是删文件；`writeReviewWaiverSelection` 重新冻结时沿用现有 `accepted`）。每个评审者只留最新一条，总数 <= 20（`MAX_ACCEPTED_RESIDUALS`，最旧的先丢）。
- 接受只对「评审者 + 被接受的运行 id + 当时的代码候选」有效：`evaluateStepAgents` 在判定里要求当前判定所依据的运行 id 与当前候选都等于记录，才把那条 `reviewer-failed` 当作已处置（结果多一个 `accepted: [{agent, runId, candidate, findings}]` 提示，没有时不出现该键）。代码变了（候选变）、评审者有了新判定运行（含同一候选上带 `--rerun-reason` 的重跑）、换了评审者，记录都对不上，不再生效。同一候选上无原因的更轻重跑不改变判定所依据的那次运行（取最严），接受仍有效。
- `AgentBlocker` 的 `reviewer-failed` 新增可选 `runId`、`candidate`（`evaluateStepAgents` 总会给出）。
- 历史行（kind `tool`，actor 由历史写入器盖章）：`review.residual-accepted reviewer=security run=<id> candidate=<c> findings=<n> by=<确认者>`，每个被接受的评审者一行。

**命令面**

| 步骤 | 行为 |
| --- | --- |
| `review request --event <前进边>`（用完） | `cmdCheck` 新选项 `releaseFailedReviewers`：评审者「不通过」不拦请求（缺失 / 过期 / 进行中 / 宿主不符照旧拦）；锁内用**不带接受记录**的判定冻结待接受项（撤回回执后重新请求，仍不通过的评审者再次列出，不会因为接受过就悄悄消失），逐条输出：`[REVIEW] 待接受的剩余阻断 N 项（…）：` / `  reviewer:security — 2 个阻断级发现（运行 <id>，候选 <c>）` / `    · high src/a.ts:3 SQL 拼接` |
| `review request --event <前进边>`（未用完） | 照旧：评审者不通过 -> `check` 失败，exit 2，不冻结任何东西 |
| `review acknowledge`（人工、非 AFK） | 在提交 approved 回执的同一把锁内（`approveFrozenWaivers`）写入 `accepted`；成功行 `[REVIEW] 已接受剩余阻断 N 项：reviewer:security`（消息码 `review.residualAccepted`）；回执之后追加 `review.residual-accepted` 历史行 |
| `review acknowledge --delegated` | 有待接受项 -> 拒绝（`review.residualDelegatedRefused`），回执保持待确认，什么都没写；与豁免的委托拒绝同一机制 |
| `review acknowledge`（`TENON_AFK=1`） | 有待接受项 -> 拒绝（`review.residualAfkRefused`），回执保持待确认 |
| `tenon check` | 接受生效后评审者不再算阻塞，另出一行 `[WARN] 评审者 'security' 仍不通过（N 个阻断级发现），但用户已接受这个剩余阻断（运行 <id>，只对这次运行与当时的代码有效）`，退出码不受影响 |
| `tenon transition <前进边>` | `stepAgentBlockersFor` 读边车 `accepted` 喂给 kernel 判定，对得上的放行 |

**Dashboard**：Dashboard 确认不展示待接受项，所以不顺带接受：评审请求冻结了剩余阻断时，`POST /api/change/<c>/decisions` 返回 409 `{ ok:false, code:'residual-pending', error }`（提示回终端 / 回复「确认继续」确认），回执保持待确认；`approveFrozenWaivers` 新增 `acceptResidual?: boolean`（缺省 true），Dashboard 路由传 false 作并发窄窗口里的纵深防线。旧请求残留的清单不算（绑定核对）。

**hook 注意点（第 3 组写进技能）**：用户回复「确认继续」走 `hooks/confirm-clear-prompt.sh` 的 manual 路径（`tenon review acknowledge <c>`），会接受剩余阻断；持续授权口令（`INTENT=authorize`）走 `--delegated`，遇到待接受的剩余阻断会被拒绝，且 hook 把输出丢弃，agent 重读 `status` 仍是 `await-review`——要让用户回复「确认继续」。
