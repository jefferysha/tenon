# 调研报告：宿主 hook 的 session_id 可靠性（fix-hook-cross-session-isolation）

日期 2026-10-07。`tenon:deep-research` 已加载；firecrawl/exa MCP 不可用，改用 WebFetch + curl 取官方页面原文并本地 grep（WebFetch 的小模型摘要曾给出与原文不符的转述，例如「session_id 在 resume 时不变」「load_reason」，已弃用，下文引文均取自原始页面文本）。

## 待答问题
1. Claude Code 各 hook 事件是否带 session_id
2. 子代理内 hook 的 session_id / agent_id / agent_type
3. resume / continue / compact 后 session_id 是否变化
4. Codex 的会话标识字段与仓库中 CODEX_THREAD_ID / TENON_HOST_SESSION_ID 的来源
5. 仓库现有 hook 对 session_id 的读取与缺失处理；test-hooks.sh 是否带 session_id

## 结论

### Q1 session_id 是公共字段（所有事件）
- https://code.claude.com/docs/en/hooks 「Common input fields」：「Hook events receive these fields as JSON, in addition to event-specific fields documented in each hook event section.」表中 `session_id` ——「Current session identifier」。因此 PreToolUse、PostToolUse（含 AskUserQuestion）、UserPromptSubmit、SessionStart 都带。
- 页面把 AskUserQuestion 列为普通工具（PreToolUse 可 `defer`；matcher 可匹配），未见 PostToolUse 对它有特殊的输入字段豁免。`tool_name=AskUserQuestion` 的 PostToolUse 输入示例我未能在原文中找到单独条目（证据不足，见下）。
- 文档只说「Current session identifier」，未承诺格式（仓库按 `[A-Za-z0-9_-]{1,128}` 校验，见 Q5）；文档示例是 `"session_id": "abc123"`，真实值为 UUID。

### Q2 子代理：session_id 是父会话的，靠 agent_id 区分
- 同页：「When running with `--agent` or inside a subagent, two additional fields are included」；`agent_id`：「Unique identifier for the subagent. Present only when the hook fires inside a subagent call. Use this to distinguish subagent hook calls from main-thread calls.」`agent_type`：「Present when the session uses `--agent` or the hook fires inside a subagent. For subagents, the subagent's type takes precedence over the session's `--agent` value.」
- SubagentStart 示例里 `"session_id": "abc123"` 与独立的 `"agent_id": "agent-abc123"` 并列；SubagentStop 另有 `agent_transcript_path`。文档**没有明说**「子代理里的 PreToolUse/PostToolUse 沿用父 session_id」这一句；但 `agent_id` 的定义（「distinguish subagent hook calls from main-thread calls」）与「session_id 是通用字段」组合，只能推出 session_id 字段仍是会话级字段、子代理用 agent_id 区分。此点属推断，建议主线用实测或明确按「不依赖」处理。
- Codex 对照（Q4）：「Subagent hooks use the parent session id.」

### Q3 resume / continue / clear / compact 与 session_id：官方未承诺稳定；有大量已知反例
- 官方 SessionStart matcher 表：`startup` New session；`resume` `--resume`, `--continue`, or `/resume`；`clear` `/clear`；`compact` Auto or manual compaction；`fork` 「A new session forked from an existing one: `--fork-session` with `--resume` or `--continue`, the `/fork` background copy, `/branch`, or a conversation you move to the background. Before v2.1.214, forked sessions reported source "resume".」——https://code.claude.com/docs/en/hooks
- `/clear`：https://code.claude.com/docs/en/commands 「/clear [name] Start a new conversation with empty context.」；compact 对应「To free up context while continuing the same conversation, use /compact」。文档未写 `/clear` 是否换 session_id，但「new conversation」+ 独立的 `clear` source 暗示换（推断，未找到一手明文）。
- Agent SDK：https://code.claude.com/docs/en/agent-sdk/sessions 「Forking creates a new session that starts with a copy of the original's history but diverges from that point. The fork gets its own session ID; the original's ID and history stay unchanged.」
- 发行说明（https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md，当前 2.1.292）：
  - 「Changed `claude --resume <session-id> --bg` to continue that session under its own ID when nothing is running it, instead of silently starting a copy; a copy is now announced」——说明 resume 路径上曾存在「悄悄起副本（新 ID）」。
  - 「Fixed `claude -p --resume <file>` adopting a malformed session ID recorded in the transcript; it now resumes under a fresh session ID instead」——特定条件下 resume 会用新 ID。
  - 「stdio MCP servers now receive the same `CLAUDE_CODE_SESSION_ID` as hooks/Bash on `--resume`」；「Added `CLAUDE_CODE_SESSION_ID` environment variable to the Bash tool subprocess environment, matching the `session_id` passed to hooks」（可在 Bash 子进程里取到与 hook 一致的 id）。
  - 「Fixed `/branch` success message not including the new branch's session id for `/resume`」（/branch 产生新 id）。
- 社区 issue（二手/线索，均 Closed as duplicate、无维护者回复）：#12235（2.0.50）「When resuming a conversation using `--resume`, the `session_id` provided to hooks is a new UUID rather than the original session's ID.」https://claudeissues.com/issue/12235-session-id-changes-when-resuming-a-conversation-via-resume ；#26563「session_id in hook payloads switches to a different session ID after /resume」https://claudeissues.com/issue/26563-hook-payload-session-id-misattributed-after-resume ；#39355 / #15545：`--fork-session` 时 SessionStart 报告的是原会话 id。
- 对 2026-10-07 观察（4f9542da → d4b6f501）：**未找到一手依据能精确解释**。可能解释（均未证实）：`/clear`、`/branch`/fork、或 resume 起了新 id（上述 issue 与 changelog 条目）。需要 SessionStart 的 `source` 字段才能分辨；若仓库保存 SessionStart 输入或 transcript，可用 `source` + 新旧 `transcript_path` 核对。

### Q4 Codex
- https://developers.openai.com/codex/hooks（308 跳转到 https://learn.chatgpt.com/docs/hooks）：`session_id`——「Current Codex session id. Subagent hooks use the parent session id.」；公共字段另有 `transcript_path`、`cwd`、`hook_event_name`、`model`；turn 级事件另带 `turn_id`、`permission_mode`。事件含 SessionStart/PreToolUse/PostToolUse/UserPromptSubmit/SubagentStart/SubagentStop/Stop 等；SessionStart source 取值「startup, resume, clear, and compact」。文档未写 resume 后 session_id 是否保持（未找到）。
- `CODEX_THREAD_ID`：Codex 文档未提及（未找到官方文档）。仓库内证据：`.trellis/scripts/common/active_task.py:80-85` 注释「REAL, undocumented (verified 2026-08-05: injected by codex-cli 0.146.0 into shell children, absent from the parent env; openai/codex#19937)」——是 Codex 注入 shell 子进程的环境变量，不是 hook 输入字段。`packages/cli/src/hostKind.ts:19` 用它判定宿主为 codex。
- `TENON_HOST_SESSION_ID`：不是任何宿主提供的变量，是 Tenon 自己的约定：`hooks/review-ack.sh:114` 调 `tenon review acknowledge --delegated` 时由 hook 把 hook 输入的 session_id 注入；`packages/cli/src/commands/review-acknowledge.ts:81` 读 `TENON_HOST_SESSION_ID ?? CODEX_THREAD_ID`。`hooks/gate.sh:305-306` 先读 hook JSON 的 session_id，缺失再回退这两个 env，再回退 `unknown`。
- 注意：Codex 的 hook 输入 `session_id` 与 shell 里的 `CODEX_THREAD_ID` 是否同值——**未找到一手依据**，不应当作同一个键混用。

### Q5 仓库现状（文件:行号）
读 hook 输入 session_id 的位置与缺失/非法处理：
- `hooks/host-session-binding.sh:16-21`：id 空/含非 `[A-Za-z0-9_-]`/>128 → return 1；binding 文件 `.pipeline/terminal-sessions/<id>.json` 必须存在、非符号链接、≤4096 字节、protocol=`pipeline-terminal-session-v1`、内部 session_id 一致（:21-33）、Change 存在且未归档（:35-45）；任一失败 return 1（无回退）。
- `hooks/breadcrumb.sh:119-134`：有 session_id → 只认 binding，无 binding 则「generic resume remains unbound」；无 session_id 才回退 `ACTIVE_NAME`（仓库全局指针，:134）。
- `hooks/router.sh:44-46`：非法→置空；`:961` 仅非空时写 `host_session_id`；「malformed/unknown ids stay absent rather than falling back to the repo-global active Change pointer」（:41-43）。
- `hooks/confirm-clear-prompt.sh:74-76`、`hooks/interactive-skill-gate.sh:82-84`：读取并校验，非法→置空；目前仅用于授权/自治路径，评审与交互 marker 仍是项目根全局文件（`.pipeline-pending-*`）。
- `hooks/review-ack.sh:107-114`：`--delegated` 模式 session 非法 → return 1；有效则 export 给 CLI。
- `hooks/gate.sh:305-306`：只用于自批准候选的 identity 字符串，缺失→env→`unknown`；marker 判定本身不看 session。
- `hooks/terminal-activity.sh:20-24`：缺失/非法 → `exit 0`（失败即放行）；`:45` 要求 binding 的 session_id 一致才写心跳。
- `hooks/codex-skill-receipt.sh:45-47`：session_id、transcript_path、turn_id、tool_use_id 缺任一 → `exit 0`。
- `hooks/skill-tracker.sh:94`：读取，用于技能追踪（未展开核对其缺失分支）。
- `hooks/confirm-clear.sh`：**完全不读 session_id**（只取 cwd），PostToolUse AskUserQuestion 清项目根 marker——这正是跨会话互相清标记的位置。
- `hooks/json-input.sh`：只实现字符串键值提取，不做 `agent_id` 识别；仓库内 hooks 目前无一处读取 `agent_id` / `agent_type`（grep 无命中）。

`tools/test-hooks.sh` 构造输入：带 session_id 的有 `:780`（breadcrumb 未绑定会话）、`:1546`（router，`"s"`）、`:1637,1670,1675`（router/rv-session）、`:1913-1920`（terminal-activity，绑定与未绑定）、`:2159-2201`（confirm-clear-prompt 与 interactive-skill-gate，授权会话 vs `session-authority-other`）、`:2488`（PostToolUse 大输入，`"s"`）、`:3366`。未带 session_id 的是其余 gate / confirm-clear 的大量用例（仓库默认路径），需要在改造时补「带/不带 session_id」双向用例。

## 证据不足
- AskUserQuestion 的 PostToolUse 专属输入样例：官方页只确认 session_id 为公共字段，未见独立样例。
- 子代理内 Pre/PostToolUse 的 session_id 是否等于父 session_id：文档无直接一句话（Codex 有）。
- Claude `/clear`、`--resume`、`--continue` 是否换 id：无官方明文承诺；只有 issue 与 changelog 间接证据。
- Codex resume 后 session_id 是否保持；hook 输入 session_id 与 CODEX_THREAD_ID 是否同值。
- 4f9542da → d4b6f501 的具体触发原因。
