### 2. P1：`--delegated` 不能来自带空白的引号串
- 去引号时按 shell 规则划引号区间（区间外遇哪种引号就开哪种，区间里只有同种引号能关；两种混用时按双引号再切一次、用累计偏移对齐出每个引号字符的种类），带空白的区间里每个词前垫 **`\003`（QMARK）**。`--delegated` 只认原词恰好等于它（不带任何标记）。`"--delegated"`、`--deleg""ated`、`'--delegated'` 照常算开关。
- **与任务说明的一处不同**：任务说沿用 `\002`，我另开了 `\003`。原因：`ack_q` 规则（确认子命令那个词来自带空白的引号串，则开关一律不认，堵住 `bash -c 'tenon review acknowledge c' --delegated`）要把「引号串里的词」和「花括号 / 反斜杠拆出来的词」分开；若共用 `\002`，`tenon review ack{n,}owledge c --delegated`（已有的放行用例）会被误拦。两个标记字符都不在还原范围内（`\u0000`–`\u0003`、`\u007f` 不还原）。
- 转义空白（`a\ b` 的 b）同样垫 QMARK（它也是「一个参数被切成几个词」）。
- **整条命令以 `<shell> -c|-lc "整串"` 开头**（Codex 的 `/bin/zsh -lc "…"`）先取出整串再判定（`pipeline_peel_shell_wrapper`，整串里不能再有同种引号，否则不取）。不这样做，Codex 包装下的合法委托确认会被引号口径拦掉，已有的「codex 登录 shell 包裹」放行用例会红。
- 评审挂起放行表 `is_review_control_command`：选「判定在它之前已拒绝」。顶部拒绝与放行表读的是同一份命令文本（同一个 64 KiB 上限的读取函数），顶部先跑，被判成手动确认的命令走不到放行表；在函数头注释里写明，并让 P1 写法进「评审挂起 + 没有标记」两种状态都跑的拦截表（RED 时评审挂起那一遍红了 4 条：P1 的 `"x --delegated y"`，以及 `--reason` / `--event` / `--as` 的值是 `--delegated` 三条，都是 `*\ --delegated\ *` 通配命中；改完后顶部先拒绝，4 条全绿）。放行表本身没改。

### 3. P2：review 之后不再在第一个非选项词放弃
- 状态机改成与 `program-review.ts` 的 `review <sub> [name]` + `--event/--delegated/--as/--reason` 对齐：带值选项的下一个词是值；`--` 之后全是位置参数；第一个位置参数就是 sub（`acknowledge` → 确认；`request` / `revoke` / 别的词 → 不是确认）。
- 值或位置参数带 QMARK（占了几个词）、或引号核对做不了时，不再按「第一个位置参数」判，退成「段里出现 `acknowledge` 词就算确认」（失败关闭）。
- `--delegated` 在 review 之后任何位置都算（`tenon review --delegated acknowledge x` 现在放行）；**带值选项的值不是开关**（自查时发现 `tenon review acknowledge c --reason --delegated` / `--as --delegated` / `--event --delegated` 此前会被当成开关放行，已修并补用例）。
- 与任务说明「在 review 之后的词里找确认子命令」相比，我用了「第一个位置参数」的精确判法而不是「任意词」：这样 `review request … --reason "…acknowledge…"`、`review revoke c --reason acknowledge` 不会被误拦；不确定时退回任意词的宽判。

### 4. 花括号步长
展开后还留着没认出的花括号组（`{x..y..N}` 等）的词：字母能依次拼出 acknowledge 就置 `OVERFLOW` + `HIT`（按现有超预算规则拦）。纯数字区间（`{1..10..2}`）字母拼不出，照常放行。`tenon review ack{n..n..1}owledge x`、`{a..z..1}cknowledge` 都拦。
