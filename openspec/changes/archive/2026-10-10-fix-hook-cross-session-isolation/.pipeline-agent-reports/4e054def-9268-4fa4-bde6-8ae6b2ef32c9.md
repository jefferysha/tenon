## 二、F1 复核：定级由 medium 降为 low

**F1 是什么**：`tenon session activate --host-session <任意合法 id>` 在写入新绑定后，会删掉别的会话对同一 Change 的绑定。被移交的会话落入「无任务」，项目根上只带 change 的评审标记不再拦它，用户在该会话里的放行语也不再写回执。

**1. 改动前就有的同等自我脱离**

- 我复核了 `activate <另一个 Change>` 这条路径。它改写共享指针，评审标记随即不再匹配本会话任务，等价于脱离门。
- 设计 §1 也写明拦截只是体验层，离开评审步仍要 canonical 回执。
- 所以「agent 能让自己不被评审标记拦」不是本任务新增的能力，我同意这点。

**2. 新增的可利用面**

- 比改动前多出一点：调用者可以用某个仍然活着的**别的会话**的 id 去 `activate`。这会删掉该会话（原持有者）对同一 Change 的绑定，并把 Change 绑给调用者传入的 id。
- 前提是知道别的会话的 id，这些 id 就是 `.pipeline/terminal-sessions/` 下的文件名，同机同用户可读。
- 改动前绑定文件按「会话 id」一对一，也可以被同样覆盖，所以「冒用别人 id」本身不新。新增的只是「删除其他会话对同一 Change 的绑定」这一动作。

**3. 是否被记录覆盖**

- `docs/adr/fix-hook-cross-session-isolation.md:24` 把自动移交写成决定，第 55 行写明「两个仍活着的会话先后 activate 同一 Change 时，先绑的那个失去门约束」。第 40 行否决了 `--takeover`，理由是会卡住会话恢复。设计文档 §1 对应段落有同样内容。
- 记录的是「两个会话先后 activate 同一 Change」这一自然场景，用户已确认。「agent 蓄意传入他人 id」是同一机制的恶意用法，同一个行为、同一个后果。
- 记录里没有单独写「`--host-session` 不验证调用者」，所以我认为需要补一句文档说明，但不是缺陷。

**4. 我的原修法不可行**

- 我原来建议「要求 `--host-session` 等于宿主会话环境变量」。主线核实 Claude Code 的 agent shell 里没有这个变量，我对 Claude 环境无法反驳，这个建议作废，请忽略。
- 剩余可行的缓解：在 ADR 风险一节补一句「`--host-session` 不鉴权调用者，同用户 agent 可移交他人的绑定，canonical receipt 是真正的边界」。不需要改代码。

**5. 定级结论**

- 改动前已有的脱离门禁路径等价，新增部分已被经用户确认的记录覆盖，边界仍是 canonical receipt，不能直接批准评审。
- 故定为 **low**，作为需在文档里写明的残余风险，不再是阻断项。
