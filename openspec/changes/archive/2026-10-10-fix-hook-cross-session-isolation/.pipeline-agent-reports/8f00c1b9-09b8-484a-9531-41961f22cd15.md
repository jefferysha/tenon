- 自测中发现并修掉的缺陷：`\001` 当标记会让 bash 3.2 的模式替换出错（改 `\002`）；`${rest#*字母}` 对距离是平方级（改 `IFS=字母 read` 切一次，40 秒降到 1 秒）；续行前的空格留下只剩标记的空词会打断词链造成漏拦（实测去掉跳过那行时 exit 0，已修并加用例）。

## 第 4 部分：命令读取上限（主线追加）

### 做法
- 手动 acknowledge 判定读命令的上限 `ACK_COMMAND_MAX` 从 512 KiB 降到 **64 KiB**（65536 个编码后的字符）。只改 gate 这一处判定用的上限；`RECORD_COMMAND` 等受保护路径判定仍是 512 KiB，`hooks/json-input.sh` 没动。
- 超过上限的命令不解码、不逐字处理：解码失败且输入长度大于上限时，对原始输入做一次线性的字面检查——含 `acknowledge` 就拦（不看 `--delegated`），不含就不判定。拦截文案与原来相同（抽成 `pipeline_refuse_manual_acknowledge`）。
- **把这条拒绝提前到受保护路径写入判定之前。** 原先它排在后面：受保护路径分支遇到含 `bash` / `node` / `./` 等字样的超大命令要解码并分析，自审批候选提取更慢，hook 超时被宿主当非阻断错误放行，拒绝就跟着被拖过限时。提前之后，拒绝判定的耗时只取决于它自己。
- 函数头注释和调用处注释已改：上限数字、实测原因；「覆盖不到」清单里的「超过 512 KiB 的命令」改为「超过 64 KiB 且原文不含 acknowledge 字样的命令里的拆分 / 编码写法」，并去掉原先的「接近上限会跑满限时」一条。

### 为什么是 64 KiB，不是建议的 128 KiB
实测（本机 bash 3.2.57，整个 gate 的墙钟，hooks.json 给 gate 的限时是 5 秒），载荷是命令字段占满上限的密集写法，末尾带一个拆词的手动确认，判定都正确（exit 2）：

| 命令字段约 131 000 字符（旧上限 512 KiB 下） | 耗时 |
| --- | --- |
| 密集引号 `\"` | 3.0 秒 |
| 密集反斜杠 | 2.6 秒 |
| 密集 `\x61` | 2.2 秒 |
| 空格分隔的反斜杠 | 2.0 秒 |
| 空格分隔的引号 / 转义编码 | 1.4 / 1.3 秒 |
| 密集花括号词 | 0.3–0.5 秒 |

128 KiB 的最坏载荷约 3 秒，超出「最坏 ≤ 2 秒」的目标，也没有给宿主与机器负载留余量。耗时的大头是 `json-input.sh` 的逐段 JSON 解码（已有成本，密集引号时约每 KB 20 ms，65 KB 里占 1.35 秒，我的函数只占 0.16 秒），所以只能降上限。

| 命令字段约 65 000 字符（新上限 64 KiB） | 耗时 |
| --- | --- |
| 密集引号（JSON 里 `\"`） | 1.5 秒 |
| 密集反斜杠 | 1.4 秒 |
| 密集 `\x61` | 1.1 秒 |
| 空格分隔的反斜杠 / 引号 / 转义编码 | 1.0 / 0.7 / 0.7 秒 |
| 密集花括号词 / 单引号 / `$` | 0.1–0.4 秒 |
| 超过上限（229 KB 的普通词填充），原文含 acknowledge | 0.4 秒，拦 |
| 超过上限（229 KB），原文不含该词 | 0.3 秒，放行 |
| 小命令 | 约 13 ms / 次，与改前无可测差别 |

最坏 1.5 秒，在目标之内。64 KiB 也和同文件里 `json_command_short` 的上限一致。

### RED → GREEN
- 新用例（`tools/test-hooks.sh`）：
  - 上限之上、原文含 acknowledge：`echo acknowledge`、带 `--delegated` 的确认，都要拦（两条）；上限之上、原文不含该词，放行。
  - 上限之下：带 `--delegated` 的委托确认照常放行、手动确认照常拦（证明上限之内仍按完整静态判定）。
  - 上限附近三类密集载荷（引号 45 KB、转义编码 57 KB、花括号词 49 KB）各一条拦截（词中拆开的手动确认），外加转义编码密集的无关命令放行，全部断言 3 秒内完成。
- 先在旧上限下跑：`1886 passed, 2 failed`，两条失败正是「上限之上原文含 acknowledge」的拦截用例（exit 0，应为 2）；其余新用例在旧实现下本来就通过（它们是边界和性能的守卫）。改实现后 `1888 passed, 0 failed`。
- 一次试错：第一版「上限之上」用例用分号填充，旧实现下整个测试套件卡了十分钟以上。原因不在手动确认判定，而是 gate 后面的自审批候选提取对分隔符填充是平方级（见遗留）。改用普通词填充。

### 仍覆盖不到（函数头注释已如实写明）
变量或命令替换拼出的字符串（含 eval、printf）、别名与 shell 函数、脚本文件里的调用、脚本语言解释器内联程序（`-c` / `-e`）里构造的调用、靠文件系统展开的通配符路径、**超过 64 KiB 且原文不含 `acknowledge` 字样的命令里的拆分 / 编码写法**（例如 70 KB 填充后再接 `tenon review ackn""owledge x`，现在会放行；超过上限的命令靠字面检查，这是主线定下的取舍）。
