## 发现清单

**F1（low，不确定）`hooks/gate.sh:174-193`：两个按需加载的库缺失时处理方向相反**
- `ack-command.sh` 缺失调用 `pipeline_refuse_ack_lib_missing`，失败关闭。
- `protected-writes.sh` 缺失直接 `exit 0`，失败放行，代码注释说明这沿用本文件的 fail-open 约定。
- 两者都有 `verify-skills.sh` 的发布守卫，也有测试覆盖（`tools/test-hooks.sh` 第 681 行附近）。
- 这是否是有意区分，我没有查设计文档。如果是，建议在 `gate.sh` 里用一句话写明两个库的方向为什么不同；如果不是，则统一。

**F2（low）`packages/cli/src/commands/statusStepRounds.ts:12-21`：`stepRounds` 是纯转发**
- 只做了 `readStepRounds(deps, dir, state, plan, stepId)`，没有任何附加逻辑。
- 按删除测试，删掉它后复杂度不会在调用方重新出现，只是少一层名字。
- 它已被 `review-rounds.ts` 与 `statusStep*` 调用，可以保留作 CLI 内的稳定入口。更简洁的做法是调用方直接用 kernel 的 `readStepRounds`，并删掉这个文件。

**F3（low）`packages/server/src/transition.ts:238-245` 与 `packages/cli/src/main.ts:279-285`：`.pipeline-history.jsonl` 的读取各写了一份**
- 轮次判定逻辑只有 kernel 一份实现，CLI 与 server 没有复制。
- 重复的只是「读 JSONL 文件」这个很薄的 IO 适配器，而且两份行为不一致：
  - server 只对 ENOENT 返回空串，其他错误上抛。
  - CLI 的 `main.ts` 对任何错误都返回空串。
- CLI 这种吞掉所有错误的做法会让轮次偏小，偏离了 `step-rounds-read.ts` 注释里的失败关闭意图。
- 实际影响很窄：只有没有 canonical 链头的旧任务才走 JSONL 分支。
- 修法：把「读 history 文件，仅 ENOENT 返回空串」做成共享的适配器，由两个宿主复用。

**F4（low）`hooks/lib/` 的拆分**
- 拆分成按需加载的库是合理的：库只被 `gate.sh` 引用，有发布守卫，`tools/test-hooks.sh` 也能直接引用。
- 单文件约 630 到 680 行。体量是否越线已由 code-size 评审者覆盖，这里不重复报。

## 结构结论

- kernel 没有混进 IO。`step-rounds-read.ts` 通过注入的 `recordStore` 与 `readHistoryRaw` 读转换链和历史文件。
  - 状态里有链头却没装配 `recordStore` 时直接抛错，不退回 JSONL，这个失败关闭的设计是对的。
- CLI 与 server 两处轮次读取没有重复实现，都走 kernel 的 `readStepRounds`。
- `statusStepRounds*` 与 `review-rounds.ts` 的职责边界清楚：前者负责状态块里轮次的读取与动作路由，后者负责 `review request` 的上限强制与剩余阻断冻结。
- 本轮没有发现 high 及以上的结构问题。
