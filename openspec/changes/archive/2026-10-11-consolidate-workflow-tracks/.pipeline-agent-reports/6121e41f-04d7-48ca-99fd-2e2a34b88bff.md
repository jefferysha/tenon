## 逐项审查结论

按 correctness、安全、错误处理、并发四个维度。

### 主线要求核实的 AFK 互斥

**结论：成立。**

- `claimWithFreshAfkWorkflowAuthority` 先重读授权，再调用 `claim(expected.track_id)`，这个回调就是 `state.claim(name, expectedTrackId, {workflowRunId, workflowId, workflowFingerprint, loopId, iterationId})`。
- `queue/claim.ts:58-86` 在 `store.withLock(changeDir)` 内重新读状态，要求同时满足：
  - `automation === 'queued'`。
  - `track === expectedTrackId`。
  - `runMetadata` 与期望的 run 身份逐项相等（`runId`、`workflowId`、`workflowPlanFingerprint`、`loopId`、`iterationId`）。
  - `archived !== 'true'`。
- 任一不满足就返回 false，不写；通过后在同一把锁内 `writeUnderLock`。
- `set track` / `cas track` 持"项目锁到任务锁"，claim 只持任务锁，但 claim 在锁内重读 `track`，轨道漂移会被拒绝。
- 授权取自 WorkflowRun 的不可变快照，工作流 YAML 之后的编辑不影响它。去掉 `TrackRegistry` 外层锁后，没有遗留窗口。

## 发现清单

1. **low**，`packages/kernel/src/workspace/archive-task.ts:319`：这里的描述按主线的要求修正。`runOpenspecArchive` 成功之后那次 `archiveEntries` 已包在 try/catch 里，读失败时进入 `unreadable` 分支，归 `activeDir=null` 的 `move-failed`，不是裸异常。目录已改名为带序号的 `runDir` 之后，剩下的裸异常来源只有 `exists(runDir)`（第 319 行）：它抛非 ENOENT 的 lstat 错误时，会被 `archiveTask` 的 catch 包成 `move-failed`，但 `activeDir` 缺省指向原 `source`。此时原目录已不存在，`clearTaskResult` 读状态失败，只会在错误信息里追加"没能清回空值"，`task_result` 残留在 `runDir` 上。下次 finish 或 terminate 会覆盖它，影响小。`failedBeforeMove` 里的 `exists(runDir)` 在它自己的 try 内，不是来源。修法：这一处用 `ArchiveTaskError('move-failed', …, runDir)` 包装，让回滚指向 `runDir`。
2. **low**，`packages/server/src/serverGetActivityRoutes.ts:166、190、216` 与 `serverPostExecutionRoutes.ts:64、89、114、139、219`：`decodeURIComponent(segment)` 对畸形百分号编码仍会抛 `URIError`。本次新增的 `&archived=1` 读取分支（history、snapshot）沿用了同样写法，生命周期路由已修，这里没有同步。修法：抽一个共享的安全解码函数，畸形时返回 400。
3. **low**，`packages/server/src/serverPostGovernanceRoutes.ts:~228`（工作流保存）：catch 现在对所有异常统一返回 500。旧代码把进入锁之前的失败（如无法形成引用校验快照）归为 400 `errors`。新逻辑里，写盘前的路径信任类错误（`assertWorkflowRootAnchor`、`ensureWorkflowProjectCoordinationPath`）也会变成 500。修法：按错误类型区分，客户端可修复的错误返回 4xx。
4. **low**，`packages/cli/src/e2e-test-outputs.test.ts:32`：用 `toContain` 比对 `serve.mjs`、`server-state.ts` 的整行源码文本，格式化或常量改名就会误报。修法：只断言目录字面量，或导出 `SERVER_DIR` 常量来比对。
5. **low**，`packages/cli/src/integration-harness-legacy.ts:28`：退役 standard 模板的逐字拷贝，将来 schema 变化会静默漂移，只能靠集成测试失败发现。修法：加一条断言，确认它仍能被 `parseWorkflow` 解析并编出计划。

## 残余风险

- 此前提的 AFK 互斥风险已核实并关闭，见上文。
- `frozenProjectLayer` 的轨道 id 来自宿主报告的任务状态。防线是授权快照的 `trackId` 等值比较，加上 claim 内的 `track` 复核。若将来有人绕开这两处，宿主就能选择另一条 `eligible` 的分支。
- `executionCoordinatePort.ts` 的 default 分支：任务记着的轨道不在冻结快照里（例如升级前遗留的 `chat`、`free`）时，`compileEffectiveWorkflowPlan` 或 `effectiveWorkflowPlanFromSnapshot` 会抛 `UnknownTrackError`，AFK 坐标无法冻结。这是失败关闭，不会越权，但这类在途任务进不了 AFK。我没有确认这种状态在实际数据里是否存在。
- `skill-action-authority-provider.ts` 和 `manifest.yaml` 把按 profile 的授权收窄为只认 `_all`。用户自己的 manifest 如果仍带 `free: []` 这类按 profile 的拒绝项，会被忽略，授权全靠分支的 `automation`。属有意收窄，升级说明里应点名。
- 仍未读的项目见 C 档。主要是 kernel 类型文件、已删除的文件，以及 `tools/oracle`、`bench`、`test-hooks.sh`。这些只有随动或测试脚本，没发现逻辑风险的迹象，但没有逐行验证。
- `archiveDirIsTask` 对 `foo` 的第二份归档与任务 `foo-2` 的归档分不开，文件头已说明并接受。
