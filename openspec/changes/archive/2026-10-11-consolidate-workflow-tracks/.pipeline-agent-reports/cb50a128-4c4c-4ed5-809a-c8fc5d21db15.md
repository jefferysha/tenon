## 对取舍 1-6 的判定

1. 离开条件 = 步骤 guards 并上前进出边 guards:与 §1b 配套通用化及"离开条件一次列全"一致,**相符**。
2. advance 只走前进边:与 Q11 和 delta 场景一致,**相符**。
3. `--domain` 与状态字段 `domain`:设计 §2 明说"建任务时记入任务状态",**相符**,是对规格的落地。
4. 平铺工作流不可进 AFK:规格只在分支上声明 `automation`,平铺工作流无处声明。规格没有明确这一结果,见 F3,**规格应补一句**。
5. `tenon test sync --prune` 与 `vitest.isolate-runtime-home.mjs`:属于流程必需的验证设施,不算多做,见 F4。
6. N-1 已知限制:规格没有要求,已写入发布说明并有精确断言,见 F5,**可接受**。

## 发现

- **F1(low)** 设计 §2 写"`security` 只在碰到鉴权/依赖/契约路径时加入",`default.yaml` lite 的 verify 里 `security` 是无条件 `required: true, block_at: medium`。同一设计写"步骤、门禁、测试照搬现 `standard`",而 HEAD 的 `standard.yaml` 也是无条件 required。设计文档内部自相矛盾,实现取了"照搬"那一支,请主线裁决。delta spec 未涉及此条。
- **F2(low)** `packages/dashboard-app/src/model/progressModel.ts:228-229` 仍有 `workflow === 'default'`,用于排序而不是能力判断,不违反"不得以名称判治理能力"。如果架构检查有白名单,建议确认这处已被它覆盖。
- **F3(low)** 平铺工作流因无法声明 `automation` 而不可进 AFK(失败关闭)。delta spec 未写这一行为,建议在 `workflow-tracks` 补一句。
- **F4(low)** `tenon test sync --prune`(`test-sync-prune.ts`)、`vitest.isolate-runtime-home.mjs` 和 `.tenon/tests/catalog.yaml` 的 `e2e/dashboard/support/*.mjs` 一行,规格均未提及。它们是工作流必需测试的验证设施,不是产品行为,不按多做处理,建议规格补一句。
- **F5(low)** N-1(v0.3.1)读取升级后新建的 lite/平铺任务被拒,新 default 任务的 `status` 投影降级为警告。这是规格没有承诺的兼容限制,已记入发布说明和 `n-minus-one-compat.sh`,建议在 `design.md` 风险段补一条。
- **F6(low)** 轻量验证步没有显式写 `max_rounds: 2`,而其他三条轨道写了。设计 §2 说"沿用默认 2 轮",`standard.yaml` 在 HEAD 也没有写。我没有找到解析层的默认值落点,所以不判定偏差,请确认默认值确实是 2。
- **F7(low)** 验证报告显示 `code-size` 超出 `lines_added ≤ 2000`(新增 29395 行,删除 33431 行,净减 4036 行),已登记豁免待批准。这是流程项,与规格一致性无关。
