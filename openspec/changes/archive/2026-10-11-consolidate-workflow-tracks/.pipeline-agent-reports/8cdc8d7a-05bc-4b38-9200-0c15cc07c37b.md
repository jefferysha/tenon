## 结论要点

依赖方向：
- kernel 没有依赖 cli、server、automation。
- server 和 cli 只经 `@tenon/kernel` 的公共导出使用轨道和生命周期能力。
- automation 的 `frozen-project-layer` 和 `custom-phases` 只依赖 kernel 公共 API。
- `custom-phases` 对分支做逐条求值，没有取"第一条"。
- `frozen-project-layer` 授权取自冻结快照，失败时一律关闭，边界清楚。

轨道并入分支：
- 分支只有一份解析：`branches.ts` 的 `workflowBranches` 加 `resolve-track.ts` 的 `resolveTrack`，放在无依赖的叶子模块里避免环。
- cli、server、automation 没有各自再解析一遍分支。
- `parse-track-branch`、`compile-track-branch`、`serialize-track-branch` 分别是语法层、值域层、写回层，职责对称。
- `effective-plan-build` 里的 `legacyPlanTrack` 被收窄成只服务旧快照。

路由分层：
- 数据流是：`routing/router-table.ts`（纯函数建表） → `router-sources.ts`（读文件有界、不跟随符号链接） → `router-cache.ts`（编码） → `router-gen.mjs`（薄壳，动态加载 kernel 的 dist） → `router.sh`（消费）。
- 分层正确：纯函数与 IO 分开，输出只有 hex 数据，没有 shell 赋值。

任务生命周期：
- `createTaskLifecycleApplication` 的 store、clock、git、openspec 调用器、终端活跃探测都可以注入，只有默认值才碰 IO。
- 锁序统一在 `lockedTask`。
- cli 和 server 共用这一个应用层，没有重复实现。
- `commit-paths.ts` 是纯净的小模块，git 以注入函数传入。

`check-architecture` 对新边的覆盖：
- 覆盖的有：
  - 执行模型字面量比较（`execution-model-seam.mjs`）。
  - 跨包深度 import，必须是 `exports` 里声明的键。
  - 工作流身份的 `default` 比较。
  - 领域目录引 `node:` 模块。
  - 内核运行期 import 环。
  - 各层的行数。
- 没覆盖的有：
  - 谁可以 import `legacy-phase-manifest/`。
  - `routing/` 的纯函数模块是否碰 IO。
  - 内置工作流名单的重复（见发现 2、3、7）。

## 发现清单

1. **medium** `packages/kernel/src/infrastructure/guard-file-context.ts:21`：基础设施层 import `workflow/legacy-phase-manifest/phase-exit-context.js` 里的类型 `BoundedFileRead` 和 `PhaseExitFileContext`。`step-exit-report.ts:26` 也引了 `PhaseExitFileContext`。`HEAD` 上这个类型放在 `workflow/` 下，本任务才把它挪进"下个版本整体删除"的目录。旧引擎删除时，新旧引擎共用的出口报告和 infrastructure 都会断，而且 infrastructure 反向依赖了 workflow 的子目录。修法：把这两个类型放回中性模块（如 `workflow/phase-exit-types.ts`），让 `legacy-phase-manifest/` 反过来依赖它。

2. **medium** `packages/kernel/src/routing/router-table.ts:17`：`BUILTIN_ROUTER_WORKFLOWS = ['default','design-system']` 重复了 `workflow/identifier.ts:16` 的 `TEMPLATE_WORKFLOW_NAMES`。这份名单决定"可直接路由"还是"必须先让用户选择"，两处各改一处会让路由和模板清单不一致。`check-architecture` 的身份规则只看 `=== 'default'` 比较，这种 `.includes` 抓不到。修法：`isBuiltinRouterWorkflow` 复用 `isTemplateWorkflowName`，`builtinRank` 复用同一个有序清单。

3. **low** `tools/check-architecture.mjs` 和 `tools/execution-model-seam.mjs`：这两个检查只拦字面量比较，不拦 import。`legacy-phase-manifest/` 目前被这些目录外文件直接引用：
   - `effective-plan-build.ts:12`
   - `implicit-completion.ts:15`
   - `guard-file-context.ts:21`
   - `step-exit-report.ts:26`
   - `index.ts`

   接缝的注释说"整目录同生共死"，实际删除面比目录大。修法：加一条 import 规则，只允许白名单文件引旧目录；或收成单一的 `legacy-index.ts`。

4. **low** `packages/kernel/src/workflow/execution-seam-types.ts:12`、`step-exit-report.ts:10`、`transition-application*.ts`：新引擎的接缝契约是用 `flow/transition-table.ts` 的 `TransitionContext` 和 `EventName` 声明的。`flow/` 里的旧模型代码和新引擎代码纠缠在一起：`flow/default-event-policy.ts` 引 `workflow/guard-handlers`，`guard-handlers.ts:18` 又引 `flow/guard.ts` 的 `taskCount`。双向依赖现在只靠类型导入躲过运行期环检查。删旧引擎前需要先把 `TransitionContext`、`taskCount` 迁出 `flow/`。

5. **low** `packages/kernel/src/flow/default-event-policy.ts` 的删除面：grep 确认 step-graph 代码没有使用 `DEFAULT_EVENT_POLICY`、`evaluateDefaultEventPreconditions`、`normalizeDefaultGuardFields`。它们只被 `legacy-phase-manifest/{legacy-execution,transition-plan-default,forward-edge,phase-exit-context}.ts` 引用，另有 `flow/index.ts` 重新导出。CLI 里还有三处用到，在 CLI 自己的旧模型分支里：
   - `check.ts:139`：`evaluateDefaultEventPreconditions('verify-pass', …)`
   - `check.ts:129`：`deps.flow.guardCheck`
   - `statusStep.ts:143`：`phaseExitGuardFields`

   `check.ts` 这一段和 kernel 的 `legacy-execution` 适配器并行实现，删旧引擎要在两个包里同步清理。修法：把这个文件挪进 `legacy-phase-manifest/`，CLI 只经 kernel 导出的旧引擎入口调用；并在 ADR 或设计文档里写一份跨包删除清单。

6. **low** `packages/server/src/endedTasks.ts:~58`：`ARCHIVED_TASK_DIR`（任务名字符集）和 `DATED_NAME`（日期前缀）重复了 kernel 里的命名知识：
   - `archive-task.ts:63` 的 `isTaskLifecycleName` 和 `datedName`。
   - `archived-task-name.ts` 的日期前缀正则。

   同一份"归档目录名 = 日期 + 任务名 + 序号"的约定散在三处。`endedTasks` 里"有界、`O_NOFOLLOW` 的只读读取"和 `router-sources.readCapped` 也是同类重复。两者职责不同（`archiveDirIsTask` 判定任务是否已归档，`endedTasks` 列出摘要），没有重复实现，只是命名约定重复。修法：kernel 导出一个 `parseArchivedDirName(dir): {date, name} | null`，两处共用。

7. **low** `packages/kernel/src/workspace/archive-task.ts` 和 `task-lifecycle.ts:150`：
   - `archive-task.ts` 把纯逻辑（`isTaskLifecycleName`、`fieldText`、`terminalTaskResult`、`taskArchiveSpec`、`datedName`）和 IO（`execFile`、锁、`rename`）放在同一个 378 行文件里。
   - `task-lifecycle.ts:150` 的 `scalar` 与 `fieldText` 等价，是重复。
   - `taskArchiveSpec` 通过快照里 `documentPolicy` 是否存在来推断 `openspec` 或 `none`。分支本身已有 `TrackBranch.spec` 字段，这里是第二个来源。我没有验证两者在所有分支上都一致，不确定。

   修法：纯函数拆到 `task-names.ts` 或类似模块；`task-lifecycle` 复用 `fieldText`；`taskArchiveSpec` 说明为何不读分支 `spec`，或直接读它。

8. **low** `tools/check-architecture.mjs:184`：`DOMAIN_DIRS` 不含 `kernel/src/routing/`。`router-table.ts` 和 `router-cache.ts` 注释写"纯函数"，但没有规则防止以后混进 `node:` 调用。`router-sources.ts` 是 IO 边缘，应列入 `DOMAIN_INFRASTRUCTURE`。修法：把 `routing/` 加进 `DOMAIN_DIRS`，把 `router-sources.ts` 加进例外。

9. **low** `packages/server/src/serverWorkflowOrchestrationRoutes.ts:108`：没给 `track` 时 `track = listTracks(compiled)[0]?.id`，隐式取第一条分支；而 `resolveTrack` 与 `custom-phases.ts` 都明确拒绝"取第一条"。如果这是预览接口，取第一条可以接受；我没有读该处上下文，不确定。如果它会影响真实的冻结或授权，应该改成显式报错。

10. **low** `packages/cli/src/commands/execution-cli-seam.ts:42`：同上一轮 low 4，`frozenPlanCandidates` 在 CLI 里枚举两种执行模型名，且候选顺序是隐含契约。修法：由 kernel 导出候选列表。

## 残余风险

- `router.sh` 和 kernel 之间有一份跨语言契约：`router-table.ts` 的 `routerSourceDigest` 摘要字节流约定、`MAX_ROUTER_ROWS = 64` 的行数上限、`router-sources.ts` 的文件读取界限，在 `router.sh` 里各有一份。只有 `tools/test-hooks.sh` 在守。这是设计选择，不是缺陷；改任何一边都要同时改另一边。
- `hooks/router.sh` 内部的分层、`router.sh` 里残留的 `standard:*|simple:*` 分支都没有读，没有结论。
- `check:architecture` 在实现步已通过，我没有重跑；本报告对它的判断只来自读规则。
- 各 `*.test.ts`、dashboard-app、生成产物没有评审。
