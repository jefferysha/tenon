## 0. 待答问题

- Q1 OpenSpec CLI 对 `openspec/changes/<name>/` 下「不是 OpenSpec 变更」目录的处理：`validate --all --strict` 是否判失败；有无官方跳过 / 忽略机制；`archive <name>` 的行为。

## 1. 摘要（先看这里）

1. **本仓库钉死的 `@fission-ai/openspec@1.6.0` 没有任何忽略机制**。`validate --all` 把 `openspec/changes/` 下每个非 `archive`、非 `.` 开头的目录都当成变更，零 delta 一律报错 `Change must have at least one delta`，`--strict` 与否都一样。已实验复现。
2. **官方有一个跳过机制，但 1.6.0 里没有**：`.openspec.yaml` 里写 `skip_specs: true`，从 **1.7.0** 起生效。实验确认：目录里只有 `.openspec.yaml`（`schema: spec-driven` + `skip_specs: true`）加任意其他文件、没有 `proposal.md`、没有 `specs/`，`validate --all --strict` 通过（1.7.0 与 1.14.1 均已验证）。
3. **升级有代价**：用本仓库现有 45 个主规格做对照，1.7.0 严格校验全过；1.13.2 与 1.14.0 有 2 个主规格失败（Purpose 占位词警告）；1.14.1 有 20 个失败（需求文本超 500 字符被升级成警告）。`tools/check-openspec.node-test.mjs` 还断言版本恰为 `1.6.0`，升级必须同步改测试。
4. **其他可用的零升级出路**（均已在 1.6.0 与最新版上实验复现）：`openspec/changes/archive/` 下的目录与 `.` 开头的目录不参与 `validate --all`；`openspec archive <非变更目录>` 在 1.6.0 与 1.14.1 都能成功归档（带 `--yes`），不报错。自定义 schema（如官方 `rapid` 例子）不能豁免校验。
5. **三个同类工具都不靠关键词自动路由**，都是让用户在入口显式选，档位之间多为「原地切换且保留会话」（Kiro）或「按产物新开」（OpenSpec 官方建议范围爆炸时新开变更）。唯一接近「分类 + 默认从重」的是 OpenSpec 旧版（v0.15.0）`AGENTS.md` 的决策树，其兜底是「不确定 → 建 proposal（更安全）」。
6. **自定义项的发现方式**普遍是目录扫描（Kiro 的 `.kiro/agents/`、`.kiro/workflows/`；OpenSpec 的 `openspec/schemas/`）或安装时注册（Spec Kit 把扩展命令注册进代理集成），选择界面按来源分组列出。

## 2. Q1：OpenSpec 对非变更目录的处理

### 2.1 版本与依据

### 2.2 `validate --all --strict` 对非变更目录：判失败

**源码证据（1.6.0）**

- `dist/commands/validate.js`，`listChangeIds` 的注释原文：「Resolve change IDs by directory existence within the resolved root — the same rule `openspec status`/`instructions` use (`getAvailableChanges`) — rather than requiring `proposal.md`. This lets `validate` resolve a scaffolded or still-authoring change that the sibling commands already resolve (#1182).」
- `dist/commands/workflow/shared.js`，`getAvailableChanges`：「Returns the list of available change directory names under openspec/changes/. Excludes the archive directory and hidden directories.」实现为 `.filter((e) => e.isDirectory() && e.name !== 'archive' && !e.name.startsWith('.'))`。
- `dist/core/validation/validator.js`，`validateChangeDeltaSpecs` 末尾：`if (totalDeltas === 0) { issues.push({ level: 'ERROR', path: 'file', message: this.enrichTopLevelError('change', VALIDATION_MESSAGES.CHANGE_NO_DELTAS) }); }`；`constants.js` 中 `CHANGE_NO_DELTAS: 'Change must have at least one delta'`。变更校验只看 `specs/**/spec.md` 的 delta，不看 `proposal.md`、不看目录里的其他文件。
- 上游发行说明（CHANGELOG.md，1.6.0 小节）：「`validate` resolves changes like `status` — `openspec validate <change>` (and `--all`/`--changes` and the interactive selector) now resolves a change by directory existence, matching `status`/`instructions`, instead of requiring `proposal.md`. A scaffolded or still-authoring change is validated rather than reported as `Unknown item`, and a resolved-but-invalid change now exits non-zero.」（#1182）。URL：https://github.com/Fission-AI/OpenSpec/blob/main/CHANGELOG.md

**实验（1.6.0，临时目录 `scratchpad/osexp.kRs0ut`）**：建了 `real`（有 proposal + 合法 delta）、`lite`（只有 `notes.md`）、`empty-dir`（空目录）、`proposal-only`（只有 proposal.md）、`.hidden-lite`、`archive/`。`DO_NOT_TRACK=1 OPENSPEC_TELEMETRY=0 openspec validate --all --strict --no-interactive`：

- `✓ change/real`；`✗ change/empty-dir`、`✗ change/lite`、`✗ change/proposal-only`；`.hidden-lite` 与 `archive` 未出现在列表里；`Totals: 2 passed, 3 failed (5 items)`，退出码 1。
- `validate lite --strict --json` 的唯一错误：`Change must have at least one delta. No deltas found. Ensure your change has a specs/ directory ...`。
- 结论：**没有 `proposal.md` 与没有 delta 都判失败；有 `proposal.md` 但没有 delta 同样失败**。

### 2.4 `skip_specs: true`：1.7.0 引入，是官方唯一的「零 delta 合法」声明

- 引入版本：CHANGELOG 1.7.0 小节（PR #1399）原文：「Add `skip_specs: true` change metadata for work with no spec-level behavior change (pure refactors, tooling, docs). `openspec validate` accepts a zero-delta change that declares the marker (honored only when the metadata parses under the shared change-metadata schema and names a schema that loads) and errors when the marker and delta specs are both present, the artifact graph no longer blocks `tasks` on spec files for such changes, `openspec status` renders the specs stage as explicitly skipped, and the propose/specs guidance points to the marker instead of contradicting the validator.」
- 官方 CLI 文档（`docs/cli.md`，validate 小节）：「A change with zero spec deltas fails validation unless its `.openspec.yaml` declares `skip_specs: true` (for pure refactors, tooling, or docs work — see [Recipe 5](examples.md#recipe-5-a-refactor-with-no-behavior-change)).」URL：https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md
- 官方 `docs/cli.md`，archive 选项表：「`--skip-specs` | Skip spec updates for one archive run. A change that permanently has no spec deltas should declare `skip_specs: true` in its `.openspec.yaml` instead — it archives with no flag」
- 官方 `docs/concepts.md`：「`.openspec.yaml`        # Change metadata (optional): schema, created, skip_specs, retire_capabilities」。URL：https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md
- 实现（1.14.1 `dist/core/validation/validator.js`）：声明了标记且 `specs/` 下没有任何文件时，给 INFO `skip_specs is set in .openspec.yaml: change declares no spec-level behavior changes, zero deltas accepted`；声明了标记但 `specs/` 下有任何文件时给 ERROR `skip_specs is set in .openspec.yaml but spec files exist under specs/. Remove skip_specs or delete the delta spec files`；标记存在但元数据非法（例如 schema 名不存在）时 ERROR `skip_specs is set but .openspec.yaml is not valid change metadata, so the marker is not honored`，同时仍报零 delta。
- 严格模式对未知键的处理（1.14.0 起）：CHANGELOG 1.14.0 小节原文：「**Change metadata** — Warn when `.openspec.yaml` contains unrecognized keys such as `skip_design`. Those keys were stripped with no signal, so `status` still demanded the design artifact and `validate --strict` exited 0. `status`, `validate`, and `archive` now name the ignored keys; `validate --strict` fails.」已实验：1.14.1 下往 `.openspec.yaml` 加 `tenon_track: lite`，`validate --strict` 退出码 1（WARNING 被 strict 升级为失败）；已知键为 `schema, created, goal, affected_areas, initiative, skip_specs, retire_capabilities`（`dist/core/change-metadata/schema.js` 的 `CHANGE_METADATA_KNOWN_KEYS`）。**含义：若走该机制，`.openspec.yaml` 里不能夹带 Tenon 自己的字段（在 ≥1.14.0 且 strict 时）**。

**实验结果（`validate --all --strict --no-interactive`，目录 `lite-skip`：`.openspec.yaml` = `schema: spec-driven` + `skip_specs: true`，另有 `notes.md`，无 proposal、无 specs）**

- 1.7.0（`scratchpad/osexp3`）：`✓ change/lite-skip`，`Totals: 1 passed, 0 failed`，退出码 0。
- 1.14.1（`scratchpad/osexp2`）：`✓ change/lite-skip` 加一行 INFO，退出码 0；同目录下的 `proposal-only`、`empty-dir`、非法 schema 的 `lite-bad-schema`、与 `specs/` 冲突的 `lite-skip-conflict` 按预期判失败。
- 1.14.1 另测：带真实任务 `tasks.md`（复制自本仓库已归档任务 `2026-10-10-fix-hook-cross-session-isolation`）的 `skip_specs` 目录，`validate --strict` 通过；任务文件格式提示在测得的样本里没有被升级为失败（仅两个样本，不作普遍保证）。
- `openspec status --change lite-skip`（1.14.1）输出 `[~] specs (skipped: change declares skip_specs)`，`openspec list` 把该目录当变更列出（显示 `1/2 tasks`）。

### 2.6 `openspec archive <name>` 对非变更目录

**源码（1.6.0，`dist/core/archive.js`）**

- 只校验存在 delta 的变更：先扫描 `specs/<cap>/spec.md` 是否含 `## ADDED|MODIFIED|REMOVED|RENAMED Requirements`，`if (hasDeltaSpecs) { ... validateChangeDeltaSpecs ... }`；没有 delta 就不进校验分支，所以**零 delta 不会阻止归档**。
- `proposal.md` 校验被 `try { await fs.access(changeFile) ... } catch { // Change file doesn't exist, skip validation }` 包住，缺 `proposal.md` 直接跳过。
- 主规格更新：`findSpecUpdates(changeDir, mainSpecsDir)` 没有可更新项时不进入更新分支；`--skip-specs` 可显式跳过。
- 其余：未完成任务数 > 0 且没传 `--yes` 才会提示确认；否则 `fs.rename` 到 `openspec/changes/archive/<YYYY-MM-DD>-<name>`。

**实验**

- 1.6.0：`openspec archive lite --yes`（只有 `notes.md`）→ `Task status: No tasks`、`Change 'lite' archived as '2026-10-10-lite'.`，退出码 0；`archive .hidden-lite --yes --skip-specs --json` → `archivedAs: 2026-10-10-.hidden-lite`、`specsUpdated: false`，退出码 0（仅 CLI 指定名时可归档 `.` 开头目录；`validate --all` 仍会跳过它）。
- 1.14.1：`archive lite-skip --yes`（有 `skip_specs`、1/2 任务）→ 提示未完成任务后因 `--yes` 继续，归档成功；`archive empty-dir --yes`（无元数据的空目录）→ 归档成功。CHANGELOG 1.13.1 小节佐证：「`--no-validate` still archives as before, a change with no spec files still archives, and notes without delta sections under `specs/` are not affected.」
- 归档后目录进入 `archive/`，后续 `validate --all` 不再校验（`getAvailableChanges` 排除 `archive`；已实验）。

**注意（1.13.1 起）**：「名字空间目录」检测：`openspec/changes/<area>/<name>/` 这种嵌套被 `validate` / `archive` 识别并报错。判定一个目录「是变更而不是包装目录」的信号是根上有 `.openspec.yaml`、`proposal.md`、`tasks.md`、`design.md` 之一，或 `specs/` 下有文件，或自己有非 `.` 开头的普通文件（`dist/utils/nested-change.js`）。任务目录只要自己有文件（如 `tasks.md`）就不会被误判。

### 2.7 对 design.md 候选做法的证据映射（不替主线决策）

| 候选做法 | 已验证事实 | 代价 / 前提 |
| --- | --- | --- |
| A. 任务目录写 `.openspec.yaml`（`schema: spec-driven`、`skip_specs: true`） | 官方机制；1.7.0 与 1.14.1 都通过 strict；`archive` 无需旗标 | 钉死版本必须从 1.6.0 升到 ≥1.7.0 并改 `check-openspec.node-test.mjs`；只能放已知键（≥1.14.0 strict）；目录里不能有 `specs/` 下的任何文件；`schema` 必须是可加载的 schema 名。本仓库当前不写 `.openspec.yaml`（仓库内 grep 无结果） |
| B. `tools/check-openspec.mjs` 读任务状态过滤 | `validate --all --json` 的输出含 `items[].id / type / valid`（实验确认），`validate <id>` 可单点校验；1.6.0 即可用 | 需要自写过滤逻辑与对应单测；钉死版本不动。本条的「过滤实现可行」是基于上述输出结构的推断，未写实现验证 |
| C. 不治理的任务完结后移入 `openspec/changes/archive/` | 两个版本都排除 `archive/`，实验确认 | 与提案里「完结时提交但不移入 archive」冲突；进行中阶段该目录仍在 `changes/` 下（CI 只看最终提交树时可能无影响，需主线确认 CI 对象） |
| D. 目录名以 `.` 开头 | 两个版本都排除 | 任务路径 `openspec/changes/<c>/` 被本仓库多处写死（提案已述）；1.14.1 的 `validateChangeName` 注释写明查找会拒绝 `getAvailableChanges` 排除的名字（隐藏目录、archive），即 OpenSpec 自家命令无法按名定位 |
| E. 目录移到 `openspec/changes/` 之外 | `changesDir` 写死，OpenSpec 不扫描别处 | 迁移成本最大（路径写死处很多） |
| F. 靠 schema 选择豁免 | 实验证明不行 | 不可行 |

## 3. Q2：同类工具如何在一个工作流里表达轻重档、路由与升级

### 3.1 GitHub Spec Kit

**轻重档的表达：没有「同一工作流里的轻量轨道」，而是文档推荐的两条路径，加上几个独立的具名工作流。**

- 官方 quickstart（https://github.com/github/spec-kit/blob/main/docs/quickstart.md）原文：「After installing Spec Kit, each skill below is a step in the process. Two paths are common:」「**Shorter path** — for smaller features:」`/speckit-specify`、`/speckit-plan`、`/speckit-tasks`、`/speckit-implement`、`/speckit-converge`；「**Full path** — for production features, adding `/speckit-clarify`, `/speckit-checklist`, and `/speckit-analyze` as quality gates:」。
- 内置具名工作流（仓库 `workflows/` 目录有 `speckit`、`bugfix`、`assess`）。`workflows/bugfix/workflow.yml`：`name: "Guided Bug Fix"`，`description: "Runs bug assess → human review gate → bug fix → bug test on a bug report"`，步骤 id 依次为 `assess`、`review-assessment`（`type: gate`，`on_reject: abort`）、`fix`、`test`。全量工作流 `speckit`（`name: "Full SDD Cycle"`）：`specify → review-spec(gate) → plan → review-plan(gate) → tasks → implement`（https://github.com/github/spec-kit/blob/main/docs/reference/workflows.md）。可见「轻量档」的步骤数与评审门数都比全量档少（bugfix 一个门，speckit 两个门），与 Tenon 的 standard（一个评审门）结构相近。
- 单个工作流内部可以分支：官方步骤类型表有 `if`（「Conditional branching (then/else)」）与 `switch`（「Multi-branch dispatch on an expression」）。

**路由：让用户显式选**。文档只写用户该选哪条路径 / 调哪个命令，未发现自动路由器（关键词或分类）。官方 reference 概览（https://github.com/github/spec-kit/blob/main/docs/reference/overview.md）：「For guided examples, start with [SDD](../quickstart.md), [bug fixing](../guides/bugfix.md), or [idea assessment](../guides/assessment.md).」quickstart 开头：「Use SDD to build a feature or application from a specification. For a repair, follow the [bug-fixing quickstart](guides/bugfix.md); ... These are independent processes, not prerequisites for this guide.」

**升级**：未找到。文档没有「轻量路径超范围时怎么升级到全量路径」的描述；`docs/concepts/complex-features.md` 讲的是上下文耗尽后的「分批执行 / 子代理 / 拆成多个小 spec（spec of specs）」，属于拆分而非换档。

### 3.2 OpenSpec 自身

**轻重档的表达有三层，都是用户配置 / 选择：**

1. 命令集合档位：`docs/workflows.md`（https://github.com/Fission-AI/OpenSpec/blob/main/docs/workflows.md）「### Default Quick Path (`core` profile)」：`/opsx:explore`、`/opsx:propose`、`/opsx:apply`、`/opsx:update`、`/opsx:sync`、`/opsx:archive`；「### Expanded/Full Workflow (custom selection)」加上 `/opsx:new`、`/opsx:continue`、`/opsx:ff`、`/opsx:verify`、`/opsx:bulk-archive`、`/opsx:onboard`，启用方式 `openspec config profile` + `openspec update`。
2. schema 档位：`docs/customization.md`（https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md）给了「Rapid Iteration Workflow」示例 schema `rapid`：「A minimal workflow for quick iterations」，artifacts 只有 `proposal` 与 `tasks`。选择顺序原文：「1. CLI flag: `--schema <name>` 2. Change metadata (`.openspec.yaml` in the change folder) 3. Project config (`openspec/config.yaml`) 4. Default (`spec-driven`)」。
3. 变更级声明：`skip_specs: true`（见 2.4）。

**路由：用户显式选**（`openspec new change <name> --schema <name>`，帮助原文 `--schema <name>  Workflow schema to use (default: spec-driven)`）。文档未发现自动路由。
**旧版 v0.15.0 `openspec/AGENTS.md`（已不在现行 1.6.0 / 1.14.1 包里，grep 无结果；仅作历史参照）**有一个由代理执行的判定：「Loose matching guidance: - Contains one of: `proposal`, `change`, `spec` - With one of: `create`, `plan`, `make`, `start`, `help`」，以及「Skip proposal for: - Bug fixes (restore intended behavior) - Typos, formatting, comments - Dependency updates (non-breaking) - Configuration changes - Tests for existing behavior」，决策树：「├─ Bug fix restoring spec behavior? → Fix directly ├─ Typo/format/comment? → Fix directly ├─ New feature/capability? → Create proposal ├─ Breaking change? → Create proposal ├─ Architecture change? → Create proposal └─ Unclear? → Create proposal (safer)」。URL：https://github.com/Fission-AI/OpenSpec/blob/v0.15.0/openspec/AGENTS.md 。要点：**错字级请求直接修、不建变更；不确定时默认走重**。

**升级 / 超范围**：`docs/workflows.md`「### When to Update vs Start Fresh」原文：「**Update the existing change when:** - Same intent, refined execution - Scope narrows (MVP first, rest later) ...」「**Start a new change when:** - Intent fundamentally changed - Scope exploded to different work entirely - Original change can be marked "done" standalone - Patches would confuse more than clarify」，并有示例「"Need to also support custom themes" → New change (scope exploded)」。即**范围爆炸 = 新开变更**，不是原地换档。是否能原地改已有变更的 schema：官方文档未找到专门说明（只有解析顺序里写了「Change metadata」）。

### 3.3 Kiro

当前官方文档（2026-10 抓取；各页页脚更新日期：specs 2026-10-02，plan 2026-10-10，workflows 2026-10-09，quick-spec 2026-08-04）的档位是一个由轻到重的阶梯：**Default 代理（普通聊天）→ Plan → Quick Spec → Spec（Feature：Requirements-First / Design-First）→ Bugfix**。

- 内置工作流清单（https://kiro.dev/docs/ide/chat/）原文：「Built-in workflow | Description」「Spec | Structured feature development — generates requirements, design, and tasks」「Plan | Plan-only mode — breaks ideas into an implementation plan without making changes」「Bug Fix | Structured bug-fix workflow — investigate, diagnose, and resolve bugs」「Quick Spec | Fast spec workflow — clarify, then auto-generate requirements, design, and tasks」「Selecting a built-in workflow is optional. If you skip it, the session uses the **Default** agent for general coding assistance.」
- 轻重档的选择指引：Plan 页（https://kiro.dev/docs/specs/plan/）原文：「For well-defined features that need formal requirements and design documents, use Feature Specs instead. For quick, well-understood changes, skip planning and work directly with the default agent.」「Use Plan mode for tasks that need 15–60 minutes of implementation - long enough to benefit from planning, short enough that formal specs would be overkill」。对照表：Plan mode「Best for: Medium complexity, explore-then-build」，Feature Specs「High complexity, team collaboration, audit trail」。
- Quick Spec 页（https://kiro.dev/docs/specs/quick-spec/）原文：「Quick Spec is a session mode that auto-generates requirements, design, and tasks in a single pass. Instead of approving each phase before the next begins, you answer clarifying questions up front」；对比 Vibe：「Vibe mode is conversational and unstructured - there are no artifacts saved to `.kiro/specs/`. Quick Spec still produces the full Spec artifacts (requirements, design, tasks), just without approval gates between phases.」
- 步骤：Spec 的三阶段固定为「Requirements or Bug Analysis → Design → Tasks」，Bugfix 把第一阶段换成 `bugfix.md`（「Bug analysis with current/expected/unchanged behavior」）（https://kiro.dev/docs/specs/）。轻量的 Quick Spec 产物与完整 Spec 相同，只去掉阶段间审批门；Plan 不产出文档。

**路由：用户选，无关键词路由**。
- 入口选择：「Choose **Plan** from the workflow options on the "Let's build" screen when starting a new session. To switch mid-session, click the agent name in the bottom bar of the chat input and select **Plan** from the agent picker.」Specs 页入口：「Kiro will ask if you are developing a Feature or fixing a Bug」。
- 唯一的自动判定是信息 vs 动作：「Smart intent detection: Kiro intelligently analyzes your messages to understand whether you want information or action.」不涉及选档。

**切换：原地切换，保留会话**。ide/chat 页「Switching agents mid-session」原文：「Select an agent to switch the session to that agent's configuration. The switch takes effect immediately for your next message.」「Conversation history | Preserved. The agent sees prior messages」「The agent selector is disabled while the agent is actively executing a multi-step workflow. You can only switch agents when the agent is idle and waiting for your next message.」Quick Spec → Feature Spec：「There's no explicit mode switch, but the artifacts are identical in format to a standard Feature Spec - you can continue working with them using any Spec workflow」。

**升级判断**：文档只有人读的指引，如 Quick Spec 页「Should I use Quick Spec for complex features? Use your judgment. For features where requirements quality is critical - compliance-sensitive domains, high-stakes systems, unfamiliar territory - a standard Feature Spec with explicit review gates is usually the better fit.」

**术语漂移（证据冲突，已如实记录）**：用户口中的「vibe 模式」在旧版 Kiro 文档里是会话选择器里的「Vibe / Spec」两种会话；`https://kiro.dev/docs/chat/vibe/` 现在只剩一行跳转（「This page has moved to /docs/ide/setup/」）。当前文档把普通聊天叫 **Default 代理**，「Vibe」只在 Quick Spec 页的 FAQ 里作为对照词出现。搜索结果摘要里提到旧版「session picker」的说法属于二手摘录，没有取到一手原文，不作证据。

## 4. Q3：自定义工作流 / 模板如何被路由或选择界面发现

- **Kiro**：代理选择器按来源分组，原文：「available agents are grouped by source: **Built-in** — Default, Spec, Quick Spec, Bug Fix, Plan; **User** — Custom agents from `~/.kiro/agents/`; **Workspace** — Custom agents from `.kiro/agents/` in your project」（https://kiro.dev/docs/ide/chat/）。同名冲突：「When both locations have agents with the same name, workspace agents take precedence.」（https://kiro.dev/docs/custom-agents/）。声明式工作流配方（recipe）：「Recipes can come from your workspace (`.kiro/workflows/`), your user configuration, recipes synchronized for your account, or the set bundled with Kiro; a valid recipe in a higher tier wins when names collide.」（https://kiro.dev/docs/workflows/）。注意：「Let's build」屏幕只列内置工作流（「Selecting a built-in workflow is optional」），自定义代理在会话内的选择器里出现；官方还明说「Workflows are distinct from the built-in workflow choices shown when you start an IDE session」。发现方式 = 目录扫描，无注册步骤；工作区代理「loaded only if the workspace is trusted」。
- **Spec Kit**：安装时注册。`docs/reference/extensions.md`（https://github.com/github/spec-kit/blob/main/docs/reference/extensions.md）原文：「Extension commands are registered with the active AI coding agent integration.」工作流用 `specify workflow list`（「Lists workflows installed in the current project.」）、`specify workflow search`（跨目录搜索）、`specify workflow add <source>`（安装到 `.specify/workflows/<id>/`）。想改内置工作流不必改安装件：项目覆盖层放 `.specify/workflows/overlays/<id>/*.yml`（`insert_after` / `insert_before` / `replace` / `remove` 四种编辑，按步骤 id 锚定）。目录来源与信任：「Catalogs are resolved in this order (first match wins)」，社区目录默认只可发现、不可直接安装（`install_allowed: false`）。
- **OpenSpec**：schema 目录扫描，无注册步骤。`docs/customization.md`：「Custom schemas live in your project's `openspec/schemas/` directory and are version-controlled with your code.」另有用户级目录 `~/.local/share/openspec/schemas/`；`openspec schema which --all` 列出全部并标注来源（「whether it's from your project, user directory, or the package」）。本次在 1.14.1 实验：项目里放 `openspec/schemas/rapid/schema.yaml` 后，`openspec schemas` 立即输出 `rapid (project)` 与 `Artifacts: proposal → tasks`，无需任何注册。选用仍是显式的（`--schema` 或 `config.yaml`）。
- 共性（事实归纳，非结论）：被调查的三家里，没有一家靠关键词路由去「发现」自定义项；发现靠目录 / 安装注册，选择靠用户在列表里点选或写名字，且自定义项与内置项并排出现在同一个列表里（Kiro 分组、OpenSpec `openspec schemas`、Spec Kit `workflow list`）。
