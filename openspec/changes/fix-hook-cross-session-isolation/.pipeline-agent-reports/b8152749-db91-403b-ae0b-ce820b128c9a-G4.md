## 0. 与派发说明不一致的一处（请主线先看）

派发说明里「当前步骤**声明了**回规格的边时给直接命令 `tenon transition <c> <该事件>`」这一支**我没有实现**，因为它在 kernel 现行语义下不成立，实现了就是再造一条必然失败的指令：

1. 计数口径（kernel `currentRound`）：只有落到**早于本步所有回退目标**的步骤才清零。受约束步骤自己声明的每条回退边，其目标本身就是它的回退目标，所以「目标早于本步所有回退目标的边」在当前步骤上恒为空集；落到那个目标不会清零。
2. 强制层（`rejectOnRoundsExhausted`）：用完后受约束步骤上「既不是前进边也不是放弃边」的边一律被拒，自己声明的回 spec 的边也一样。
3. 实证：`packages/cli/src/review-residual.integration.test.ts` 新增用例「verify 自己声明了回 spec 的边」——真 CLI、真落盘：verify 上再声明 `rework-spec -> spec`，用完后 `status` 的 `exits` 里它 `ready:false` 带 `rounds-exhausted`，`tenon transition <c> rework-spec` exit 1（`2/2`），任务仍在 verify；`next` 的第 2 条出路不含任何 `tenon transition <c> rework-spec`。另有单测 `statusStepRoundsRoute.test.ts` 的最后一例用 kernel 的 `currentRound` / `stepBackTargets` 证明落到自己声明的 spec 边不清零（计数仍是 2）。

所以真实路径恒为两步，不分「直达 / 不直达」：用户先调高上限 -> 经回退边回到回退目标步骤 -> 在**那一步**上执行落到更早步骤的边。我按此实现；同时处理了两种计划里确实会出现的变体（见 1.1）。如果主线仍想要「直达命令」那一支，需要先改 kernel 的清零口径或强制层，这超出本组「不改计数口径」的约束。

## 1. 改动

### 1.1 代码（packages/cli/src）

- `commands/statusStepRoundsRoute.ts`（新，纯函数）：`roundsRoute(plan, stepId)` 算出 `RoundsRoute = { back, reset, resettable }`。`back` = 本步第一条（非放弃）回退边中，其目标步骤上有落到更早步骤的边的那条（找不到就取第一条回退边）；`reset` = 回退目标步骤上目标早于本步所有回退目标的边（`stepBackTargets` + 步骤序，放弃边 `scope-expanded` 除外）；`resettable` = 工作流里有早于所有回退目标的步骤。不受约束的步骤返回 null。

- 点名事件：`经 requirements-changed 回到 spec 重新规划：当前步骤上没有直达这条路的边（用完后它的回退边也被拒），要分两步，第一步同样要用户先决定调高上限——先由用户定 N（须大于 2），执行 tenon set demo max_rounds <N>，调高后重读 next，经回退边 verify-fail 回到 build；再在 build 上执行 tenon transition demo requirements-changed 回到 spec，回到规格后验证轮次重新计数，用户可以再把 max_rounds 调回去`

强制层拒绝文案（zh）：`……或回到规格重新规划（当前步骤没有直达的边：要先调高上限，经回退边回到回退目标步骤，再在那一步上执行回到规格的事件，回到规格后验证轮次重新计数）；或终止任务……`；en：`or go back to the spec to re-plan (this step has no direct edge for that: raise the limit first, take a back edge to the step it points to, then run the event that returns to the spec on that step; the verification rounds are counted again once the spec is reached); or end the task`。
