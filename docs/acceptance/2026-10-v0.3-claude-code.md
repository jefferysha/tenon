## 2. 信任授权方式

v0.3 的 `tenon test run` 在这台机器上第一次执行目录和任务内联测试的命令之前，要求用户本人在自己的终端里运行 `tenon test trust`。本次验收里 agent 自己做不到这一步，也不该做到；这里写清楚信任是怎么给出的。

**hook 拦住了直接调用，行为正确。** 我（验收执行者，运行在装有 `tenon@tenon` 插件的 Claude Code 里）直接运行 `tenon test trust fix-last-items-off-by-one` 被 PreToolUse 门拒绝，连 `tenon test trust --help` 也被拒：「测试命令的信任只能由你本人在自己的终端里给出（tenon test trust）；CI 由运行器设置 TENON_TEST_TRUST=1，agent 不能替你确认」。只读的 `--status` 形式没有被拒（它只列出摘要和是否已信任）。这与 `docs/usage/security-model.md`、`cli-reference.md` 的描述一致。验收中的 Claude Code 会话也一样：它们走到 `run-tests` 时都如实停下来，请用户在自己的终端里运行 `tenon test trust`，没有自己运行，也没有设置 `TENON_TEST_TRUST`。全部被拒的调用和原文见 `$EV/hook-refusals.txt`。

**信任是编排者在用户明确指示下，用 wrapper 脚本给出的。** 据编排者转述，用户在 2026-10-06 明确授权编排者代为执行（原话：「你自己执行啊 还有哪些没执行的全部执行」；我没有直接看到这句话）。编排者用 `$EV` 下的两个脚本完成：`grant-trust.sh <演示项目根目录> <change>`（只接受 `~/tenon-accept-v03/` 下的路径，内部 `exec tenon test trust "$@" --yes`）和 `trust-status.sh`（`tenon test trust <change> --status --json`）。脚本文本里不含 hook 拦截的字面串，所以没有被拦。验收执行者没有运行这些 wrapper：遇到信任提示时它先停下来交回编排者，由编排者读过命令清单后授权。这恰好演示了 `docs/usage/security-model.md`「Residual risk」一段写明的残余风险：拥有用户权限的进程可以「build a path the hook cannot parse」，该文件的其他段落也写明 hook 的匹配是静态的、尽力而为的。这里不是产品缺陷，记为信息级发现 F10。

两次授权的命令清单：

| Change | 授权时间（CST，约） | 授权前状态 | 被信任的命令 | 授权后 |

**记录篡改的 wrapper 被另一道守卫拦下。** 场景 6 里要在副本上篡改一条已提交的测试记录（改一个字节、删一条记录）。守卫不只匹配命令行，还会检查被调用的脚本：我的两份脚本和一次对副本记录的 Edit，以及编排者的 `bash s6-tamper-record.sh`，都因为脚本里有对测试记录路径的写入被拒（「测试记录与基线只能由 tenon test run / tenon test baseline 写入...」），即使目标只是 `$EV` 下的临时副本。我们没有再绕这第二道守卫。这两处守卫结合起来的结论：同样是 wrapper，对信任命令没有拦住（残余风险），对写记录路径的脚本拦住了（过严，见 F9）。篡改检测改由自动化测试覆盖，见场景 6。

摩擦点（按用户的感受记录）：

- 首次信任要人在终端：这是设计，但对全程无头的验收来说是硬停点，等了 3 小时 24 分。
- 评审门之外有 5 次纯「继续」（open → explore、explore 的对话技能之间、build → verify、ship → archive 两次），会话在 interactive 模式下每次转换前都停下来展示产出。

## 5. 问题清单

严重度：blocker 阻断发布；high 主路径失败且无合理绕过；medium 功能缺陷或与文档不符，有绕过；low 体验、文档或小瑕疵（含信息级）。本次没有 blocker、high。

### 5.1 medium

**F1（medium）`verify --ci` 的候选比对把 git 忽略的 `.claude/settings.local.json` 算进工作区，报错文案还指错了原因**
- 现象：干净克隆上 `tenon verify --ci --change fix-last-items-off-by-one` 退出 2，`candidate-mismatch`，消息说候选代码「在记录完成之后提交改动过：src/cart.js, test/cart.test.js」。实际原因是作者的工作区里有一个 git 忽略的 `.claude/settings.local.json`（我加的 hook 配置），克隆里没有它；把这一个文件拷进克隆，同一命令退出 0。`src/cart.js` 和 `test/cart.test.js` 只是被交付提交一并提交，并没有在测试之后被改过。
- 影响：Claude Code 会在项目里自己写 `.claude/settings.local.json`（允许列表等），它通常被 git 忽略，所以每个用 Claude Code 的项目都会在 CI 上撞到这个，而且提示指向错误的文件，很难自己查出来。`docs/usage/ci-verification.md` 把「git 忽略的构建输出」列为一类原因，但没有提到这个宿主文件。
- 证据：`$EV/s6/out-ok/change-text-en.out`（失败）、`$EV/s6/out-pass/change-text-en.out`（拷入该文件后通过）、`$EV/s6/out-ok/change-sarif-en.out`；`packages/kernel/src/workspace/fingerprint.ts` 只排除 `.claude/agents`（含只包着它的 `.claude/` 空壳）、`.github/hooks` 和 `.pipeline-owned.json`，`.claude/settings.local.json` 不在其中；另一个旁证是探针项目里同一个文件让已记录的评审者结论变成「过期」（截图 6）。
- 建议修法：把 `.claude/settings.local.json`（以及其他宿主本地配置，如 `.codex/` 已排除的同类）加进候选排除列表；同时让 `candidate-mismatch` 的消息列出「检出树里多了或少了哪些路径」，而不是「记录之后提交过的文件」。

**F2（medium）被放弃的 standard 任务（`escalated`）会让 `verify --ci` 在带升级链的 PR 上失败**
- 现象：1B 的升级链把 `add-format-price`（`escalated`，没有运行记录，按文档 `scope-expanded` 是「放弃边，不需要任何测试证据」）随新任务的交付提交一起入库。在归档提交 `8558374` 的克隆里：交付的 `format-price-default` 通过，但 `--change add-format-price` 退出 2（`test-file-unregistered`、两个 `test-not-run`），`--since 0edf81f`（承载这条链的 PR）整体退出 2，3 个错误全来自被放弃的任务。
- 影响：按推荐路径升级一次的项目，之后每个选中这个任务的 CI 都会失败，只能手动归档/删除任务或不用 `--since`。
- 证据：`$EV/s6/out-escalated-at-archive.txt`、`$EV/s1/escalation.log`。
- 建议修法：`verify --ci` 对终态为 `escalated` 的任务按 abandon 处理（跳过或只给 note），或让 `scope-expanded` 的后续步骤提示归档/删除被放弃的任务；同时 `escalate.then` 的文案可以加上这一步。

### 11.6 缺口 5：`tenon update` 然后回滚

`tools/runtime-update-rollback-acceptance.mjs`（`node tools/runtime-update-rollback-acceptance.mjs`）：像 `npm run test:clean-install` 一样，在隔离的 HOME / `CODEX_HOME` / 运行时和随机 Dashboard 端口里用本地 git 发布夹具跑 `install.sh --codex`，然后走更新与回滚，每一步之后重读 `runtime status --json` 与 `doctor --json`（前三步还核对 Dashboard 健康身份）。`tenon update` 用 Node 的 `fetch` 问 GitHub 的 latest release；脚本用 `NODE_OPTIONS=--import` 的预载只替换这一个 URL 的应答，所以不依赖公开的 latest 恰好等于检出的版本。技能安装仍要克隆上游仓库，需要网络。

实际输出（脚本跑过 4 次，每次都是前三步通过、第四步以同一条错误失败；`<A>`、`<B>` 是内容寻址的 release id）：

```text
{"step":"1 install (build A)","active":"<A>","previous":null,"revision":1,"activeValid":true,"previousValid":false,"lastAudit":"activated","doctor":{"green":21,"yellow":6,"red":0}}
{"step":"2 tenon update --codex (same build)","active":"<A>","previous":null,"revision":1,...,"doctor":{"green":21,"yellow":6,"red":0},"updateExit":0}
{"step":"3 tenon update --codex (newer build)","active":"<B>","previous":"<A>","revision":2,"activeValid":true,"previousValid":true,...,"doctor":{"green":21,"yellow":6,"red":0},"updateExit":0}

```

- 步骤 1：安装通过，没有上一份 release，doctor 没有红灯，Dashboard 身份与 active release 一致。
- 步骤 2：同一个构建再 `tenon update --codex`，退出 0，「已在宿主、managed runtime 与 Dashboard 精确生效；无需更新」，release id 与 Dashboard 进程都没变，仍然没有上一份 release。
- 步骤 3：构建 B（同一个稳定标签，CLI bundle 多了几个字节）发布到本地发布夹具后再 `tenon update --codex`：退出 0，active 换成 B，上一份是 A 且两份都有效，doctor 没有红灯，Dashboard 换成新进程并与 B 一致。
- 步骤 4：`tenon runtime repair --rollback` 退出 1，**见 F18**。

F18 的后续状态（保留夹具查得，随后删除）：`tenon runtime status` 读到 active = A、previous = B、revision 3，两份都有效，`doctor` 只多一个红灯 `identity:release`——看上去像回滚成功；但 `managed-release-transaction/runtime-rollback.json` 还在，再跑一次 `tenon runtime repair --rollback` 同样拒绝，`tenon update --codex` 与 `tenon setup --codex --yes` 都以「存在未完成的 runtime rollback；请先重跑 tenon runtime repair --rollback」拒绝。

根因（在夹具里验证过）：安装器写的启动器（`packages/cli/src/runtime/launchers.ts`）带一行 `export TENON_NODE_PATH=…`，回滚由 `runtime/tenon-bootstrap.mjs` 自己处理，它自己的启动器生成器（`stableLauncherText`）没有这一行；`convergeRollbackLauncher` 比较「磁盘上的启动器」与自己生成的内容，既不相等、也不是 legacy、也不是缺失，就把它当作第三方检查点拒绝。拒绝发生在选择文件已经翻转之后。在夹具里把这一行补进已安装的 `active.mjs` 副本后，同一条 `tenon runtime repair --rollback` 退出 0，`runtime status` 仍是 active = A、previous = B。仓库里补同一行，`bootstrap.test.ts` 的其余 32 例全部通过，下面的回归测试随之翻转（随后已还原这处改动）。v0.2.1 与 v0.3.1 的启动器生成器与 bootstrap 都是这种不一致。

自动化：`packages/cli/src/runtime/bootstrap.test.ts` 新增一例，从安装器的 `writeStableLaunchers` 写出的启动器出发跑 bootstrap 回滚（已有的回滚测试都从没有启动器、或 bootstrap 自己写的启动器出发，所以一直没碰到）。它现在用 `it.fails` 标记，套件保持绿；去掉 `.fails` 即变成这个缺陷的回归测试（单独当普通用例跑时，报错就是上面那一行拒绝）。

另一个观察 F20：回滚成功之后（夹具里补过那一行再跑），`tenon doctor` 有一个红灯 `identity:release`（发布身份漂移：宿主插件仍是 B，runtime 是 A），它给出的修复是 `tenon update --codex`——那会把回滚再前滚回去。`docs/usage/updates-recovery-and-uninstall.md` 没有提这个红灯。

### 11.8 新发现

严重度定义同第 5 节。

**F18（high）`tenon runtime repair --rollback` 在正常安装 + 更新之后必然失败，并让回滚、更新、`setup` 全部卡死**
- 现象：见 11.6。更新到较新的构建之后跑文档里的回滚命令：退出 1，`rollback refuses a third-party launcher checkpoint: tenon`；此时 `runtime status` 已经显示回滚成功，但回滚日志没清掉，之后 `tenon runtime repair --rollback`、`tenon update`、`tenon setup` 都因「存在未完成的 runtime rollback」拒绝。
- 影响：`docs/usage/updates-recovery-and-uninstall.md` 把它写成唯一的精确回滚，并写「v0.3 写的数据 v0.2.1 都读得了，可以用它回滚」。按文档操作的用户会进入没有 CLI 出路的状态（只能手工清日志与启动器）。v0.2.1、v0.3.1 的两处生成器都是这种不一致。
- 证据：`tools/runtime-update-rollback-acceptance.mjs` 的输出（11.6）；`packages/cli/src/runtime/bootstrap.test.ts` 新增的 `it.fails` 一例；`runtime/tenon-bootstrap.mjs` 的 `stableLauncherText` 与 `packages/cli/src/runtime/launchers.ts` 的 `launcherText` 对比。
- 建议修法：让 bootstrap 的启动器生成器写出与安装器完全一致的 `export TENON_NODE_PATH=…` 行（非 legacy 形态），并把 `it.fails` 改成普通 `it`；同时让拒绝发生在翻转选择文件之前，或让失败的回滚回到翻转前，避免半截状态。**建议在 v0.3.2 里修，发布前用 `node tools/runtime-update-rollback-acceptance.mjs` 在真机上复验。**

**F19（medium）任务起点之前就已提交、还没批准的 `not_applicable` 声明：评审批准之后，出口被它自己的目录改写卡死**
- 现象：目录里已提交 `not_applicable: [{kind: typecheck, …, approved_by: null}]`，步骤策略要求 `typecheck`；起一个任务、`review request`、`review acknowledge`：批准把 `approved_by` 写回目录，这个改写相对任务起点是受保护文件的新改动，没有批准行；`tenon test status` 与 `tenon transition` 报 `protected-file-unapproved` 并提示再 `tenon review request`，而 `review request` 拒绝（「已获确认；请直接执行该 transition，不能重复 request」）。手改回 `approved_by: null` 也一样。CI 的 `verify --ci` 同样报 `protected-unapproved`。
- 影响：只有「声明先于任务、没批准就提交」时才会走到（文档里的流程是任务里声明并一次批准，那条路径通过，见 11.7）；走到之后没有 CLI 出路。
- 证据：调试用例（没有留在仓库里）：在基线提交的目录里直接写声明，任务里 `review request` + `review acknowledge`，再 `test status` / `transition` / `review request`。
- 建议修法：批准写回 `approved_by` 时一并记录该目录新内容的受保护批准行，或者让受保护文件的判定把 Tenon 自己的 `approved_by` 写回排除在外。

**F20（low）回滚之后 `tenon doctor` 有红灯 `identity:release`，建议的修复会撤销回滚**
- 现象与影响：见 11.6。回滚只换 runtime，宿主插件仍是较新的构建，身份检查按设计报漂移；文档没有提，提示的 `tenon update --codex` 把回滚前滚回去。
- 建议：文档在回滚一节说明这个红灯，或让 doctor 在刚回滚时给出区别于更新漂移的提示。

**F21（low）composite action 的失败路径只有静态检查**
- 现象：「`exit-code != 0` 时让作业失败」这一步无法在工作流里以「期望失败」的方式验证而不引入步骤失败也算过的开关；`tampered` 作业因此绕开它直接跑 `run.sh`。
- 影响：这一步的接线靠 `verify-action.integration.test.ts` 的静态断言保护；要真正端到端覆盖，需要另一个工作流 dispatch 它并读取结论。

F18 的影响范围后来也核实过：F18 提到的「v0.2.1、v0.3.1 的两处生成器都是这种不一致」其实更早就是如此，两份文件在本仓库的根提交（`4073e547`）里就已经不一致，所以第一个发布标签 v0.1.0 起每个版本都会被卡住。用各标签自己的 CLI 在隔离的 HOME 里走 install、`tenon update`、`tenon runtime repair --rollback`（`tools/runtime-update-rollback-acceptance.mjs` 的卡死场景，把被卡版本换成对应标签），v0.1.0、v0.1.10、v0.2.0、v0.2.1、v0.3.0 都以 `rollback refuses a third-party launcher checkpoint: tenon` 退出 1、选择已翻转、回滚日志留下；v0.3.1 由上面的验收脚本在 CI 里覆盖。其余标签只做了静态对照：每个标签的 bootstrap 都没有 `export TENON_NODE_PATH=`、都带「third-party launcher checkpoint」拒绝，安装器的 `launchers.ts` 都有这一行。另外，从 v0.3.1 用 `tenon update` 更新到包含修复的 release 之后，`tenon runtime repair --rollback` 退出 0、回滚日志不留、launcher 一对逐字节不变，之后的 `tenon update` 回到较新的 release（一次性验证，没有进验收脚本）。

评审之后补上的三处加固：
- **锁的同一性。** 收尾遗留回滚日志的 `settlePendingRollback` 在 `<managedTransactionRoot>/.pipeline.lock`（`withExclusiveRuntimeTransaction`）里运行；bootstrap 的回滚先拿同一个目录作外层锁，再拿 `<stateRoot>/.pipeline.lock`（release store 的锁）作内层，所有写选择与日志的人都是「先外后内」，互斥且不会死锁。`bootstrap.test.ts` 用测试专用的暂停点（`TENON_TEST_ROLLBACK_PAUSE_AFTER_JOURNAL`，没设置时无效）把真实的 bootstrap 进程停在「日志已落盘、选择还没翻转」，断言两个锁目录的名字、并发的 setup 事务进不来且日志与选择不动、回滚结束后 setup 才进入并看到翻转了一次、日志已被回滚自己删掉；把外层锁指到别处该测试即失败。
- **私有启动器副本。** 丢弃「选择从未翻转」的日志时，同事务 id 的 `<launcher>.tenon-rollback-<id>.previous` 在与日志记录的检查点逐字节、逐权限位相同时一并删除；内容、权限位或事务 id 不同的留下；启动器本身已不在时，匹配的副本先放回启动器路径再删（它是唯一剩下的原件）。
- **F19 的检查到写入之间。** `updateCatalog` 新增在目录锁内、读目录之前运行的 `observe`；批准先取目录摘要、再查 diff，同步的 `mutate` 紧贴写盘再核对摘要，不符就拒绝整次批准（什么都不批准、不写、不封存，同一条确认可以重试）。测试模拟检查期间落盘的手改。
