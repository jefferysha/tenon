# 推荐方案：按任务节点约定交付，按调用实例绑定，按运行证据验收

日期：2026-09-11。状态：设计推荐，尚未实现或做运行基准测试。依据：7 个真实 skill 的[抽样审计](/Users/a1234/Documents/code-manager/projects/tenon-local/docs/research/2026-09-11-skill-io-sample-audit.md)、当前 Tenon 静态代码，以及下文一手协议资料。

**已被后续方案调整（2026-09-12）：**用户明确编排 UI 只负责操作，不与模型协商文件 I/O。当前推荐见[工作流编排与执行期产物管理](/Users/a1234/Documents/code-manager/projects/tenon-local/docs/research/2026-09-12-runtime-artifact-lineage-and-workflow-ui.md)。本文要求节点在编排/准备时补齐交付文件的部分不再作为默认前提；实例绑定、版本证据与业务完成条件仍供新方案参考。以下保留历史推导，不作为当前实现规格。

## 1. 选择与理由

**选择：workflow 节点拥有交付要求，准备阶段将其绑定为本次执行契约，执行器负责接收产物和控制完成；skill 提供执行指令与可提取的约束。**

关键变化是：不再要求先破解所有现成 skill 的完整语义，才能构建 workflow。对于能够独立调度和验收的 skill，可以建立单独节点；对于 frontend-design 一类持续指导行为的 skill，将它记录为节点使用的方法，不虚构单独的输入输出和结束时刻。

| 候选方式 | 能解决的部分 | 不选作主方案的原因 |
| --- | --- | --- |
| 安装时扫描文本、路径或文件变化 | 技能发现、线索提取、候选产物发现 | 无法可靠区分条件输出、临时文件、原有输入、其他执行的写入与最终结果 |
| 安装时让模型完整解析每个 skill | 提取自然语言条件与候选约束 | 对未使用技能付费；缺失任务信息仍不存在；模型提取不能证明执行会遵守 |
| 所有 skill 必须增加统一 manifest | 自研、可治理技能的长期接口质量 | 第三方存量不具备；多轮和组合技能仍需要实例化；只能作为可选增强 |
| 节点交付要求 + 按需准备 + 受控提交 | 已有技能、动态工作流、提前预览和验收共用同一执行计划 | 需要新增执行边界与产物协议；语义不清的任务仍有准备成本。综合当前需求推荐 |

## 2. 输入输出究竟由谁定义

输入输出需要区分三类来源，保留每条约束的来源及适用条件：

1. **任务要求：**用户要求交付什么、下游必须消费什么、选用的 workflow 模板要求什么。由创建 workflow 的规划过程生成可编辑节点约定。
2. **执行方法的约束：**所选 skill 的显式声明、经过维护的适配器、原文中可确认的要求。没有声明时保留未知，不自动登记一个空输出。
3. **本次绑定：**实际输入文件或值、上游产物版本、操作模式、项目目录、输出目标、读写范围、适用检查。这些在节点准备阶段确定。

生成节点约定不等于发现了 skill 固有能力。规划器可以根据“请输出一份研究报告”提出 report 输出；这是一项本次任务要求，需要执行器传入并验收，不能宣称原 skill 自带该接口。

约束冲突时不能简单覆盖：例如任务需要两个文件而适配器只支持一个，必须选择可支持的执行方式、拆分节点或暴露冲突；不能改写元数据就声称兼容。

用户不需要手写每个字段。新建 workflow 原本就要确定步骤和依赖，规划器在同一轮生成结果槽位、输入来源和未决项；程序校验结构、引用和条件。常见需求沿用模板；任务没有指定文件名且 skill 未限定时，按项目惯例分配运行专属目标位置。只有真实歧义才需要补充信息。

**自动化减少填写，不消除约定本身。** 如果用户意图、上下文、skill 和下游要求都没有说明交付内容，系统不能证明一个模型猜测就是正确答案。

## 3. 用结果槽位承载不同产出，文件名只是绑定信息

整体结果模型需要容纳以下形态；第一个实现切片只覆盖文本/值和固定数量文档，再扩展代码变更集及动态集合：

- 文本或结构化值：例如问答、审查结论，不强制落成 Markdown 文件。
- 文件或文件集合：媒体类型、必需性、数量条件、成员类型与集合结束条件；具体路径可后绑定。
- 代码变更集：绑定执行前基线和执行归属，包含修改、删除、新增，不能把整个共享工作区 diff 当成本次产出。

状态变更或外部操作可扩展为有实际证据的回执；不能以模型声称“已完成”代替真实状态验证。

槽位和产物分开存储。例如 `node.research.outputs.report` 在执行前存在，表示预期报告；文件内容和版本在写入后才存在。UI 的下载链接只指向实际可取的内容。

输入也要区分“启动所需的业务输入”和“运行中实际读取的辅助资料”。前者绑定用户请求、上游结果、指定文件及相关项目快照；后者可能随研究发现而增加，记入读取记录。执行前可以展示必需输入和允许访问的范围，不能保证预测全部未来读取路径。需要完整封闭输入集合时，执行器必须限制读取范围，新增依赖先修订约定；仅列一个 inputs 字段做不到这种保证。

**一个节点对应一个 coordinator execution，是初版接入约束。** 它可以使用多个 skill，记录加载、使用、贡献关系。某个 skill 需要独立调度、重试和验收时才拆为子节点；不能把读取 SKILL.md 自动当成创建一个业务调用，也不能强称每个文件唯一由最近读取的 skill 生产。

## 4. 执行前、执行中、执行后的准确时机

| 时点 | 工作 | 可见性和约束 |
| --- | --- | --- |
| 发现已安装或新安装 skill | 读取来源与名称等元数据；首次引用按实际 runner 定位；有机器声明则解析 | 目录可用性和已知能力；不默认调用模型解析全部正文 |
| 新建或编辑 workflow | 同一规划过程生成节点目标、结果槽位、依赖和未决条件；引用所选 skill | UI 立即显示预期结果、输入来源及待准备事项 |
| 节点依赖就绪，准备执行 | 读取所选 skill 的必要内容；解析模式、路径、输入版本、检查条件；校验宿主能力和读写范围 | 生成该次执行的契约快照；关键未知未解决时保持 preparing，而非 running |
| 执行中 | 使用绑定上下文工作；发布草稿或新版本；记录新增 skill 和子任务 | 同一个输出槽位展示生成进度和草稿；动态结果在已声明集合下逐项出现 |
| 请求完成 | 提交值、文件引用或变更集；执行器检查必需结果及适用规则 | 缺失或无效结果不能标成功；通过后的精确版本供下游消费 |
| 审查与后续变更 | 按约定和已观察事实决定规则适用性，绑定被检查版本 | 显示待检查、通过、失败或带理由的不适用；内容或相关策略变化使旧证据失效 |

准备阶段允许有界的只读探查；创建运行记录属于执行器元数据操作。若确定业务要求本身需要较多研究、交互或产文，就创建明确的 discovery/需求梳理节点，约定其阶段性结果，不能把大量业务工作藏进“执行前解析”。

这能避免循环：brainstorm 只需先约定 PRD 草稿、未决问题和自身完成条件；由它发现的 build 验收标准在随后 build 节点准备时绑定，不能要求 brainstorm 执行前就拥有未来完整答案。

## 5. 一个具体例子：新 workflow 使用两个现成 skill

用户请求：“调研 A 与 B 的差异，并交付 PDF。”规划阶段生成两个节点：

| 节点 | 本次输入 | 预期结果 | 使用的 skill |
| --- | --- | --- | --- |
| 研究比较 | 问题、范围、可用来源 | 一份有来源的 Markdown 报告；输出位置按仓库惯例绑定 | research |
| 导出 PDF | 上一节点已接纳的报告版本 | 一份 PDF；创建模式；渲染与交付检查 | pdf |

这里“一份 PDF”来自请求，“Markdown 报告”来自 research 原文；文件名由准备过程在项目规则允许范围内补齐。UI 在文件出现前展示这两个结果槽位。

若换成“阅读这份 PDF 并回答问题”，pdf 节点绑定文本结果，而不会错误要求生成 PDF。这不是修改同一个全局 pdf 契约，而是建立另一份调用实例契约。

如果临时安装新的研究 skill：运行器先定位真实来源，再检查它与当前任务约定的兼容性。能够在受管理节点中完成并提交约定结果时可以使用；不需要复制一份 I/O 定义到所有 workflow。适配器覆盖不到的行为保留未知，不能以安装成功宣称约束成功。

## 6. 动态 skill、动态分支和动态数量

技能来源解析必须与实际执行器共用。项目目录、用户目录、插件包与远端服务分别通过 provider 接入；同名冲突要消歧。安装事件和目录 watcher 是刷新提示，实际引用与启动前的定位、内容校验才决定运行对象。

首次引用未知 skill 时按需加载，并缓存可复用的事实。缓存至少关联来源、内容快照、解析器/适配器版本；任务模式和输入绑定缓存另关联 workflow 版本与相关上下文。不能让某次 PDF 创建任务的输出数量污染该 skill 的全局目录。

运行中新增 skill：若只是节点内补充指导，登记使用关系并检查是否改变已有约束；若新增执行单元、输出或资源需求，则先创建新的计划修订及子调用，再开始对应业务操作。已开始调用的约定不得事后改成“无需交付”来掩盖失败。

输出数量未知时，先声明有元素类型和闭合规则的集合，例如“每个发现的模块一份审查结果”。发现节点产出模块清单后，下游按成员创建调用；每个调用执行前已有自己的绑定。整个 workflow 启动前无法知道的文件名，不能伪装成已经知道。

新增的额外文件先记录为候选；需要成为正式业务输出时走计划修订。额外文件不能替代缺失的必需输出。

## 7. 实时产出必须通过执行器闭环

建议提供受控的草稿发布、版本提交和节点完成接口，身份由宿主绑定到 nodeRunId / attempt，不由模型任意填写生产者。

UI 状态链为：预期槽位 → 有草稿可预览 → 已提交待检查 → 已接纳或被拒绝。草稿可提前展示，默认下游只消费已接纳版本。PRD 多轮交互时节点可进入 waiting_input，已有草稿保留，继续回答后发布新版本。

实时性以实际观察或发布能力为界：黑盒程序只在末尾一次性写出文件时，之前只能显示预期结果和真实进度，不能展示尚不存在的正文；尚不可解析的半成品 PDF 也不应显示可用预览。要更细的内容更新，需要 writer 或执行适配器提供中间版本，不能靠 UI 轮询凭空补足。

原生受管理 writer 可以直接产生事件；普通文件写入只能由隔离目录或宿主观察产生候选，再校验和认领。单独扫描共享工作区无法证明完整归属。必要时以受控 worktree/工作目录隔离写入；不能只凭模型给出的文件清单证明没有其他写入。

接纳后的内容使用不可变快照或可验证版本引用；元数据与事件先持久化再通知，UI 重连按游标补读。网络传输和文件写入不是一个天然事务，需要恢复策略，不能仅接一条 SSE 就宣称完成可靠追踪。

初期优先覆盖本地文档和文本/值结果，再扩展变更集。不能拦截执行的宿主只能显示其实际能力，例如“可观察、可验收结果”；不得宣称可强制阻止所有未约定操作。约束完成状态与阻止业务副作用是两个不同保证。

## 8. 模型费用、审查和并发怎么取舍

### 模型费用

| 情况 | 建议处理 |
| --- | --- |
| 未被选中的 skill | 不做额外语义解析 |
| 已有有效声明或适配器覆盖本次模式 | 程序解析、绑定、校验，不另开模型调用 |
| 首次选择且需要理解正文 | 在执行规划器本来就需阅读该 skill 时，同轮提取有关信息；不要额外全文重复解析 |
| 缺口会影响下游、完成判断或并发许可 | 限定问题与参考文件，必要时追加一次有预算的分析；保存证据和未知项 |
| 信息只能来自业务研究或用户选择 | 进入明确的发现/交互步骤，不反复让模型猜 |

预算控制需要限制追加分析轮数、参考文件范围、token 和时长；超限不能强填默认值。具体数值应通过真实调用记录选择，本轮没有数据支持宣称某种覆盖率、成本或延迟。

### 审查适用性

采用固定的通用基础检查，加上由任务类型、操作模式、产物类型、实际变更和项目策略选出的检查。规则有 true / false / unknown 三种适用性；unknown 是待补证据，不是跳过。

例如 PDF 创建检查内容可读和渲染，问答不要求新 PDF；表单模式决定是否检查交互字段；代码变更按实际范围选择已有检查。模型可建议检查项或提供语义审查，不能单方面删掉强制规则或自报不适用。

已有结果只有在输入/产物版本、相关配置、规则及检查器版本一致且符合新鲜度要求时才复用。格式正确不能代替语义质量；规定要做的语义审查不能仅因节省 token 取消。

### 并行与串行

多个无依赖的 skill 元数据/候选分析可以并行，结果合并和冲突决策串行。业务节点能否并行取决于输入依赖、读写资源冲突、外部资源约束和执行器能力；不能让模型仅凭描述返回一个 `parallel: true`。

独立快照上的 code-review 两个方向可以并行，比较范围和规则先解析，最后聚合。修改同一 PRD 或共享 Git 状态的调用需要串行或隔离；写入范围未知时先准备，或以共享资源独占方式运行。多个独立隔离执行仍可并行。

运行中扩大写入范围时，受控执行器须在写入前重新申请资源；不能先写再靠事后冲突检测宣称并发安全。

## 9. 最小实施顺序和验收

先复用现有 canonical TaskPlan，而不是新增一套并行权威计划。[WorkItemV1](/Users/a1234/Documents/code-manager/projects/tenon-local/packages/kernel/src/task-plan/types.ts:62)已有 requirement_refs、acceptance_refs、expected_outputs、validators、resource_claims；需要用明确的版本升级扩展表达能力。绑定后的调用契约是该计划修订的运行快照，不是另一处可随意改写的任务定义。

当前 [WorkItemV2](/Users/a1234/Documents/code-manager/projects/tenon-local/packages/kernel/src/orchestration/v2-types.ts:181)及[调度绑定逻辑](/Users/a1234/Documents/code-manager/projects/tenon-local/packages/automation/src/orchestration/runtime-v2-scheduler.ts:4)按单一选定 skill/绑定运行，因此初版沿用一个 coordinator，独立子任务拆现有 WorkItems。具体反证、初始化循环、旧 artifact intent 仅允许完成后登记等接入约束，见[独立方案审查](/Users/a1234/Documents/code-manager/projects/tenon-local/docs/research/2026-09-11-workflow-contract-design-review.md)。

1. **先建立可验收的节点执行单元。** 一个 coordinator execution、契约快照、结果槽位、提交/完成门禁，与真实生产者证据绑定；沿用已有 child WorkItem 表达需要独立运行的部分。
2. **同一闭环接上 UI。** 准备后的输入输出预览、草稿事件、最终版本和下游绑定，避免先做一套展示用目录后再另做运行规则。
3. **逐步覆盖反例。** 首个切片是文档生产节点与消费者：运行中显示草稿，验收后传递精确版本。随后覆盖 pdf 读/写不同模式、code-review 文本结果，再验证 brainstorm 的多轮更新和动态产出。
4. **扩展来源与自动化。** 复用真实 locator、按需分析、缓存失效、动态分支、检查规则和资源调度；不以全量技能解析器作为第一阶段前置工程。

必要验收：新安装技能首次引用无需重启；同名来源无静默误选；PDF 问答不报缺文件；动态集合只有闭合后才完成；brainstorm 等待回答时不误结算；工作区旧文件不能冒充本次结果；重试/并发不串产物；断线重连可恢复；实际宿主不支持前置拦截时不显示强保证。

还需处理初始化顺序：tenon-open 的初始化会创建后续绑定所需状态，不能让“建立节点执行身份”依赖已经完成整个 open。优先由受控 bootstrap 创建真实运行壳和目标，再进入节点契约绑定；具体源码接缝见独立反证审查，不能用伪造证据绕过现有完成门禁。

## 10. 业界证据及边界

- [Agent Skills 规范](https://agentskills.io/specification)将目录元数据、按需加载的指令和辅助资源分开，没有统一业务 I/O 契约。这支持按需发现，不支持“所有技能自动已有返回类型”。
- [Argo Artifacts](https://argo-workflows.readthedocs.io/en/latest/walk-through/artifacts/)在模板中声明命名输入输出，再在 workflow 中连接具体产物。这里借鉴节点契约与实际执行分离，未建议引入 Kubernetes 或迁移到 Argo。
- [Dagster Dynamic graphs](https://docs.dagster.io/guides/build/ops/dynamic-graphs)先声明动态输出，在运行中产生带 mapping_key 的成员，再 map/collect。这支持“集合结构提前声明，成员运行时确定”的处理；不是预测未知文件名。
- [MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)区分工具 inputSchema、可选 outputSchema、structuredContent 和资源引用；这些可作为明确工具的接入信息，不可冒充任意 Markdown skill 的完整业务契约。
- [A2A 规范](https://a2a-protocol.org/latest/specification/)区分任务状态、input-required 多轮交互与 TaskArtifactUpdateEvent。这支持生命周期和产物更新分离，但并不替本系统实施质量检查与持久化策略。
- [DeepSeek Harness 的 skill loader](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/skill/tool-skill/src/index.ts)和[结构化提交实现](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/subagent/subagent-in-process-driver/src/structured.ts)分别承担加载与受控结果提交。固定源码快照的详情见原调研；推荐借鉴后者的完成边界，不把前者当技能业务执行。

以上为不同机制的证据。本文的组合是针对用户场景的工程判断，不是任一项目已经完整实现的现成方案，也没有基准数据证明它在所有场景中最优。
