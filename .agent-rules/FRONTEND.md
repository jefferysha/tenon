# FRONTEND.md

本文件只在前端任务或前端相关跨端任务中读取。后端-only 任务不得读取本文件，除非需要理解 API contract、生成客户端、UI 行为或跨端验证。

## 前端项目概览

`packages/dashboard-app` 是供本机开发者操作 pipeline 状态机、工作流、AFK 任务和治理能力的客户端渲染 SPA。前端必须沿用当前主版本和既有实现；除非当前任务明确授权并包含兼容性验证，不得主动升级 React、Vite 等主要版本或替换核心技术栈。

| 项 | 内容 |
| --- | --- |
| 语言 | TypeScript；组件使用 TSX |
| 运行时 | Node.js 22 开发/构建；浏览器中运行客户端 SPA |
| 框架 | React 18 客户端渲染 SPA；Vite 6 构建 |
| 包管理工具 | 根目录 npm workspace 与 `package-lock.json`；不得混用其他包管理器 |
| UI/样式 | Radix UI、Tailwind CSS 4、CVA、Lucide；GSAP 负责动效；遵循 Tenon 现有主题 token、布局契约与共享组件 |
| 状态管理 | 优先使用现有 React 本地状态、Context 和自定义 hooks；不得仅为单一功能新增全局状态库 |
| 数据请求 | 通过 `src/api/client.ts` 等既有边界使用 `fetch` 与 SSE；组件不得自行复制协议解析、鉴权 token 或错误映射逻辑 |
| 测试/验证 | Vitest、jsdom、Testing Library；Vite 真实构建与风险匹配的浏览器 smoke check |

## 前端包结构

前端保持现有的“应用外壳 + 功能域 + API/模型/共享层”结构。新增功能应放入最接近的既有功能域；只有形成两个以上领域的稳定复用需求时才允许上移到共享层。

| 路径/包 | 允许放入 | 不允许放入 | 测试/验证 |
| --- | --- | --- | --- |
| `packages/dashboard-app/src/App.tsx`、`main.tsx` | 应用装配、顶层视图选择、Provider 和错误边界 | 具体业务域实现、重复的 API 协议处理 | 同目录 `*.test.tsx`；变更装配时运行应用级测试 |
| `src/api/` | 同源 HTTP/SSE 客户端、鉴权头、响应和错误适配；典型文件 `client.ts` | React 视图、领域展示状态、后端业务规则副本 | 同目录 `*.test.tsx`、`*Integration.test.tsx` |
| `src/model/`、`src/state/` | 纯投影/选择器、跨视图模型、应用级 hooks 与快照连接状态 | DOM 布局、样式、服务端文件写入或锁语义实现 | 同目录 `*.test.ts`、`*.test.tsx` |
| `src/shell/` | 导航、对话框、项目切换、页面外壳和 URL 状态 | 工作流、AFK、治理等领域内部逻辑 | 组件旁 `ComponentName.test.tsx` |
| `src/progress/`、`afk/`、`machine/`、`workbench/`、`advanced/`、`inbox/` | 各功能域的视图、域内 hooks/选择器和局部样式；组件用 PascalCase，纯逻辑用 camelCase | 无关功能域实现；可复用协议代码；跨域复制 | 实现旁同名 `*.test.ts(x)`；交互改动补组件测试 |
| `src/shared/` | 已被多个功能域使用的 UI、动效和无领域偏向工具 | 单一功能专用组件、API 调用、可变全局业务状态 | 与实现同目录的 `*.test.ts(x)` |
| `src/i18n/` | 翻译资源、语言 Provider、翻译 key 类型与回退策略 | JSX 页面结构、协议常量、只服务单一组件的临时文本映射 | `i18n.test.tsx` 及受影响视图测试 |
| `src/lib/`、`types.ts` | 无领域偏向的小型工具与前后端共享响应形状的客户端声明 | 大型业务流程、未经服务端契约核对的猜测类型 | 工具旁定向测试；契约改动做跨端验证 |
| `src/index.css`、功能域 `*.css` | 全局主题/token、基础样式及域内复杂布局 | 可由现有 Tailwind utility 清晰表达的重复样式；无关域样式 | 构建并进行桌面/移动、明/暗主题浏览器检查 |

## 编码规范

前端采用“现有风格 + 严格类型与交互测试”规范：

- 组件、类型和文件中的 React 组件使用 PascalCase；函数、变量、纯逻辑文件使用 camelCase；自定义 Hook 必须以 `use` 开头；测试文件与被测实现同名并使用 `*.test.ts(x)`。
- 新增或本次修改的生产代码不得使用显式 `any`、隐式 `any`、非空断言或无校验的类型断言；外部输入先以 `unknown` 接收并收窄。触碰已有违规代码时必须在修改边界内消除，范围外遗留可保留但不得扩散。
- 每个新增或修改的 React 组件必须声明显式 Props 类型；组件只负责一个清晰视图或交互边界，数据投影、协议适配和复杂副作用分别放入 model、api 或 hook。
- 状态默认归属最近使用它的组件或功能域；只有多个功能域需要一致、长期共享的状态时才提升到 Context 或 `src/state/`，不得以 prop drilling 不便为由直接引入全局状态库。
- 所有请求与 SSE 连接必须经过 `src/api/` 的统一客户端边界，处理取消/断线、非 2xx、无 JSON 体和服务端错误信封；视图必须提供适合场景的 loading、error、empty 和重试/恢复路径。
- 新增用户可见文本必须接入现有中英文国际化资源；不得在组件内新增只有单一语言的硬编码文案，协议字段、日志和开发诊断文本除外。
- 新增或修改交互必须覆盖每个可达分支，包括成功、失败、禁用、加载、空态和键盘路径；无法在自动化测试中覆盖的浏览器行为必须实际 smoke check，并在交付中说明证据。
- 列表、订阅、动画和昂贵投影必须避免无界重复工作；只有经测量或调用频率明确时才引入 memoization，不得为假设性能问题增加复杂度。

- 使用仓库锁文件对应的包管理工具；不得混用 npm/yarn/pnpm/bun。
- 新增代码前读取同目录相邻组件、hooks、样式、测试和路由实现，遵循已有命名、props、错误处理、状态管理和测试风格。
- 优先复用项目设计系统、组件库、主题 token 和布局约束；修改全局 theme/token、路由结构、构建配置或共享组件 API 前必须说明影响范围。
- UI 改动必须考虑 keyboard、focus、语义标签、ARIA（仅在语义标签不足时使用）、色彩对比、响应式和错误/空/加载状态。
- 数据请求层必须处理 loading、error、empty、重试或取消语义；不得把后端响应结构散落到无关组件中。
- 不得为单次需求引入未使用的抽象、全局状态或新依赖；任务已明确授权且依赖必要、兼容、可回退时可直接新增，否则在扩大范围或引入重大维护/安全风险前确认。
- 修改公共组件、shared hooks、路由守卫、权限展示或客户端缓存策略时，必须运行匹配风险的测试或浏览器 smoke check。

## 文件长度规范

文件长度按以下门槛执行：

- 普通组件或 hooks 超过 250 行应考虑拆分，超过 400 行必须拆分。
- 页面/路由文件超过 350 行应考虑拆分，超过 600 行必须拆分。
- 纯配置、生成文件、schema、story fixtures 或测试快照可例外，但最终回复必须说明例外原因。
- 拆分优先按视图区块、业务能力、状态逻辑、数据适配、纯展示组件和测试夹具分离。

## 前端架构约束

前端保持现有功能域分层，依赖方向为 `App/main/shell → 功能域视图 → model/state → api`；各层可以依赖 `shared/lib/i18n`，共享层不得反向导入功能域或应用装配层。

- `App.tsx`、`main.tsx` 和 `shell/` 只负责装配、导航、Provider、错误边界及跨域编排，不承载可独立测试的领域算法或协议解析。
- 功能域拥有自己的视图、局部状态和域内纯逻辑；跨域调用必须通过稳定的 props、回调、共享模型或 API 边界，不得直接读取另一功能域的组件内部状态。
- `model/` 负责无 UI 的投影、选择器和规则映射，`state/` 负责真正跨视图的连接状态，`api/` 是 HTTP/SSE、鉴权及错误信封的唯一客户端协议边界。
- 状态保留在最低可用层；只有两个以上功能域需要同一语义和生命周期时才可提升。服务端真相不得复制为另一套可独立漂移的客户端业务规则。
- 代码只有在至少两个稳定使用方、语义无领域偏向且拥有可独立测试的契约时才可进入 `shared/` 或 `lib/`；测试工具进入 `testkit.ts`，不得混入生产入口。
- 不得新增反向依赖、循环依赖，或让 `shared/lib` 成为无边界杂物目录；必须跨越既有层级时，在实现和交付说明依赖原因与验证证据。

架构自检要求：

- 本次改动是否放在正确包/层级。
- 是否新增跨层依赖或循环依赖。
- 是否把业务规则、数据适配、展示组件和副作用放在合适位置。
- 是否需要同步更新类型、mock、story、e2e 或 API contract。

## 前端验证

前端按改动风险选取以下已存在的验证，不得编造未配置的脚本：

| 目的 | 命令/方式 | 适用范围 |
| --- | --- | --- |
| 类型检查 | `npm run typecheck:web` | 所有 TypeScript/TSX、配置或跨端类型改动 |
| 前端单元/组件测试 | `npm run test:web` | 前端行为、状态、组件、API client 与 i18n 改动 |
| 定向 Vitest | `npx vitest run --config packages/dashboard-app/vitest.config.ts <test-file>` | 低风险局部改动的快速反馈；交付时列出实际文件 |
| 前端生产构建 | `npm run build:web` | 依赖、资源、样式、Vite 配置或准备交付的前端改动 |
| 跨端构建 | `npm run build` | 共享类型、server/client 契约或全栈改动 |
| Dashboard 浏览器 e2e | `npm run build` 后 `npm run test:e2e -- --project=chromium`（`e2e/dashboard/`，隔离 HOME 与随机端口，种子项目经真实 CLI 建） | 新建项目向导、项目页、工作流页、工作台测试页签、库、断线重连等已覆盖流程的改动；改这些页面的 `data-testid` 或文案须同步 e2e |
| 真实浏览器 smoke | 先执行 `npm run build:web && npm run build:server`，再按 README 启动 `npx tenon-dashboard`，检查真实同源页面 | 布局、交互、主题、响应式、SSE、写端点或鉴权行为；至少覆盖受影响的桌面/移动视口与明/暗主题 |

仓库当前没有专用 lint、format npm script；Dashboard 的浏览器 e2e 是上表的 `npm run test:e2e`，其余前端 E2E 不存在，不得声称已运行。只有当前任务明确要求并授权新增工具时，才可引入相应配置，并同时更新本节和 CI/文档。

默认要求：

- 样式或交互改动优先做浏览器 smoke check；可用时截图验证桌面和移动视口。
- 修改表单、导航、权限、支付、账号、安全、数据提交或跨端 API 行为时，至少运行相关测试或说明无法运行原因。
- 声称“页面正常”前必须实际打开或运行相应检查；不能只凭构建成功推断 UI 正常。
